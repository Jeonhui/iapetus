# Iapetus — Agent Virtual Desktop Platform 기획명세서

### 규범 우선순위

같은 사실이 여러 곳에 나오면 **아래 순서로 우선한다.** 이 규칙이 없으면 개정할 때마다 낡은 서술이 남아 서로 다른 두 진실이 생긴다.

| 순위 | 대상 | 성격 |
|---|---|---|
| 1 | **§8.2 API 공통 규약 · §8.3 리소스 스키마** | 와이어 형식의 유일한 규범 |
| 2 | **§19.5 · §19.6 전송 계약** | 내부 프로토콜의 유일한 규범 |
| 3 | 그 외 본문의 명시적 결정 | |
| 4 | §5 등의 JSON 예시 | **예시일 뿐 규범이 아니다.** 필드 형식이 어긋나면 §8.3이 맞다 |

예시는 개념을 보여주기 위한 것이며, 필드 이름·타입·형식의 근거로 인용하지 않는다.

**같은 순위끼리 충돌할 때 — 주제별 단일 출처.** 위 표는 *규범 vs 예시* 만 가른다. 수치나 결정이 본문 여러 곳에 나오면(둘 다 3순위) 표로는 판정할 수 없으므로, **주제마다 전용 절 하나를 단일 출처로 둔다.**

| 주제 | 단일 출처 |
|---|---|
| 용량·배치 밀도 | §12.4 |
| 지연 예산·미디어 파라미터 | §6.3 |
| 상한·타임아웃·식별자 | §8.2 |
| 상태 전이 | §5.4 |
| 권한·스코프 | §8.1 |

다른 절에서 이 값들을 인용할 때는 **수치를 복사하지 말고 절을 참조한다.** 복사한 수치는 원본이 바뀌어도 남는다.

## 1. 개요

### 1.1 한 줄 정의

**Iapetus는 AI Agent와 사람이 함께 소유하고 조작하는, 영속적인 가상 데스크톱(Computer)을 제공하는 플랫폼이다.**

Agent는 Iapetus 외부(사용자 제품, 에이전트 런타임, 워크플로 엔진)에 존재하고, Iapetus는 Agent가 원격으로 붙어서 화면을 보고 클릭·입력하고 앱을 실행하는 **컴퓨터 리소스**만 제공한다.

**Desktop은 사람과 Agent가 공동 소유한다. 두 주체의 권한은 동등하다.**

- **Agent**: root / Administrator. 임의 프로그램 실행·설치·삭제, 파일시스템 전체, 시스템 설정 변경.
- **사람(소유자)**: 동일. 브라우저로 접속해 자기 PC처럼 직접 쓴다. Agent가 할 수 있는 모든 것을 할 수 있다.

Agent는 사람의 **하위 권한 대리인이 아니라 동등한 위임자**다. 둘은 **같은 OS 세션을 공유**한다 — Agent가 메신저에 로그인하면 사람도 그 로그인 상태를 그대로 본다. 반대도 같다.

제약은 Desktop **안**이 아니라 Desktop **경계**에 건다 (§9 참조).

### 1.2 문제 정의

현재 Agent 자동화 도구의 한계:

| 방식 | 한계 |
|---|---|
| API/MCP 연동 | API가 없는 앱(사내 ERP, 데스크톱 메신저, 엑셀 매크로)은 자동화 불가 |
| 브라우저 자동화 (Playwright 등) | 웹만 가능. 데스크톱 앱 불가 |
| 로컬 PC 제어 | 사용자 PC 점유. 병렬 실행 불가. 항시 실행 불가. 격리 없음 |
| 일회성 샌드박스 | 세션이 끝나면 로그인 상태·설치 앱·파일이 사라짐 |

핵심 결핍은 **"Agent 전용의, 죽지 않는, 로그인 상태가 유지되는 컴퓨터"** 다.

### 1.3 해결 방향

Agent에게 **영속 데스크톱(Persistent Desktop)** 을 1급 리소스로 부여한다.

```text
Agent = Brain(LLM) + Memory + Tools + Routines + Computer(Iapetus)
```

- 사용자가 브라우저를 닫아도 Desktop은 살아 있다.
- 메신저 로그인, Chrome 쿠키, 다운로드 파일이 그대로 남는다.
- 다음 실행 때 같은 Desktop에 재접속하면 이어서 작업한다.

### 1.4 범위 (Scope)

**In Scope**
- 가상 데스크톱 프로비저닝/수명주기 관리
- 통합 Computer API (screenshot / click / type / key / scroll / launch_app …)
- OS 추상화 (Linux, Windows)
- 앱 카탈로그 및 임의 프로그램 실행·설치 (관리자 권한)
- 영속 스토리지 및 세션 상태 보존
- **사람용 풀 액세스 뷰어** (관찰 + 완전 조작 + 파일 송수신)
- 사람 ↔ Agent 제어권 중재
- 외부 Agent를 위한 REST/WebSocket API, SDK, MCP 서버

**Out of Scope (v1)**
- LLM/추론 엔진 제공 (Agent는 외부에 존재)
- Agent 프롬프트/플래닝 프레임워크
- 요소 단위 시맨틱 접근성 트리(a11y tree) 기반 조작 → v2 검토
- 모바일 OS(Android/iOS) 데스크톱 → v2 검토

## 2. 목표 및 성공 지표

### 2.1 제품 목표

1. Agent가 **OS 종류를 몰라도** 동일한 API로 컴퓨터를 조작할 수 있다.
2. Agent가 그 Desktop에 대해 **사람과 동등한 완전 권한**을 가진다. "이 앱은 못 열어요"가 없다.
3. 사람도 **같은 Desktop에 같은 권한으로 직접 접속**해 자기 PC처럼 쓸 수 있다.
4. 둘이 **같은 OS 세션·같은 로그인 상태**를 공유한다.
5. Desktop이 **분 단위가 아닌 주/월 단위로 영속**한다.
6. 하나의 계정이 **수십~수백 개의 Desktop을 병렬 운영**할 수 있다.

### 2.2 성공 지표 (KPI)

| 지표 | 목표 | 조건 |
|---|---|---|
| 콜드 스타트 (생성 → ACTIVE) | Linux < 15s, Windows < 60s | 웜 풀 미사용 |
| 웜 스타트 (SUSPENDED → ACTIVE) | < 5s | **로컬 NVMe 스냅샷 한정.** 네트워크 스토리지는 < 20s |
| 즉시성 액션 왕복 p95 (`click`, `key`, `scroll`) | < 300ms | 동일 리전 |
| 지속성 액션 (`type`, `mouse.drag`) | 오버헤드 < 150ms | 입력 지속 시간 제외한 순수 오버헤드로 측정 |
| `screenshot` p95 (1080p, JPEG q80) | < 500ms | 신선도 계약(§6.3) 충족까지 포함한 값. 캐시 프레임 반환이 아님 |
| 스트리밍 프레임 지연 (glass-to-glass p95) | < 200ms | **동일 리전 + 전 계층 수신 뷰어 한정.** 소프트웨어 인코딩 예산 57~199ms로 여유가 거의 없다. GPU 티어는 ~179ms (§6.3) |
| 계층 강등 발생률 | < 5% | 강등된 뷰어는 위 지연 KPI 대상이 아니므로, 강등 자체를 지표로 관리 |
| **로그인 세션 보존율** (suspend/resume 후 앱 재로그인 불필요) | **> 99.9%** | 100회 중 1회 실패하면 제품 신뢰가 무너지므로 99%는 불충분 |
| 제어권 선점 반영 시간 | < 500ms | 사람이 선점 버튼을 누른 시점 → Agent가 `CONTROL_LOST` 를 받는 시점 (§5.6) |
| 월간 가용성 | Linux 99.5% / Windows 99.0% | 인프라가 다르므로 분리 약속 (§12.1) |
| 첫 성공까지 시간 (TTFA, 중앙값) | < 15분 | 가입 → 첫 액션 성공. Phase 2부터 측정 (§14.5) |

## 3. 사용자 및 사용 시나리오

### 3.1 주 사용자

| 유형 | 설명 | 니즈 |
|---|---|---|
| **Agent 개발자** | Agent 제품을 만드는 개발사 | 안정적인 Computer Use 백엔드, SDK |
| **자동화 운영자** | 사내 업무 자동화 담당 | 사내 프로그램 자동화, 실행 로그, 감사 |
| **Desktop 소유자 (사람)** | Agent 제품 사용자 | "내 Agent와 내가 **같은 컴퓨터**를 함께 쓴다"는 경험. 직접 접속해 로그인·설치·조작 |

### 3.2 대표 시나리오

**S1. 웹 검색**
```text
"크롬 열어서 코쏘 검색해봐"
→ launch_app("chrome") → screenshot → click(검색창) → type("코쏘") → key("Enter") → screenshot
```

**S2. 데스크톱 앱 메시지 발송**
```text
"메신저 열어서 홍길동한테 메시지 보내"
→ launch_app("messenger")  # 이미 로그인 상태 유지됨
→ screenshot → click(친구검색) → type("홍길동") → click(대화방)
→ click(입력창) → type("안녕하세요") → key("Enter")
```

**S3. 정기 루틴 (외부 Agent 스케줄러가 트리거)**
```text
매일 09:00
→ POST /v1/desktops/{id}/resume      # 기존 Desktop 재개
→ app.list 로 실제 상태 확인 (§7.4 계약) → 살아있으면 재사용, 아니면 재실행
→ 뉴스 검색 → 정리
→ 메신저 세션 재사용 → 메시지 전송
→ POST /v1/desktops/{id}/suspend     # 다시 절전
```

**S4. 사람 개입 (Handover)**
```text
Agent가 2FA 인증 화면에서 막힘
→ Agent가 사용자에게 알림
→ 사용자가 뷰어 접속 → 제어권 즉시 선점 → 직접 입력 → Agent에게 반환
```

**S5. 사람이 먼저 세팅 (Agent는 이어받음)**
```text
사용자가 Desktop 생성 직후 직접 접속
→ 업무용 메신저 설치 + 로그인 (2FA 포함)
→ 사내 VPN 클라이언트 설치, 인증서 등록
→ 접속 종료
→ 이후 Agent가 그 로그인 상태를 그대로 사용
```
Agent에게 자격증명을 넘기지 않고도 Agent가 로그인된 앱을 쓸 수 있다. **이것이 공동 소유 모델의 핵심 이득이다.**

**S6. 사람이 결과 확인·수정**
```text
Agent가 엑셀 보고서 작성 → 저장
→ 사용자가 접속해 같은 엑셀 파일 열어 직접 수정
→ 파일 다운로드 또는 Agent에게 후속 지시
```

## 4. 경쟁·대안 분석

### 4.1 대안 지형

| 제품 | 무엇을 주는가 | 영속성 | 데스크톱 앱 | 사람 공동 사용 |
|---|---|---|---|---|
| **E2B** | 코드 실행용 샌드박스 (주로 헤드리스) | 세션 한정 | ❌ | ❌ |
| **Browserbase** | 관리형 헤드리스/헤드풀 브라우저 | 브라우저 프로필 일부 | ❌ 브라우저만 | 관찰용 라이브뷰 |
| **Anthropic Computer Use** | 모델의 화면 조작 **능력** (인프라 아님) | — | 실행 환경에 의존 | — |
| **Scrapybara / Kernel 류** | 원격 데스크톱/브라우저 인스턴스 | 제한적 | 일부 | 제한적 |
| **RPA (UiPath 등)** | 규칙 기반 데스크톱 자동화 | 사내 PC/VM | ✅ | 사람 PC 점유 |
| **Iapetus** | **영속 데스크톱 + 공동 소유** | ✅ 주/월 단위 | ✅ | ✅ 동등 권한 |

### 4.2 차별점 3축

1. **영속성** — 대부분의 대안은 작업이 끝나면 환경을 버린다. Iapetus는 로그인 세션·설치 앱·파일을 **다음 실행까지 들고 간다.** "매번 다시 로그인"이 사라지는 것이 실무에서 가장 큰 차이다.

2. **데스크톱 앱** — 브라우저 자동화 제품은 웹만 다룬다. 한국 업무의 상당 부분(데스크톱 메신저, 엑셀, 사내 ERP, 관공서 프로그램)은 웹이 아니다. **API가 없는 소프트웨어를 자동화한다**는 것이 Iapetus가 여는 시장이다.

3. **공동 소유** — 다른 제품에서 사람은 관찰자이거나, 사람과 봇이 다른 환경을 쓴다. Iapetus는 **같은 컴퓨터를 동등 권한으로 나눠 쓴다.** 사람이 로그인해 두면 Agent가 그 세션을 쓴다(S5) — 자격증명을 Agent에게 넘기지 않고도 자동화가 된다.

### 4.3 이기지 못하는 영역 (솔직한 약점)

| 영역 | 우위 제품 | 이유 |
|---|---|---|
| **순수 코드 실행 속도·비용** | E2B, Vercel Sandbox | 데스크톱 세션·디스플레이 서버가 없는 쪽이 가볍고 싸다. 코드만 돌릴 거면 우리를 쓸 이유가 없다 |
| **대규모 병렬 웹 스크래핑** | Browserbase, 헤드리스 클러스터 | 헤드리스가 GUI보다 훨씬 저렴하고 밀도가 높다 |
| **결정론적 사내 자동화** | 기존 RPA | 규칙 기반이 LLM보다 안정적이고 감사가 쉬운 영역이 분명히 있다 |
| **초저지연 원격근무 데스크톱** | VDI (Citrix, AWS WorkSpaces) | VDI는 사람 전용으로 수십 년 최적화됐다. 우리는 Agent 우선 설계다 |
| **비용 최저가** | 모든 헤드리스 대안 | 데스크톱 1개 유지 비용이 구조적으로 높다 |

**포지셔닝 결론:** "모든 자동화"를 노리지 않는다. **API가 없고, 로그인 상태가 필요하고, 사람이 가끔 개입해야 하는 업무** — 이 교집합이 Iapetus의 영역이다. 이 조건 중 하나라도 빠지면 더 싼 대안이 존재하며, 영업 단계에서 그것을 인정하는 편이 낫다.

## 5. 핵심 개념 및 데이터 모델

### 5.1 개념 계층

```text
Organization
  └── Project
        └── Desktop          # 영속 컴퓨터 (1급 리소스)
              ├── Owners     # 사람(들) + Agent(들). 전원 동등 권한
              ├── Image      # 어떤 OS/앱이 설치된 템플릿인가
              ├── Volume     # 영속 디스크 (홈 디렉토리, 앱 데이터)
              ├── OS Session # 단 하나. 사람·Agent가 공유
              ├── Apps       # 카탈로그(바로가기) + 실행중 프로세스
              └── Session    # 제어 연결 (사람/Agent 각각 생성 가능)
```

### 5.2 소유권 및 Actor 모델

**Desktop에는 여러 Owner가 붙을 수 있고, 종류가 달라도 권한은 완전히 동일하다.**

```json
{
  "desktop_id": "dsk_01H8XK",
  "owners": [
    { "type": "human", "id": "usr_kim",    "role": "OWNER" },
    { "type": "agent", "id": "agent_123",  "role": "OWNER" }
  ]
}
```

| 항목 | 사람 Owner | Agent Owner |
|---|---|---|
| OS 권한 | root / Administrator | root / Administrator (동일) |
| 프로그램 실행·설치 | ✅ | ✅ |
| 파일시스템 전체 | ✅ | ✅ |
| 시스템 설정·재부팅 | ✅ | ✅ |
| 접속 수단 | 브라우저 뷰어 (WebRTC) | Computer API (REST/WS/MCP) |
| Desktop 삭제 | ✅ | ✅ (`confirm_name` 필요) |
| Owner 추가/제거 | ✅ | ❌ **사람만 가능** |

**비대칭은 두 가지뿐이다.** ① Owner 목록 변경은 사람만 할 수 있다(아래). ② 제어권 선점은 사람만 할 수 있다(§5.6). 그 외 모든 권한은 동일하다. Agent가 스스로 다른 Agent를 초대하거나 사람 Owner를 제거할 수 없다. 권한 자체는 동등하되, **권한을 나눠주는 권한은 사람에게만 둔다.**

#### Desktop 유형 — 개인용과 공용을 구분한다

Owner가 여러 사람이면 **로그인 세션이 공유되므로 A의 개인 계정을 B가 그대로 본다.** 이는 버그가 아니라 단일 OS 세션 설계의 필연이며, 따라서 용도를 유형으로 나눠 기대를 맞춘다.

| `desktop_type` | 사람 Owner | 용도 | 개인 계정 로그인 |
|---|---|---|---|
| **`personal`** (기본) | **1명** | 개인 업무 자동화 | ✅ 허용 |
| **`shared`** | 다수 | 팀 공용 봇, 사내 시스템 자동화 | ⚠️ **비권장.** 조직 공용 계정만 사용 |

- `personal` 에 두 번째 사람 Owner를 추가하려면 `shared` 로 전환해야 하며, 전환 시 **"기존 로그인 세션이 새 Owner에게 노출된다"는 경고에 명시적으로 동의**해야 한다. 되돌릴 수 없다.
- `shared` Desktop의 뷰어에는 상시 배너를 띄운다: **"이 컴퓨터는 N명과 공유됩니다. 개인 계정으로 로그인하지 마세요."**
- 기술적으로 개인 계정 로그인을 막지는 않는다 — 무엇이 개인 계정인지 판별할 수 없기 때문이다. **경고와 유형 구분까지가 플랫폼의 책임이고, 그 이상은 조직 정책의 영역이다.**

**단일 OS 세션 공유:** Desktop 안에는 OS 사용자 계정과 데스크톱 세션이 **하나만** 존재한다. 사람과 Agent가 동시에 로그인하는 별도 계정을 만들지 않는다.

| 왜 계정을 나누지 않는가 | 결과 |
|---|---|
| 앱 로그인 상태(메신저, Chrome 프로필)는 사용자 프로필에 귀속됨 | 계정을 나누면 Agent가 사람의 로그인을 못 씀 → 제품의 존재 이유가 사라짐 |
| GUI 자동화는 활성 디스플레이 1개를 전제 | 세션을 나누면 좌표계·포커스가 갈라짐 |
| 감사는 OS 계정이 아니라 **제어 세션(actor)** 으로 구분 | 누가 했는지는 §9.4 감사 로그로 추적 |

### 5.4 Desktop 상태 머신

```text
              create
                │
                ▼
          PROVISIONING ──fail──► ERROR ──delete──┐
                │                                │
                ▼                                │
      ┌──────► ACTIVE ◄──┐                       │
      │      (부팅 완료,   │                       │
      │   OS·앱 실행 중)   │ 복구                   │
      │         │        │                       │
      │         └─► DEGRADED (기능 제한, §19.4)    │
      │         │                                │
   resume       │ idle_timeout / 명시적 suspend    │
      │         ▼                                │
      └──── SUSPENDED ──────────────┐            │
                │                   │            │
             restore            delete           │
                │                   ▼            ▼
                └──────────── DELETING ──24h──► TERMINATED
                              (복구 유예)
```

| 상태 | 의미 | 과금 |
|---|---|---|
| `PROVISIONING` | 생성 중 | 없음 |
| `ACTIVE` | 부팅 완료. 접속자 유무와 무관하게 OS·앱이 살아 있음 | 컴퓨트 |
| `DEGRADED` | ACTIVE의 하위 상태. 동작하지만 기능 제한 (데몬 프로토콜 불일치, Guest Token 갱신 실패 등). §19.4 | 컴퓨트 |
| `SUSPENDED` | 메모리 스냅샷 후 절전, 디스크 유지 | 스토리지만 |
| `ERROR` | 복구 불가 | 스토리지만 |
| `DELETING` | 삭제 요청됨. 24시간 복구 유예 중(§10.3). API 접근 차단, 볼륨은 남아 있음 | 스토리지만 |
| `TERMINATED` | 삭제 완료 | 없음 |

**READY/RUNNING을 나누지 않는 이유:** "접속자가 있는가"는 Session 리소스가 이미 표현한다. Desktop 상태를 둘로 쪼개면 과금·오케스트레이션만 복잡해지고 Agent에게는 의미가 없다. 접속 여부는 `sessions[]` 와 `last_active_at` 로 확인한다.

**idle 판정:** `idle_timeout_sec` 는 **활성 Session이 0개가 된 시점부터** 카운트한다. 사람·Agent 어느 쪽이든 붙어 있으면 카운터가 리셋된다. 접속자가 없어도 Agent가 백그라운드 작업(빌드, 다운로드)을 돌려야 하면 `auto_suspend: false` 로 끈다.

**핵심 규칙:** `SUSPENDED → ACTIVE` 재개 시 **실행 중이던 앱과 창 배치가 그대로 복원**된다 (보장 범위는 §7.4).

### 5.5 App

App은 **제한 장치가 아니라 편의 바로가기**다. 카탈로그에 없는 프로그램도 경로/명령으로 직접 실행할 수 있다.

```json
{
  "key": "acme_messenger",
  "name": "Acme Messenger",
  "os": ["windows"],
  "launch": { "type": "exec", "command": "C:\\Program Files\\Acme\\Messenger.exe" },
  "singleton": true,
  "window_match": { "title_regex": "^Acme Messenger" },
  "installed": true,
  "state": "RUNNING",
  "pid": 4820,
  "windows": [{ "id": "win_1", "title": "Acme Messenger",
               "bounds": { "x": 100, "y": 100, "width": 420, "height": 720 } }]
}
```

### 5.6 Session

사람 또는 Agent가 Desktop에 붙어 있는 제어 연결. **여러 Session이 동시에 존재할 수 있지만, 입력 제어권(control lease)은 항상 1개다.**

```json
{
  "id": "ses_9f2",
  "desktop_id": "dsk_01H8XK",
  "actor": { "type": "agent", "id": "agent_123" },
  "control": "WRITE",
  "lease_expires_at": "2026-08-15T09:47:00Z",
  "heartbeat_interval_sec": 30,
  "started_at": "2026-08-15T09:42:00Z"
}
```

| `control` | 의미 |
|---|---|
| `WRITE` | 입력 제어권 보유. 마우스·키보드·앱 실행 가능 |
| `READ` | 관찰만. screenshot·스트리밍·`app.list` 가능, 입력 불가 |

#### 제어권 중재 규칙

권한은 동등하지만, **물리적으로 키보드는 하나**다. 두 주체가 동시에 타이핑하면 화면이 망가진다. 따라서 권한이 아니라 **입력 순서만 중재**한다.

| 상황 | 결과 |
|---|---|
| 아무도 `WRITE` 미보유 | 먼저 요청한 쪽이 즉시 획득 |
| Agent 보유 중 → 사람이 요청 | **즉시 선점.** Agent는 `READ` 로 강등, `control.revoked` 이벤트 수신 |
| 사람 보유 중 → Agent가 요청 | **즉시 선점 안 됨.** `human_idle_sec`(기본 **300s**) 무입력 후 자동 이양, 또는 사람이 명시적으로 반환. 60s로 두면 S4의 2FA 입력(문자 확인·앱 전환) 중에 Agent가 키보드를 뺏는다 |
| **Agent 보유 중 → 다른 Agent가 요청** | 선착순 유지. **즉시 거부**(`CONTROL_HELD` + `retry_after_sec`). 선점 권한은 사람에게만 있다 |
| 사람 보유 중 → 다른 사람이 요청 | 선착순 유지. **즉시 거부**(`CONTROL_HELD`) — 큐를 두지 않는 정책은 사람끼리도 동일하다 |
| lease 만료 (heartbeat 끊김) | 3× interval 무응답 시 회수. 진행 중 액션은 완료까지 대기 후 회수 |

**비대칭의 근거:** 사람이 Agent보다 권한이 높아서가 아니다. 사람은 대기 큐에서 기다릴 수 없고, 개입은 대개 Agent가 막혔거나 잘못하고 있을 때 일어나기 때문이다. 반대 방향(Agent가 사람을 밀어냄)은 사람의 입력을 유실시키므로 금지한다.

**액션 중 선점:** 실행 중인 개별 액션은 중단하지 않는다(반쯤 입력된 문자열 방지). 현재 액션 완료 → 제어권 이양 → 이후 호출은 `CONTROL_LOST`.

**제어권 이양 시 입력 상태를 초기화한다.** `key.down`/`mouse.down` 은 별도 액션이므로(§7.2), Agent가 `key.down ctrl` 을 보낸 상태에서 선점당하면 **Ctrl이 눌린 채 남아 사람의 타이핑이 전부 단축키로 해석된다.** 이양 직전 `iapetusd` 가 모든 눌린 키·마우스 버튼을 강제로 떼고(`key.up` 전체 발행), 새 보유자에게 깨끗한 입력 상태를 넘긴다.

#### 동시 요청 처리 — 큐가 아니라 거부

같은 Desktop에 두 주체가 동시에 일을 시키는 상황은 실제로 일어난다. 대표적으로 **09:00 스케줄 루틴이 도는 중에 사용자가 실시간 요청**을 넣는 경우다.

**결정: v1은 큐잉하지 않고 즉시 거부한다.**

```jsonc
// POST /v1/desktops/{id}/sessions  → 409
{
  "error": "CONTROL_HELD",
  "holder": { "type": "agent", "id": "agent_123", "since": "2026-08-15T09:00:04Z" },
  "retry_after_sec": 30,
  "hint": "사람 actor는 control/acquire 로 즉시 선점할 수 있습니다"
}
```

| 대안 | 채택 | 이유 |
|---|---|---|
| **즉시 거부 + `retry_after_sec`** | ✅ v1 | 호출자가 상황을 알고 스스로 결정. 구현 단순. 무한 대기 없음 |
| 서버 측 큐잉 | ❌ | Agent 작업은 수 분이 걸릴 수 있어 큐 대기가 타임아웃을 넘김. 큐 순서·기아·취소 처리가 전부 새 복잡도 |
| 강제 선점 (Agent끼리) | ❌ | 진행 중 작업이 화면 중간 상태로 깨져 복구 불가 |

**Agent 개발자 가이드:** 동시성이 필요하면 **Desktop을 나눈다.** 이것이 이 플랫폼의 확장 모델이다. 하나의 Desktop을 여러 Agent가 나눠 쓰려는 설계는 GUI가 공유 자원이라는 사실을 거스른다.

```text
❌  Desktop 1개 ← Agent A, Agent B, Agent C   (경합)
✅  Desktop 3개 ← Agent A, B, C 각각            (병렬)
```

**예외는 사람뿐이다.** 사람은 선점할 수 있다(위 표). 사람이 Desktop을 나눠 갖는 것은 의미가 없기 때문이다 — 사용자가 보고 싶은 것은 **지금 Agent가 쓰고 있는 그 화면**이다.

### 6.2 OS 추상화

Agent는 Linux인지 Windows인지 알 필요가 없다. 동일한 Computer API가 각 OS의 `iapetusd` 안에서 네이티브 구현으로 매핑된다.

| Computer API | Linux (XFCE/X11) | Windows |
|---|---|---|
| `screenshot` | X11 XGetImage / PipeWire | DXGI Desktop Duplication |
| `click`, `move` | XTEST | SendInput |
| `type`, `key` | XTEST + IME | SendInput + IME |
| `scroll` | XTEST button 4/5 | SendInput WHEEL |
| `launch_app` | exec + .desktop | CreateProcess |
| `window.*` | EWMH / wmctrl | Win32 Window API |
| `clipboard.*` | X11 selection | Win32 Clipboard |

**차이 노출 원칙:** OS별로 존재하지 않는 기능은 `capabilities`로 사전 공표하고, 호출 시 `UNSUPPORTED_ON_OS` 에러를 반환한다. 조용히 무시하지 않는다.

### 6.3 화면 파이프라인 — 사람이 보는 경로와 Agent가 보는 경로

**요구:** 사람은 Desktop을 **실시간으로 보고 직접 조작**할 수 있어야 하고, Agent는 **판단용 정지 화면**을 받아야 한다. 두 요구는 성격이 완전히 다르므로 파이프라인을 분리하되 **캡처 소스는 하나만 둔다.**

| | 사람 (뷰어) | Agent |
|---|---|---|
| 원하는 것 | 끊김 없는 연속 화면 | 특정 시점의 정확한 한 장 |
| 지연 요구 | 낮을수록 좋음 (< 200ms) | 관대함 (< 500ms) |
| 품질 요구 | 손실 압축 OK, 움직임 중요 | **텍스트 판독 가능해야 함** (LLM이 글자를 읽음) |
| 빈도 | 30fps 연속 | 액션당 1회, 산발적 |
| 형식 | H.264 비디오 스트림 | JPEG/PNG 단일 프레임 |

Agent에게 비디오 스트림을 주지 않는다. LLM은 프레임 시퀀스가 아니라 한 장을 본다. 반대로 사람에게 스크린샷 연사를 주지 않는다. 대역폭이 10배 든다.

#### 전송 프로토콜 선택

| 후보 | 지연 | 브라우저 네이티브 | 대역폭 | 판정 |
|---|---|---|---|---|
| **WebRTC** | 50~150ms | ✅ | 적응형 0.5~8Mbps | ✅ **채택** |
| VNC / RFB (noVNC) | 200~500ms | ❌ (JS 디코더 필요) | 비효율 (raw/tight) | ❌ 지연·화질 열위 |
| RDP | 100~200ms | ❌ (게이트웨이 필수) | 좋음 | ❌ Windows 편향, 브라우저용 변환 계층 필요 |
| WebSocket + JPEG diff | 150~400ms | ✅ | 나쁨 (키프레임 남발) | △ **폴백으로만** |
| HLS / DASH | 2~10s | ✅ | 좋음 | ❌ 인터랙티브 불가 |

**WebRTC 채택 근거**
1. 브라우저에 디코더·지터버퍼·혼잡제어가 이미 들어 있다. 직접 구현할 것이 없다.
2. 네트워크 악화 시 **자동으로 비트레이트를 낮춘다.** JPEG 방식은 직접 만들어야 하고 대개 잘 못 만든다.
3. DataChannel로 입력을 같은 연결에 실을 수 있어 **화면과 입력의 RTT가 동일**하다.
4. 녹화(§7.5 V-08)를 **재인코딩 없이** 같은 스트림에서 mux 할 수 있다. 마스킹은 인코딩 이전 단계라 이 성질을 깨지 않는다 (§10.2).

**폴백:** UDP가 막힌 기업망을 위해 ① TURN over TCP/443 → ② 그래도 실패 시 WebSocket JPEG diff (5~10fps, 조작은 가능하나 부드럽지 않음). 폴백 진입 시 뷰어에 배지를 띄워 사용자가 "느린 이유"를 알게 한다.

#### 파이프라인

```text
        ┌──────────────── Guest (iapetusd) ────────────────┐
        │                                                  │
        │   X11 XDamage / DXGI Duplication                 │
        │        (변경 영역만 이벤트로 통지)                 │
        │                    │                             │
        │                    ▼                             │
        │            Frame Source  ◄── 단일 캡처 소스        │
        │           (RGBA ring buffer)                     │
        │              │            │                      │
        │   ┌──────────┘            └──────────┐           │
        │   ▼                                  ▼           │
        │ Still Encoder                  Video Encoder     │
        │ (JPEG/PNG, 온디맨드)          (H.264, 뷰어 있을 때만) │
        │   │                                  │           │
        └───┼──────────────────────────────────┼───────────┘
            │ HTTPS (Control Plane 경유)        │ SRTP → Stream Gateway (SFU)
            ▼                                  ▼
      Agent (스크린샷)                    사람 브라우저 (라이브)
                                              ▲
                                    DataChannel │ 입력 (마우스/키보드)
```

**핵심 설계 결정 3가지**

1. **단일 캡처 소스, 이중 인코더.** 캡처는 비싸고(1080p RGBA = 8MB/프레임 복사), 두 번 하면 낭비다. 링 버퍼 하나를 두 인코더가 읽는다.

   **단, 캐시된 프레임을 그냥 반환하면 안 된다.** 캡처는 XDamage 이벤트 기반이라 5~15ms 지연이 있고, Agent가 `click` 직후 `screenshot` 을 부르면 **클릭 이전 화면이 돌아올 수 있다.** 이는 Agent가 잘못된 세계 상태로 다음 판단을 내리게 만드는 정합성 오류다.

   **신선도 계약:** `screenshot` 은 **직전 액션의 완료 시각 이후에 캡처된 프레임**만 반환한다. 링 버퍼의 최신 프레임이 그보다 오래됐으면 새 캡처를 강제하고 기다린다. 응답의 `taken_at` 이 이를 증명한다.

**입력이 없는 상태 변화는 이 계약으로 막을 수 없다.** 페이지 로딩 완료, `shell.exec` 가 띄운 대화상자, `app.launch` 후의 창 렌더링은 앵커가 될 액션이 없다. 이 경우 신선도 보장은 "호출 시각 이후"까지만이며, **Agent는 `wait_for(screen_stable)` 로 명시적으로 안정화를 기다려야 한다.** 플랫폼이 자동으로 판단하지 않는다 — 무엇을 기다려야 하는지는 Agent만 안다.

2. **뷰어 0명이면 비디오 인코더 정지.** Desktop 10,000개 중 사람이 보고 있는 것은 보통 수십 개다. 뷰어가 없으면 H.264 인코더를 완전히 내리고, 캡처도 XDamage 이벤트 기반으로만 돌린다(변화 없으면 CPU 0에 수렴). **이것이 없으면 스트리밍 비용이 컴퓨트 비용을 초과한다.**

3. **1회 인코딩, N회 전송.** 관찰자가 여러 명이어도 인코딩은 한 번이다. `iapetusd` 는 인코딩된 RTP 패킷을 스트림 게이트웨이(`iapetus-stream`)로 한 번만 보내고, 게이트웨이가 SFU로서 각 뷰어에게 복제한다. 게스트 CPU는 관찰자 수와 무관하다.

**게스트는 브라우저의 WebRTC 피어가 아니다.** 게스트는 게이트웨이에게만 송신하고, 브라우저는 게이트웨이와만 피어링한다. P2P 직결은 채택하지 않는다 — ① 게스트 IP가 노출되고 ② 관찰자마다 별도 인코딩이 필요해져 위 3번이 무너지기 때문이다. 아래 「NAT 통과」의 STUN/TURN 사다리는 **브라우저 ↔ 게이트웨이 구간에만** 적용된다. 게스트 ↔ 게이트웨이는 같은 호스트/랙 내부 경로라 ICE가 필요 없다.

#### 다중 관찰자와 비트레이트 적응의 충돌

단일 인코딩 스트림에 GCC 혼잡제어를 그대로 걸면 **가장 느린 뷰어가 전체 품질을 끌어내린다.** 해상도를 낮추는 방식(simulcast/공간 SVC)은 인코딩을 계층 수만큼 반복해야 하므로 §12.4 용량 모델을 파괴한다.

**결정: 시간 계층(temporal layering)만 사용한다.**

**이 결정이 인코더를 강제한다.** x264에는 시간 계층 API가 없어 채택할 수 없고 **OpenH264**(`iTemporalLayerNum`) 또는 NVENC를 써야 한다. OpenH264는 x264 `veryfast` 보다 느려 **인코딩 비용이 1.2~1.8 vCPU로 오른다.** 계층 구조 자체는 거의 공짜지만 인코더를 바꾼 대가는 실재하며, §12.4의 예약 CPU와 동시 관찰 한도는 이 값으로 산출되어 있다.

```text
게스트 인코딩: 계층적 P 프레임 구조 1회 (계층 자체의 추가 비용 ≈ 0)
   L0: 7.5fps  (기준 계층)
   L1: +7.5fps → 15fps
   L2: +15fps  → 30fps

게이트웨이가 뷰어별로 상위 계층을 버린다:
   빠른 뷰어  → L0+L1+L2 = 30fps
   느린 뷰어  → L0만      = 7.5fps  (해상도·선명도 유지)
```

계층 ID는 게스트 → 게이트웨이 구간의 자체 프로토콜 헤더로 전달한다(이 구간은 표준 WebRTC가 아니라 자유롭다). 게이트웨이는 헤더만 보고 패킷을 버리며 **디코딩하지 않는다.**

| | 시간 계층 (채택) | Simulcast/공간 SVC (기각) | 게이트웨이 트랜스코딩 (기각) |
|---|---|---|---|
| 인코딩 비용 | 1× (단 OpenH264 전환으로 기준선이 1.5배) | 2~3× | 뷰어 수 × |
| 느린 뷰어가 받는 것 | 낮은 프레임레이트, **원본 해상도** | 낮은 해상도 | 임의 조절 |
| 텍스트 판독 | ✅ 유지 | ❌ 깨짐 | △ |

**해상도를 희생하지 않는 것이 핵심이다.** 이 절 서두에서 정한 대로 사람은 화면의 글자를 읽어야 하며, 데스크톱 화면은 대부분 정지 상태이므로 프레임레이트 저하는 실사용에서 거의 체감되지 않는다.

#### 코덱 및 비트레이트

| 항목 | 기본값 | 근거 |
|---|---|---|
| 코덱 | H.264 **High Profile** (4:2:0) | Baseline은 CABAC·8×8 변환이 없어 화면 콘텐츠에 특히 불리하다. High는 동일 비트레이트에서 텍스트가 눈에 띄게 선명하고 모든 대상 브라우저가 디코딩한다 |
| 해상도 | 1920×1080 (Desktop 원본과 동일) | 스케일링하면 텍스트가 뭉개져 사람이 읽지 못함 |
| 프레임레이트 | 30fps 상한, **변화 없으면 0fps** | 데스크톱 화면은 대부분 정지 상태 |
| 비트레이트 | 1.5Mbps 기본, 0.5~8Mbps 적응 | GCC 혼잡제어가 자동 조절 |
| 키프레임 | 2초 주기 + 뷰어 참여 시 즉시 | 신규 접속자 대기 시간 제거 |
| 인코더 | **OpenH264** (`iTemporalLayerNum=3`), 지연 우선 설정 | **x264는 시간 계층을 낼 수 없다** — SVC/참조리스트 제어 API가 없다. 아래 「다중 관찰자」 결정이 인코더 선택을 강제한다 |
| GPU 티어 인코더 | NVENC (계층 지원) | 동일 계층 구조를 하드웨어로 |

**텍스트 선명도 — 4:2:0의 한계를 인정하고 우회한다.**

H.264 4:2:0은 색차 해상도를 1/4로 줄이므로 **색이 있는 글자(구문 강조된 코드, 링크, 경고 텍스트)의 가장자리가 번진다.** QP를 낮춰도 해결되지 않는 별개의 손실이다. 4:4:4 프로파일은 브라우저 디코딩 지원이 고르지 않아 채택하지 않는다.

**대응: 움직일 때와 멈췄을 때를 다르게 다룬다.**

| 상태 | 처리 |
|---|---|
| 화면이 움직이는 중 | H.264 High 4:2:0. OpenH264 `iUsageType=SCREEN_CONTENT_REAL_TIME`, `iRCMode=RC_BITRATE_MODE`, `iMaxQp=32`, `uiIntraPeriod=60`. 부드러움 우선 |
| **500ms 이상 정지** | **변경된 영역만** 고품질 WebP(q=95)로 한 장 더 보내 덮어쓴다 (still overlay). 아래 예산 참조 |

**오버레이 예산 — "부담이 없다"고 뭉뚱그리지 않는다.**

1080p 전체를 무손실 PNG로 보내면 1~3MB이고, 기본 비트레이트 1.5Mbps에서는 5~16초가 걸린다. 그대로는 쓸 수 없다.

| 규칙 | 값 |
|---|---|
| 대상 | **직전 키프레임 이후 변경된 영역의 바운딩 박스만** (전체 화면 아님) |
| 형식 | WebP q=95 (무손실 아님. 텍스트 가장자리 보존에는 충분) |
| 크기 상한 | **200KB.** 초과하면 전송하지 않고 다음 정지 이벤트를 기다린다 |
| 전송 경로 | 비디오 트랙이 아닌 **DataChannel**(입력과 별도 SCTP 스트림). 브라우저가 `<video>` 위 canvas 레이어에 합성 |
| 최소 간격 | 2초. 정지·재개가 반복될 때 연사되지 않도록 |

**입력 지연과 대역을 경합한다.** 오버레이는 입력과 같은 DataChannel을 쓴다. 별도 SCTP 스트림이라 head-of-line 블로킹은 없지만 **혼잡 윈도를 공유**하므로, 전송 중에는 입력 왕복(20~50ms)이 일시적으로 늘 수 있다. 그래서 오버레이는 **화면이 500ms 이상 멈춘 뒤에만** 보낸다 — 사람이 조작을 멈춘 구간이므로 입력 지연 증가가 체감되지 않는다. 조작 중에는 절대 전송하지 않는다.

200KB는 1.5Mbps에서 약 1초, 0.5Mbps 하한에서도 3초다. **느린 뷰어에게는 오버레이가 늦게 도착하거나 상한에 걸려 생략될 수 있다.** 즉 모든 뷰어가 동일한 선명도로 수렴한다고 보장하지 않는다 — 빠른 뷰어는 거의 즉시, 느린 뷰어는 지연되거나 H.264 화면에 머문다.

**세 가지 최적화가 서로 맞물리는 방식** — 화면 상태에 따라 다른 것이 작동한다.

| 화면 상태 | 프레임레이트 | 시간 계층 | 정지 오버레이 (WebP q=95) |
|---|---|---|---|
| 움직이는 중 | 최대 30fps | 활성 (느린 뷰어는 L0 7.5fps) | 미전송 |
| 멈춘 직후 (< 500ms) | 0fps (신규 프레임 없음) | 무의미 | 미전송 |
| **멈춘 채 유지 (≥ 500ms)** | 0fps | 무의미 | **1회 전송.** 200KB 예산·회선에 따라 수신 여부가 뷰어마다 다름 |

정지 상태에서는 시간 계층이 의미를 잃는다. 대역폭이 충분한 뷰어는 오버레이를 받아 선명한 화면을 보고, 200KB 예산이나 회선 한계에 걸린 뷰어는 H.264 화면에 머문다. **완전히 수렴하지는 않지만, 프레임레이트 차등은 움직이는 동안에만 존재하고 정지 시점에는 대역폭이 허락하는 만큼 격차가 줄어든다.**

사용자가 글자를 읽는 순간은 언제나 화면이 멈춰 있을 때다. 그 순간에만 고품질을 지불하면 텍스트 판독 요구와 인코딩 비용을 동시에 만족시킨다.

> 파라미터는 OpenH264 API 기준으로 적는다. x264의 `tune=zerolatency` / `qpmax` 는 이 인코더에 존재하지 않는다 — 인코더를 바꾼 이상 설정 이름도 함께 바뀐다.

#### 지연 예산 (동일 리전, 유선 기준)

| 구간 | 목표 | 비고 |
|---|---|---|
| 화면 변화 → 캡처 완료 | 5~15ms | XDamage 이벤트 기반 |
| 캡처 → H.264 인코딩 (OpenH264 SW) | **12~30ms** | x264 대비 ~1.5배. 처리량뿐 아니라 프레임당 지연도 함께 오른다 |
| 게스트 → 스트림 게이트웨이 | 2~5ms | 동일 호스트/랙 |
| 게이트웨이 → 브라우저 (RTT/2) | 10~40ms | 리전 내 |
| 브라우저 지터버퍼 + 디코딩 | 20~60ms | 브라우저 제어 |
| 프레임레이트 양자화 (L2, 30fps) | 0~33ms | 전 계층을 받는 뷰어 |
| 디스플레이 갱신 (vsync) | 8~16ms | 브라우저·모니터 |
| **합계 (glass-to-glass, 30fps 뷰어)** | **57~199ms** | KPI < 200ms에 **사실상 붙어 있다.** 아래 참조 |
| 프레임레이트 양자화 (L0, 7.5fps) | 0~133ms | 계층이 강등된 느린 뷰어 |
| **합계 (L0로 강등된 뷰어)** | **57~299ms** | 하한은 프레임이 마침 준비된 순간이라 동일하다. **상한이 KPI를 크게 초과한다.** 아래 참조 |

**소프트웨어 인코딩으로는 KPI에 여유가 없다.** 상한 199ms는 200ms 목표를 1ms 남기고 통과하는 값이며, 이는 목표를 지킨다기보다 **못 지킬 조건이 하나만 더 겹쳐도 무너진다**는 뜻이다. 시간 계층을 얻기 위해 x264를 포기한 대가가 여기서 드러난다.

**따라서 GPU 티어는 관찰 밀도만의 문제가 아니다.** NVENC는 프레임당 인코딩 지연이 5~10ms로 떨어져 상한이 ~179ms가 되고, 여기서 비로소 실질적인 여유가 생긴다. §12.4가 관찰 비율 20% 초과 시 GPU를 요구사항으로 규정한 것과 별개로, **지연에 민감한 용도(원격 조작 중심)는 관찰 수가 적어도 GPU 티어를 권장**한다.

**강등된 뷰어는 KPI 대상이 아니다.** L0(7.5fps)로 떨어진 뷰어는 프레임 간격만으로 133ms를 쓰므로 200ms 예산에 들어올 수 없다. 이는 설계된 트레이드오프다 — 네트워크가 나쁜 뷰어에게 **해상도를 깎아 지연을 지키는 대신, 지연을 내주고 글자를 읽을 수 있게 한다.** 따라서 §2.2의 스트리밍 지연 KPI는 **전 계층을 수신하는 뷰어**에만 적용하며, 강등 발생률(목표 < 5%)을 별도 지표로 추적한다.

역방향(입력)은 DataChannel로 **20~50ms**. 다만 사람이 체감하는 것은 **입력 → 게스트 반영 → 캡처 → 인코딩 → 표시**의 왕복이며 이는 **75~240ms**다. 100ms 이내로 느껴지게 하려면 리전 근접 배치가 필수이고, 원거리 접속에서는 체감 지연을 피할 수 없음을 인정한다.

#### CPU 비용과 수용량

GPU 없는 일반 인스턴스 기준 실측 목표치:

| 상태 | vCPU 사용 |
|---|---|
| 뷰어 0명, 화면 정지 | ~0.01 |
| 뷰어 0명, Agent가 초당 1회 스크린샷 | ~0.05 |
| 뷰어 1명 이상, 1080p30 OpenH264 소프트웨어 인코딩 (시간 계층 3단) | **1.2~1.8** |

**인코더는 게스트 안에서 돌지만, 그 비용을 테넌트 쿼터에서 빼지 않는다.** 그러면 사람이 화면을 보는 순간 Chrome이 느려지는 자해가 발생한다. 관찰이 시작되면 **호스트가 해당 Desktop에 인코딩 전용 1.8 vCPU를 추가 할당**하고(테넌트의 2 vCPU와 별개), 관찰이 끝나면 회수한다. 이 추가분은 호스트 예약분에서 나오므로 동시 관찰 수에 상한이 생긴다.

**따라서 호스트 수용량은 메모리가, 동시 관찰 수는 예약 CPU가 결정한다.** 구체 수치는 §12.4에 단일 출처로 정리한다.

GPU 티어(NVENC/QSV)는 인코딩 CPU 비용이 **Desktop당 0.05 vCPU 수준**으로 떨어진다. 단 병목이 vCPU에서 **GPU의 동시 인코딩 세션 수**로 옮겨갈 뿐이며(1080p30 기준 GPU당 수십 세션), 이 한도가 **`gpu` 등급의 호스트당 14대**(§12.4)보다 낮으면 그것이 새 상한이 된다. GPU 모델별 실측 후 확정한다. 관찰이 많은 워크로드(교육·감사·데모)는 GPU 티어를 권장한다.

#### 썸네일 프리뷰

대시보드의 Desktop 목록에서 수십 개를 동시에 보여줘야 한다. 전부 WebRTC를 붙이면 즉시 한계를 넘는다.

| 용도 | 방식 | 비용 |
|---|---|---|
| 목록 썸네일 | **320×180 JPEG, 10초 주기, 오브젝트 스토리지 캐시** | 게스트 CPU는 무시할 수준. **저장·PUT 비용은 아님** — 10,000 Desktop이면 분당 6만 PUT |
| 카드 호버 프리뷰 | 1fps JPEG 폴링 | 낮음 |
| 상세 보기 | WebRTC 풀 스트림 | 높음 |

**썸네일 생성은 목록 화면을 실제로 보고 있는 동안만 동작한다.** 아무도 대시보드를 열지 않았는데 전 Desktop의 썸네일을 계속 굽는 것은 낭비다. 썸네일도 스크린샷이므로 §10.2 보존 정책을 따른다(기본 24시간).

썸네일은 스틸 인코더가 저해상도로 뽑아 S3에 올리고 CDN이 서빙한다. **비디오 인코더를 깨우지 않는다.** SUSPENDED Desktop은 절전 직전 마지막 썸네일을 그대로 보여준다 — 사용자가 "무엇이 떠 있던 컴퓨터인지" 알아보게 하는 것이 목적이므로 실시간일 필요가 없다.

| v3 | 양방향 (마이크 → Desktop). 화상회의 자동화 시나리오 |

v1에서 오디오를 빼는 이유는 립싱크 동기화가 지연 예산을 압박하고, 초기 시나리오(검색·메시지·업무앱)에 소리가 필요 없기 때문이다.

#### NAT 통과

```text
1순위  ICE host/srflx (STUN)     → 직접 UDP.  가장 낮은 지연
2순위  TURN over UDP:3478        → 릴레이. +10~20ms
3순위  TURN over TCP/TLS:443     → 기업 방화벽 통과용. +30~60ms
4순위  WebSocket JPEG diff       → WebRTC 완전 차단 환경
```

TURN 자격증명은 **Viewer Token 발급 시 함께 내려주는 단기 크리덴셜**(HMAC 기반, 15분)이다. 고정 TURN 계정을 두지 않는다 — 유출 시 무제한 릴레이 남용이 발생하기 때문이다.

### 6.4 런타임 선택

| 백엔드 | 용도 | 커널 격리 | 메모리 스냅샷 | 파일 공유 |
|---|---|---|---|---|
| Docker 컨테이너 (XFCE + Xvfb) | 로컬 개발, 셀프호스트, 단일 조직 | ❌ 공유 커널 | ❌ | bind mount |
| Kata Containers | (검토했으나 미채택) | ✅ | ❌ **없음** | virtio-fs (qemu) |
| **Firecracker microVM** | **멀티테넌트 SaaS (채택)** | ✅ | ✅ | ❌ 블록 디바이스만 |
| Windows VM | 데스크톱 앱(메신저, Excel, ERP) | ✅ | ✅ | — |

**Kata를 쓰지 않는 이유:** Kata는 OCI 이미지를 그대로 쓰면서 커널 격리를 얻는 매력적인 경로지만, **실행 중 VM 스냅샷 API가 없다.** VM templating은 부팅 가속 기능이지 체크포인트가 아니다. 프로세스 보존 suspend/resume(§7.4)이 제품의 핵심 주장이므로, 스냅샷을 지원하는 **Firecracker를 직접 오케스트레이션**한다.

**Firecracker의 대가:** virtio-fs 디바이스가 없어 호스트→게스트 파일 단위 공유가 불가능하다. 따라서 **영속 볼륨과 `iapetusd` 주입(§19.4) 모두 블록 디바이스로 붙인다** — 데몬은 읽기 전용 squashfs 이미지, 홈은 ext4 볼륨이다. Kata/qemu 경로였다면 쓸 수 있었던 파일 단위 마운트는 포기한다.

이미지는 **OCI 하나로 유지**하고, Firecracker 경로에서는 부팅 시 rootfs로 변환해 사용한다. Dockerfile은 한 벌만 관리한다.

#### 검토했으나 채택하지 않은 것 — 멀티세션 (OS 1개, 데스크톱 화면 N개)

하나의 OS에 X 디스플레이를 여러 개 띄우고 테넌트별로 화면만 나누는 구조(Windows RDS, Linux 멀티시트)를 검토했다. 커널·바이너리·페이지 캐시를 공유하므로 **세션당 실효 메모리가 4GB → 약 1.1GB로 줄어든다.** 밀도만 보면 매력적이다.

**서로 다른 고객 사이에는 채택하지 않는다.** 우리는 Agent와 사람 모두에게 게스트 root를 준다(§7.3). root는 Unix 권한을 설계상 우회하므로, 디렉토리나 OS 계정으로 나누는 것은 **정리이지 격리가 아니다.**

| 격리 수준 | 막는 것 | 우리에게 |
|---|---|---|
| 디렉토리 + Unix 권한(DAC) | 비-root의 실수 | root를 주면 무의미 |
| **MAC (SELinux MCS / AppArmor)** | **root의 고의도 일부 막음** | **§7.3이 이걸 해체할 권한을 준다 — 아래 참조** |
| user namespace / 컨테이너 | 비-root의 고의 | 공유 커널 → root가 커널 취약점으로 탈출 |
| **microVM** | **root의 고의** | ✅ 채택 |

**MAC은 허수아비가 아니다.** SELinux MCS는 정확히 이런 OS 내 멀티테넌트 분리를 위해 존재하고(OpenShift가 쓴다), **root가 DAC을 우회한다는 사실 자체가 MAC이 만들어진 이유**다. 따라서 "root니까 디렉토리가 무의미하다"는 논거로는 MAC을 기각할 수 없다.

**기각 근거는 §7.3이다.** 우리는 커널 모듈·드라이버·`system.service`·`sudo`/UAC 상승을 **보장한다고 약속했다.** 이는 `CAP_MAC_ADMIN`·`CAP_SYS_ADMIN`을 주는 것과 같고, 그 권한을 가진 주체는 자기에게 걸린 MAC 정책을 해제할 수 있다. **반대로 그 권한을 회수하면 §7.3이 약속한 "이 앱은 못 열어요가 없다"가 성립하지 않는다.** OWNER 모드와 MAC은 양립 불가이며, 이것이 microVM까지 올라가는 진짜 이유다.

§9.1이 컨테이너조차 멀티테넌트에서 금지한 것과 같은 근거다. 컨테이너보다 약한 분리가 성립할 수 없다.

**밀도 이득도 우리 워크로드에서는 역전된다.** 멀티세션은 세션 하나만 메모리 스냅샷할 방법이 없어 **suspend를 할 수 없다.** 세션은 상주하거나 죽어서 상태를 잃거나 둘 중 하나다. 반면 VM 모델은 유휴 Desktop이 `SUSPENDED` 로 내려가 RAM 점유가 0이 된다.

보유 10,000대 기준 필요 RAM:

| 활성 비율 | VM-per-Desktop | 멀티세션 | |
|---|---|---|---|
| 1% | **0.4TB** | 10.7TB | VM 27배 우세 |
| 5% | **2.0TB** | 10.7TB | VM 5.5배 우세 |
| **28%** | 10.9TB | 10.7TB | 손익분기 |
| 100% | 39.1TB | **10.7TB** | 멀티세션 3.6배 우세 |

**이 비교는 멀티세션에 유리하게 편향되어 있다.** VM 쪽은 오버커밋 금지 규칙(§12.4) 때문에 **예약량 4GB**로 계산되는 반면, 멀티세션 쪽은 **평균 실사용 1.1GB**로 계산된다. 통계적 다중화의 이득을 한쪽에만 준 것이다. 스왑 없는 호스트에서 세션의 피크(DE 300~400MB + Chrome 800MB~1.5GB)를 안전하게 담으려면 세션당 1.8~2.2GB가 필요하므로, **공정하게 잡으면 손익분기는 45~55%로 올라간다.** 아래 수치는 보수적으로 잡은 것이며 결론은 더 강해진다.

**손익분기는 (보수적으로 잡아도) 활성 비율 28%다.** S3 정기 루틴(하루 몇 분)은 활성 비율이 한 자릿수 퍼센트이므로 VM 모델이 5~27배 유리하다. 멀티세션이 이기는 조건은 "거의 항상 켜져 있는 Desktop"인데, 그것은 VDI의 영역이고 §4.3에서 우리가 진다고 인정한 시장이다.

**RAM만 비교한 표라는 점도 밝혀둔다.** VM 모델은 `SUSPENDED` 마다 메모리 스냅샷을 로컬 NVMe에 남기므로 1만 대면 약 40TB이고 호스트 어피니티가 붙는다(§7.4). 활성 1%에서는 **RAM 0.4TB를 디스크 40TB와 맞바꾸는 셈**이며, GB당 단가 차이(5~10배)를 감안해도 여전히 크게 유리하다. 스냅샷을 포기하고 볼륨만 보존하면 이 비용도 사라지지만 프로세스 보존을 잃는다.

**결론: `auto_suspend` 를 기본 on으로 둔 설계(§13)가 이 효율의 근원이다.** 유휴 비용을 0으로 만드는 대가로 대당 메모리를 더 쓰는 교환이며, 우리 워크로드에서는 이 교환이 크게 남는다.

#### 유보 — Desktop Group (v2 검토)

위 분석은 **서로 다른 신뢰 도메인** 사이의 이야기다. **같은 고객의 Desktop끼리는 격리할 이유가 없으므로** 결론이 달라진다.

특히 §5.6이 "동시성이 필요하면 Desktop을 나눠라"라고 안내하는데, **그렇게 나뉜 Desktop들은 정의상 함께 활성**이다. 함께 켜지고 함께 꺼지므로 개별 suspend의 이득이 사라지고, 공유의 이득만 남는다.

| 병렬 Agent 3개 | 메모리 |
|---|---|
| Desktop 3개 각각 VM | 12GB |
| **1 OS + 화면 3개** | **5.3GB** (2GB OS + 3 × 1.1GB) |

**2.3배.** 실재하는 이득이다.

**설계 방향 — API 모델은 바꾸지 않는다.**

```text
Desktop Group = 배치 지시(placement directive)이지 새로운 조작 단위가 아니다.

  DesktopGroup grp_01H8
    ├── Desktop dsk_A  → 게스트 OS의 :1 디스플레이
    ├── Desktop dsk_B  → :2
    └── Desktop dsk_C  → :3
```

- **Desktop은 그대로 API의 단위다.** 좌표·제어권·감사·뷰어가 전부 Desktop 하나에 대응하므로 §7.2 좌표계, §5.6 제어권, §9.4 감사의 **구조(shape)가 바뀌지 않는다.** 디스플레이 축을 API에 추가하면 이 셋이 전부 2차원이 되어 비용이 급증한다.
- **다만 구조가 아니라 의미(semantics)는 좁아진다.** 그룹 안에서는 OS가 하나이므로 **시스템 범위 액션이 그룹 전체에 미친다.** 이는 "격리가 없다"와는 다른, API에 드러나는 변화다.

| 액션 | 그룹 안에서의 의미 |
|---|---|
| `system.reboot` | `dsk_A` 에 호출해도 **B·C가 함께 재부팅**된다 |
| `system.service` / `system.env` | OS 전역이므로 그룹 전체에 반영 |
| `process.list` / `process.kill` | **다른 Desktop의 프로세스가 보이고 종료할 수 있다** |
| `app.list` | 그룹 내 모든 Desktop의 설치·실행 앱이 섞여 보인다 |
| `spec_tier` | Desktop별 필드지만 OS가 하나이므로 **그룹 내 동일해야 한다** |
| `privilege_mode: restricted` | 게스트 안에서 강제되므로 **디스플레이별로 다를 수 없다** |

v2에서 Group을 실제로 만들 때 **이 목록이 비용의 실체**다. "배치 지시일 뿐"이라는 말이 시스템 범위 액션까지 덮지는 않는다.
- 바뀌는 것은 런타임뿐이다. `iapetusd` 가 게스트 안에서 X 디스플레이 N개를 supervise하고 각각을 Desktop ID에 매핑한다.
- 그룹 내 Desktop은 **같은 프로젝트·같은 Owner 집합**이어야 한다. 신뢰 도메인이 같다는 것이 전제 조건이다.

**감수하는 것 — 이것이 v2인 이유.**

| 항목 | 결과 |
|---|---|
| suspend 단위 | **그룹 전체.** 하나가 활성이면 전원이 상주한다 |
| 격리 | 그룹 내에는 **없다.** 파일·클립보드·프로세스가 전부 공유된다 |
| 장애 전파 | 한 Desktop이 커널을 망가뜨리면 그룹 전체가 죽는다 |
| `iapetusd` 복잡도 | 멀티 디스플레이 supervise, 디스플레이별 캡처·인코더·입력 |
| §7.2 단일 모니터 고정 | 그룹 자체는 이 규약을 깨지 않는다(Desktop당 여전히 1화면) |

**v1에 넣지 않는 이유는 검증 순서다.** 병렬 실행 수요가 실제로 관측되기 전에 런타임을 복잡하게 만들면, 아직 존재를 모르는 사용 패턴을 위해 핵심 경로를 흔드는 것이 된다. H-3(사람 개입 활용도)처럼 **"그룹 수요"를 Phase 2에서 관측한 뒤 결정한다.**

### 7.2 Computer API (핵심)

Agent가 사용하는 통합 조작 인터페이스.

#### 셸 / 시스템

Agent는 관리자 셸을 **기본으로 사용할 수 있다**.

| 액션 | 파라미터 | 설명 |
|---|---|---|
| `shell.exec` | `command`, `cwd?`, `env?`, `elevated?`, `timeout_ms` | 동기 실행, stdout/stderr/exit_code 반환 |
| `shell.spawn` | `command`, `detach?` | 장기 실행 프로세스. `pid` 반환 |
| `shell.stream` | `pid` | 실행 중 출력 스트리밍 |
| `system.env` | `set`/`get` | 환경변수 |
| `system.service` | `name`, `action`(start/stop/enable) | 서비스 제어 |
| `system.reboot` | — | 게스트 재부팅 (볼륨 유지) |

#### 복합 액션 (편의)

| 액션 | 설명 |
|---|---|
| `act` | 액션 배열을 순차 실행 후 최종 screenshot 반환 (왕복 감소) |
| `wait_for` | 화면 변화 / 창 등장 / 지정 시간 대기 |

**`act` 는 원자적이지 않다.** GUI 조작은 롤백이 불가능하다 — 3번째 액션이 실패해도 앞의 2개는 이미 화면에 반영됐다. 따라서 다음 semantics로 정의한다.

- **fail-fast**: 실패한 액션에서 즉시 중단. 나머지는 실행하지 않는다.
- **부분 결과 반환**: 성공한 액션까지의 결과 배열 + `failed_at` 인덱스.
- **실패 시점 screenshot 필수 반환**: Agent가 "화면이 어디까지 진행됐는지" 판단할 유일한 근거.
- 재시도는 Agent 책임. 플랫폼은 자동 재시도하지 않는다.

```json
{
  "results": [
    { "type": "app.launch", "ok": true },
    { "type": "mouse.click", "ok": false, "error": "ACTION_TIMEOUT" }
  ],
  "failed_at": 1,
  "screenshot": { "url": "..." }
}
```

**`act` 예시**
```json
{
  "actions": [
    { "type": "app.launch", "key": "chrome", "wait_for_window": true },
    { "type": "mouse.click", "x": 640, "y": 120 },
    { "type": "type", "text": "코쏘" },
    { "type": "key", "keys": "Enter" },
    { "type": "wait_for", "mode": "screen_stable", "timeout_ms": 5000 }
  ],
  "return_screenshot": true
}
```

### 7.3 권한 모델 — 사람과 Agent 모두 Desktop의 소유자

**원칙: Desktop 안에서 누구도 제약하지 않는다.**

사람 Owner와 Agent Owner 모두 `OWNER` 권한을 가진다. 아래 표의 모든 항목이 **양쪽 다** 해당한다:

| 권한 | 보장 |
|---|---|
| 임의 프로그램 실행 | `app.launch(command=...)`, `shell.exec` 로 경로 제한 없이 실행 |
| 프로그램 설치/삭제 | `app.install` (apt / winget / msi / 직접 다운로드) |
| 파일시스템 전체 | 시스템 디렉토리 포함 읽기·쓰기·삭제 |
| 관리자 권한 | `sudo` / UAC 상승. NOPASSWD 구성이라 비밀번호 프롬프트 자체가 없음 |
| 시스템 설정 | 네트워크, 시간대, 레지스트리, 서비스, 드라이버 |
| 프로세스 제어 | 임의 프로세스 조회·종료 |
| 브라우저 프로필 | 확장 설치, 인증서 추가 |
| 게스트 재부팅 | `system.reboot` |

**왜 이렇게 하는가:** 앱 단위 화이트리스트는 실제 업무 자동화에서 반드시 깨진다. 사내 ERP 실행 파일이 업데이트로 경로가 바뀌고, 엑셀 매크로가 별도 런타임을 부르고, 설치 마법사가 임시 실행 파일을 만든다. 이런 것을 매번 화이트리스트에 등록하게 만들면 제품이 못 쓰게 된다. 대신 **Desktop 자체를 일회성 신뢰 경계로 취급**하고, 안이 아니라 밖에서 통제한다 (§9.1).

**App 카탈로그의 역할 변경:** 카탈로그는 이제 **차단 장치가 아니라 발견(discovery) 도구**다. Agent가 `app.list`로 "이 컴퓨터에 뭐가 설치돼 있고 어떻게 여는가"를 알아내는 용도. 카탈로그에 없어도 실행할 수 있다.

#### 서드파티 앱에 대한 원칙

데스크톱 앱 자동화는 약관 리스크를 동반한다. 다음 세 가지 원칙으로 노출을 최소화한다.

| 원칙 | 내용 | 이유 |
|---|---|---|
| **1. 우리는 앱을 배포하지 않는다** | 서드파티 앱을 기본 이미지에 사전 설치하지 않는다. 사용자가 직접 설치하거나(S5), 고객 조직이 자기 이미지에 담는다 | 배포·재배포 관련 조항에 저촉될 여지를 없앤다. 설치 주체는 언제나 고객이다 |
| **2. 사용자 자기 계정만** | 자동화 대상은 **그 Desktop 소유자 본인의 계정**이다. 타인 계정 조작, 대량 계정 운영, 계정 판매·대여 목적 사용을 약관으로 금지한다 | 대부분의 서비스 약관이 문제 삼는 것은 자동화 자체가 아니라 **계정 오용과 대량 행위**다 |
| **3. 특정 앱에 의존하지 않는다** | 앱은 카탈로그의 한 항목일 뿐이며, 어떤 앱이 차단되어도 플랫폼은 계속 동작한다 | R-01 완화. 제품 서사를 특정 앱 이름에 묶지 않는다 |

**이 문서에서 특정 상용 앱을 예시로 들지 않는 것도 같은 이유다.** 기능은 "데스크톱 앱 자동화"이지 "특정 앱 자동화"가 아니다.

**기본 카탈로그 (사전 설치)**

| key | Linux | Windows |
|---|---|---|
| `chrome` | ✅ | ✅ |
| `terminal` | ✅ | ✅ (PowerShell) |
| `files` | ✅ | ✅ (Explorer) |
| `text_editor` | ✅ | ✅ |
| `vscode` | ✅ | ✅ |
| *(사내 메신저)* | 조직 이미지 | 조직 이미지 |
| `excel` | ❌ | ✅ (라이선스 필요) |
| `custom_erp` | 조직 이미지 | 조직 이미지 |

**선택적 제한 (기본 OFF):** 규제 산업 고객을 위해 프로젝트 정책으로 `restricted` 모드를 켤 수 있다. 이 모드에서만 화이트리스트가 강제되고 `APP_NOT_ALLOWED` / `POLICY_BLOCKED` 에러가 발생한다. 기본값은 `owner` 모드이며 아무것도 막지 않는다.

```jsonc
// 기본값 — Agent·사람 모두 완전 권한
{ "privilege_mode": "owner" }

// 옵트인 — 규제 산업용
{
  "privilege_mode": "restricted",
  "allowed_apps": ["chrome"],
  "shell_exec": false
}
```

### 7.4 영속성

| 대상 | 보존 방식 |
|---|---|
| 홈 디렉토리 / 사용자 프로필 | 영속 볼륨 |
| 브라우저 쿠키·세션·확장 | 영속 볼륨 (Chrome 프로필) |
| 앱 로그인 상태 (메신저 등) | 영속 볼륨 + Suspend 스냅샷 |
| 실행 중 프로세스·창 배치 | Suspend 메모리 스냅샷 |
| 다운로드 파일 | 영속 볼륨 |

**보장 수준은 실행 런타임에 따라 다르다.**

| 런타임 | `restart` | `suspend / resume` |
|---|---|---|
| **Firecracker / Cloud Hypervisor** microVM (SaaS) | 볼륨 보존 | 볼륨 + 프로세스 + 창 배치 보존 (**아래 제약 참조**) |
| Kata Containers | 볼륨 보존 | **볼륨만 보존.** Kata에는 실행 중 VM 스냅샷 API가 없다 — VM templating은 부팅 가속 기능이지 체크포인트가 아니다 |
| Docker (셀프호스트) | 볼륨 보존 | **볼륨만 보존.** CRIU 의존이 불안정해 v1 미지원 |
| Windows VM | 볼륨 보존 | 볼륨 + 프로세스 보존 |

**격리와 스냅샷은 다른 기능이며, 런타임 선택은 이 둘의 교집합으로 결정된다.** Kata는 격리에 강하지만 스냅샷이 없다. 따라서 프로세스 보존이 필요한 SaaS 경로는 **Firecracker(또는 Cloud Hypervisor)를 직접 오케스트레이션**한다 (§19.2).

**메모리 스냅샷 복원의 실제 제약 — 전부 설계에 반영해야 한다**

| 제약 | 결과 | 대응 |
|---|---|---|
| **CPU 기능셋 호환** | 스냅샷은 같은 CPU 템플릿의 호스트에서만 복원된다 | 호스트 풀을 CPU 템플릿별로 분리. Desktop에 템플릿 라벨 고정 |
| **호스트 어피니티** | 스냅샷이 로컬 NVMe에 있으면 그 호스트로만 재개 (§12.2 RB-4) | 해당 호스트에 메모리 여유가 없으면 재개 실패 → `NO_RESUME_CAPACITY` 반환 후 **스냅샷 폐기 + 다른 호스트에서 콜드 부팅** |
| **게스트 시계 정지** | 복원 시 시계가 며칠 전에 멈춰 있음 → TLS 세션·JWT 만료·쿠키 검증이 깨진다 | **복원 직후 `iapetusd` 가 강제 시각 동기화**를 수행하고, 완료 전까지 액션을 대기시킨다. 이 단계가 없으면 §2.2의 로그인 세션 보존 KPI가 성립하지 않는다 |
| **TCP 소켓 사망** | 모든 연결이 끊긴 상태로 깨어남 | 메신저·브라우저는 재연결한다. "창 배치가 그대로"는 맞지만 "연결이 그대로"는 아니다 |

**SUSPENDED가 공짜가 아니다.** 4GB Desktop 10,000개 = 약 40TB의 스냅샷 저장이며 호스트 어피니티가 걸린다. §12.4의 "SUSPENDED 무제한"은 **스토리지 요금을 내는 한**이라는 뜻이지 배치 제약이 없다는 뜻이 아니다.

셀프호스트 Docker에서 `suspend` 는 사실상 `stop` 이며, resume 시 앱이 재시작된다. **로그인 상태는 볼륨에 있으므로 어느 경우든 유지된다** — 이것이 제품의 핵심 가치이고, 프로세스 보존은 부가 최적화다.

**Agent 계약:** 재개 후에는 반드시 `app.list` 로 실제 실행 상태를 확인한다. "suspend 전에 Chrome이 떠 있었으니 지금도 떠 있다"고 가정하면 안 된다.

### 7.5 사람 접속 — 풀 액세스 뷰어

사람은 **관찰자가 아니라 동등한 Owner**다. 뷰어는 "Agent 감시 화면"이 아니라 **원격 데스크톱**이어야 한다. 기술 파이프라인은 §6.3에서 확정했고, 이 절은 사용자에게 보이는 기능을 규정한다.

**전제:** 사용자는 언제든 자기 Desktop을 **볼 수 있어야 한다.** Agent가 지금 무엇을 하고 있는지 화면으로 확인하지 못하면, 사용자는 Agent를 신뢰할 수도 교정할 수도 없다. 가시성은 부가 기능이 아니라 제품의 신뢰 기반이다.

**가시성 3단계** — 사용자가 지불하는 주의(attention)와 비용에 따라 나눈다.

| 단계 | 화면 | 비용 | 언제 |
|---|---|---|---|
| **1. 목록 썸네일** | 320×180, 10초 주기 | 거의 0 | 대시보드에서 여러 Desktop을 훑을 때 |
| **2. 라이브 관찰 (READ)** | 풀 해상도 WebRTC, 입력 불가 | 인코딩 1.8 vCPU (호스트 예약분) | Agent 작업을 지켜볼 때 |
| **3. 직접 조작 (WRITE)** | 풀 해상도 + 입력 | 위와 동일 | 개입·세팅·수정 |

2단계와 3단계의 인프라 비용은 같다. **관찰과 조작을 가르는 것은 제어권뿐이다.**

2단계와 3단계 사이 전환은 **버튼 하나, 재접속 없음.** 관찰하다 이상하면 즉시 손을 댈 수 있어야 한다 (§5.6 선점).

| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| V-01 | 라이브 화면 스트리밍 | WebRTC (폴백: WebSocket JPEG diff) | P0 |
| V-02 | **완전 입력 제어** | 마우스·키보드·스크롤·드래그. 로컬 PC와 동일 감각 | P0 |
| V-03 | 제어권 선점 / 반환 | Agent로부터 즉시 선점, 명시적 반환 | P0 |
| V-04 | 읽기 전용 모드 | 관찰만 (제어권 미보유 상태) | P0 |
| V-05 | 클립보드 동기화 | 로컬 ↔ Desktop 양방향 복붙. **기본은 수동(붙여넣기 시 전송)** — 자동 동기화는 사람의 로컬 클립보드를 Agent가 `clipboard.read` 로 읽을 수 있게 하므로 옵트인 | P0 |
| V-06 | 파일 드래그앤드롭 | 브라우저 → Desktop 업로드, 역방향 다운로드 | P1 |
| V-07 | 특수키 전달 | Ctrl+Alt+Del, Win/Cmd, F11, 한/영 전환 | P1 |
| V-08 | 세션 녹화 | 액션 로그 + 프레임 녹화 | P1 |
| V-09 | 임베드 뷰어 | 외부 제품에 iframe/SDK 삽입 (서명 URL) | P1 |
| V-10 | 다중 관찰자 | 여러 사람 동시 관찰(READ), WRITE는 1명 | P2 |
| V-11 | 목록 썸네일 | Desktop 목록에 최근 화면 미리보기 (§6.3) | P1 |
| V-12 | 폴백 전환 표시 | WebRTC 차단 시 저품질 모드 진입을 사용자에게 고지 | P1 |
| V-13 | 모바일 뷰어 | 반응형 레이아웃 + 터치→마우스 매핑 | P2 |

**뷰어 UI 필수 요소**
- 현재 제어권 보유자 표시 (`Agent 조작 중` / `내가 조작 중`)
- 원클릭 선점 버튼 + 반환 버튼
- Agent가 다음에 무엇을 하려는지 알 수 없으므로, **선점 시 Agent에게 이유 메모 전달** 필드(선택)

**입력 경로 통일:** 뷰어의 마우스·키보드 입력도 Agent와 **같은 Computer API 액션으로 변환**되어 같은 큐를 지난다. 별도 입력 경로를 만들지 않는다 — 감사 로그가 갈라지고 제어권 중재가 불가능해지기 때문이다.

**구체 경로 — 이 부분이 정해지지 않으면 뷰어를 만들 수 없다.**

```text
브라우저 ──DataChannel──► 스트림 게이트웨이 ──§19.5 제어 스트림──► 게스트
                              │                    (source: viewer + session_id)
                              └──감사 레코드──► Control Plane
```

| 결정 | 값 | 근거 |
|---|---|---|
| 입력이 Control Plane을 경유하나 | **아니오** | 경유하면 §6.3의 20~50ms 입력 예산에 왕복이 하나 더 붙어 조작감이 무너진다 |
| 그러면 감사는 누가 남기나 | **게이트웨이가 비동기로 Control Plane에 기록** | 감사는 입력 경로에 동기적으로 끼어들 필요가 없다 |
| 제어권 검증은 어디서 | 게이트웨이가 세션의 `WRITE` 보유를 확인 후 전달 | 리스 상태는 게이트웨이가 구독한다 |
| 게스트는 어떻게 구분하나 | 프레임의 `source: viewer` + `session_id` | 감사 actor 판정과 §5.6 이양 처리에 사용 |

**마우스 이동은 좌표를 합쳐 보낸다.** 사람이 드래그하면 초당 60~120 이벤트가 발생하는데 이를 그대로 액션으로 만들면 §8.2의 요청 상한을 즉시 넘긴다. 게이트웨이가 **캡처 틱(최대 30/s)에 맞춰 좌표를 합치고**, 게스트는 마지막 좌표만 반영한다. 감사 로그에는 **입력 버스트 단위로 1건**을 남긴다 — 픽셀 단위 이동 궤적은 감사 가치가 없고 로그만 폭증시킨다.

**한글 입력:** 뷰어는 브라우저 IME 조합 이벤트(`compositionend`)를 잡아 **완성된 문자열을 `type` 액션으로 전송**한다. 키 단위로 보내면 게스트 IME와 이중 조합이 발생한다.

## 8. 외부 인터페이스 명세

### 8.1 인증 및 인가

Iapetus는 **두 종류의 주체**를 인증한다. 인증 수단은 다르지만, 인증 이후의 Desktop 권한은 동등하다 (§5.2).

#### 자격증명 종류

| 종류 | 형식 | 보유자 | 유효기간 | 용도 |
|---|---|---|---|---|
| **Project Key** | `sk_iap_live_...` | 고객사 서버 | 무기한 (수동 회수) | Desktop 생성·삭제, Owner 관리, 정책 변경 |
| **Agent Token** | `at_iap_...` (JWT) | Agent 런타임 | 1시간 (갱신 가능) | 지정된 Desktop만 제어 |
| **Viewer Token** | `vt_iap_...` (JWT) | 사람 브라우저 | 15분 (자동 갱신) | 뷰어 스트림 접속 + 입력 |
| **Guest Token** | `gt_iap_...` | `iapetusd` | 부팅 시 주입, 24시간 | 게스트 → Control Plane 아웃바운드 전용 |

**Project Key는 절대 브라우저나 Agent 프로세스에 내려보내지 않는다.** 고객사 서버가 Project Key로 단기 토큰을 발급받아 전달하는 구조다.

```text
고객사 서버 ──[Project Key]──► POST /v1/tokens
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
              Agent Token                     Viewer Token
           (scope: 특정 Desktop)          (scope: 특정 Desktop, 15분)
                    │                               │
                    ▼                               ▼
              Agent 런타임                     사람 브라우저
```

#### 토큰 스코프

토큰은 **Desktop 단위로 좁혀서** 발급한다. Agent가 다른 고객의 Desktop은 물론, 같은 프로젝트의 다른 Desktop에도 닿지 못하게 한다.

```json
{
  "sub": "agent_123",
  "actor_type": "agent",
  "desktop_ids": ["dsk_01H8XK"],
  "scopes": ["desktop:control", "desktop:files", "desktop:shell"],
  "exp": 1755250000
}
```

| 스코프 | 허용 액션 |
|---|---|
| `desktop:read` | screenshot, app.list, window.list, 이벤트 구독 |
| `desktop:control` | 마우스·키보드·앱 실행·창 조작 |
| `desktop:files` | fs.* |
| `desktop:shell` | shell.*, system.*, app.install |
| `desktop:admin` | suspend/resume/restart/delete |
| `desktop:owners:manage` | 해당 Desktop의 Owner 추가·제거, 유형 전환 |
| `desktop:audit:read` | 해당 Desktop의 감사 로그 조회 |
| `project:manage` | Desktop 생성(**생성 시점의 초기 Owner 지정 포함**), 프로젝트 정책 변경 (Project Key 전용) |

**사람 actor에게는 두 스코프가 무조건 붙는다.** `actor.type: "human"` 으로 발급되는 모든 Viewer Token에는 `desktop:owners:manage` 와 `desktop:audit:read` 가 **자동으로 포함되며, 고객사가 제외할 수 없다.** 발급 요청에서 이 스코프를 빼려는 시도는 `400 CANNOT_WAIVE_HUMAN_RIGHTS` 로 거부한다.

**생성 시점은 예외다.** Desktop이 만들어질 때는 보호할 사람 Owner가 아직 없으므로, `POST /v1/desktops` 의 `owners` 파라미터로 초기 Owner를 지정하는 것은 `project:manage` 로 가능하다. 이것이 없으면 고객사 서버가 Desktop을 만들어도 Agent가 Owner가 아니어서 모든 호출이 `NOT_OWNER` 로 막히고, 사람이 뷰어를 열어 클릭해야만 Agent가 붙는다 — §8.4 SDK 예제, §14.1의 15분 TTFA, S3 무인 스케줄 루틴이 전부 성립하지 않는다.

**보호되는 것은 "제거"이지 "최초 지정"이 아니다.** 생성 이후의 Owner 추가·제거는 `desktop:owners:manage`(사람 전용)를 요구하므로, **고객사는 한 번 붙은 사람 Owner를 떼어낼 수 없다.** §9.3이 지키려는 것은 정확히 이 지점이다.

| 시점 | 필요 권한 | 근거 |
|---|---|---|
| 생성 시 초기 Owner 지정 | `project:manage` (Project Key) | 아직 보호 대상 사람 Owner가 없음 |
| **사람 Owner가 0명인 동안 추가** | `project:manage` (Project Key) | 부트스트랩. 아래 참조 |
| 사람 Owner가 1명 이상일 때 추가·제거 | `desktop:owners:manage` (사람 전용) | 사람 Owner 축출을 막는 것이 핵심 |

**Owner가 아닌 사람도 뷰어를 열 수 있다.** `NOT_OWNER` 는 Owner가 아닌 actor의 호출을 막지만, 사람 actor에게는 두 가지 예외를 둔다: ① `READ` 뷰어 접속 ② 아래 부트스트랩 조건에서의 자가 Owner 등록. 이것이 없으면 §14.1의 "사람은 나중에 추가" 경로가 성립하지 않는다.

**부트스트랩 예외가 필요한 이유:** Agent만 Owner인 Desktop에 첫 사람을 붙이려 할 때, 그 사람의 Viewer Token은 `desktop:owners:manage` 를 갖고 있어도 **아직 Owner가 아니므로 `NOT_OWNER` 로 막힌다.** 예외가 없으면 사람을 영원히 추가할 수 없다. 따라서 **사람 Owner 수가 0인 동안에만** Project Key로 사람을 추가할 수 있고, 한 명이라도 붙는 순간 그 문은 닫힌다. 이후 고객사는 사람을 **넣을 수도 뺄 수도 없다.**

이것이 §9.3의 최종 사용자 보호를 **계약이 아니라 기술로** 만드는 장치다. 이 규칙이 없으면 Agent 축출권·감사 열람권을 고객사 서버가 중개해야 하는데, 고객사는 §9.3이 지목한 위협 주체 자신이므로 보호가 성립하지 않는다. Owner 관리가 `project:manage`(Project Key 전용)에만 있으면 안 되는 이유다.

**스코프는 권한 모델(§7.3)과 다른 층이다.** OWNER 모드는 "Desktop 안에서 무엇을 할 수 있는가"(무제한)를, 스코프는 "이 토큰으로 어느 API를 부를 수 있는가"를 정한다. `desktop:shell` 없는 토큰은 셸을 못 부르지만, `desktop:control` 로 터미널 앱을 열어 타이핑하면 결국 셸을 쓸 수 있다 — **스코프는 사고 방지용이지 보안 경계가 아니다.** 이 한계를 문서에 명시한다.

#### 토큰 서명과 키 관리

`jti` 로 토큰을 회수한다고 해놓고(아래 회수 절) 정작 클레임에 `jti` 가 없으면 회수를 구현할 수 없다. 서명 체계를 여기서 확정한다.

| 항목 | 값 |
|---|---|
| 알고리즘 | **EdDSA (Ed25519)** |
| 키 배포 | `GET /.well-known/jwks.json` (인증 불요, 캐시 1시간) |
| 회전 주기 | 90일. 신·구 키를 **30일 병행**한 뒤 구 키 폐기 |
| 키 식별 | JWT 헤더의 `kid`. 검증자는 `kid` 로 JWKS에서 고른다 |
| 긴급 회전 | 즉시 신규 키 발행 + JWKS 갱신 + 구 키 즉시 폐기. 발급된 토큰이 전부 무효화되므로 §8.1 회수와 함께 사고 대응 절차로만 사용 |

**RS256이 아니라 Ed25519를 쓰는 이유:** 서명·검증이 빠르고 키가 짧으며, RSA의 패딩 선택 오류 같은 구현 함정이 없다. 모든 대상 언어의 JWT 라이브러리가 지원한다.

**전체 클레임**

```json
{
  "jti": "jti_01H8XK4M2N7P9Q3R5S6T7V8W9X",
  "iss": "https://api.iapetus.dev",
  "aud": "iapetus",
  "sub": "agent_123",
  "actor_type": "agent",
  "project_id": "prj_01H8...",
  "desktop_ids": ["dsk_01H8..."],
  "scopes": ["desktop:control", "desktop:files", "desktop:shell"],
  "iat": 1755250000,
  "exp": 1755253600,
  "orig_iat": 1755250000
}
```

| 클레임 | 역할 |
|---|---|
| `jti` | **회수의 손잡이.** `POST /v1/tokens/revoke` 가 받는 값 |
| `orig_iat` | 최초 발급 시각. self-refresh 총수명 상한(뷰어 8시간 / Agent 24시간) 판정에 쓴다. `iat` 만으로는 갱신할 때마다 초기화되어 상한이 무의미해진다 |
| `actor_type` | `human` 이면 §8.1의 필수 스코프 두 개가 자동 부여된다 |

**회수는 상태를 봐야 한다.** JWT는 자체로 무상태 검증이 가능하지만 회수는 그렇지 않다. Control Plane은 폐기된 `jti` 목록을 **5초 TTL 캐시**로 들고 있으며, 이것이 §8.1이 회수 반영을 "< 5s"로 약속한 근거다. 토큰 수명이 짧아(15분~1시간) 목록은 작게 유지된다.

**Project Key는 JWT가 아니다.** `sk_iap_live_...` 는 **256비트 엔트로피의 불투명 랜덤 문자열**(Base62 43자)이며 서버 측 해시 비교로 검증한다. 만료가 없으므로 JWKS·회전 체계와 무관하고, 폐기는 레코드 삭제로 즉시 반영된다.

**Guest Token은 JWT이되 별도 발급 경로를 쓴다.** `iapetusd` 가 §19.5 연결마다 제시하는 값이므로 형식을 명시한다.

| 항목 | 값 |
|---|---|
| 형식 | JWT, **위와 동일한 Ed25519 키·JWKS** |
| 클레임 | `jti`, `iss`, `aud: "iapetus-guest"`, `sub: {desktop_id}`, `iat`, `exp` |
| 발급 | Desktop 프로비저닝 시. 갱신은 **mTLS 클라이언트 인증서를 근거로** 자체 재발급 |
| 수명 | 24시간 |
| 스코프 | 없음 — 게스트는 Control Plane API를 호출할 권한이 없다(§9.1). 이 토큰은 **§19.5 스트림 연결에만** 쓰인다 |

**긴급 키 회전 시 게스트 토큰이 일괄 무효화된다.** 1만 대가 동시에 mTLS로 재발급을 요청하면 그 경로 자체가 병목이 되고, 실패하면 §8.1대로 전부 `DEGRADED` 로 떨어진다. 따라서 긴급 회전은 **Desktop을 해시 버킷으로 나눠 15분에 걸쳐 순차 적용**하며, 이 지연을 감수한다 — 게스트 토큰은 스트림 연결에만 쓰이므로 사고 시 즉시 차단이 필요한 대상은 Agent·Viewer 토큰이다.

#### 사람 actor 인증

Viewer Token 자체는 사람을 식별하지 못한다. 고객사가 자기 사용자를 인증한 뒤 그 결과를 담아 발급받는다.

```http
POST /v1/tokens
Authorization: Bearer sk_iap_live_...

{
  "type": "viewer",
  "desktop_id": "dsk_01H8XK",
  "actor": { "type": "human", "id": "usr_kim", "display_name": "김철수" },
  "ttl_sec": 900,
  "control": "write"
}
```

`control` 필드는 **이 토큰이 요청할 수 있는 최대 권한**이며, 제어권을 자동으로 획득하지 않는다. 뷰어는 접속 시 항상 `READ` 로 시작하고, 사용자가 버튼을 눌러 `POST /v1/sessions/{sid}/control/acquire` 를 호출해야 `WRITE` 가 된다.

**뷰어를 여는 것만으로 Agent를 선점해서는 안 된다.** 사용자는 대개 "무슨 일이 일어나는지 보려고" 창을 연다. 그 행위가 진행 중인 Agent 작업을 중단시키면 관찰 자체가 위험한 행동이 되고, §7.5의 가시성 3단계가 무의미해진다.

응답은 토큰과 함께 **`viewer_url`** 을 반환한다.

```json
{
  "token": "vt_iap_...",
  "expires_in": 900,
  "viewer_url": "https://viewer.iapetus.dev/d/dsk_01H8...?t=vt_iap_..."
}
```

`viewer_url` 은 **토큰이 박힌 완성된 접속 주소**이며 별도 리소스가 아니다. 유효기간은 토큰과 동일(15분)하고, 토큰이 self-refresh 되면 뷰어가 주소를 갱신하지 않고 연결을 유지한다. Desktop 리소스에는 저장되지 않는다 — actor마다 다른 값이기 때문이다.

이 주소를 사용자 브라우저에 넘긴다. 감사 로그의 `actor.id` 는 여기서 온 값이다 — **Iapetus는 고객사가 보낸 사용자 식별자를 신뢰**하며, 최종 사용자 인증 책임은 고객사에 있다. 이 신뢰 경계를 계약서에 명시한다.

#### 회수 (Revoke)

| 대상 | 방법 | 반영 시간 |
|---|---|---|
| Project Key | 대시보드/API에서 폐기, 즉시 재발급 | 즉시 |
| Agent / Viewer Token | `POST /v1/tokens/revoke` — `jti` 또는 `desktop_id` 단위 (클레임은 위 표) | < 5s (폐기 목록 캐시 TTL) |
| 전체 (사고 대응) | `POST /v1/projects/{id}/revoke-all` | < 5s. 모든 세션 강제 종료 |

토큰은 짧게 유지(15분~1시간)하여 **회수 실패 시에도 노출 창이 자동으로 닫히게** 한다.

#### 갱신 (Refresh)

Project Key는 브라우저에 내려가지 않으므로, 뷰어는 스스로 갱신할 방법이 있어야 한다. **아직 만료되지 않은 토큰 자신을 제시해 연장**하는 self-refresh 방식을 쓴다.

```http
POST /v1/tokens/refresh
Authorization: Bearer vt_iap_...        # 만료 전 토큰 자신

→ { "token": "vt_iap_...", "expires_in": 900 }
```

| 규칙 | 값 |
|---|---|
| 갱신 가능 조건 | 토큰이 아직 유효하고, 회수되지 않았고, Desktop이 삭제되지 않음 |
| 갱신 시점 | SDK/뷰어가 만료 5분 전 자동 호출 |
| **총 수명 상한** | 최초 발급 후 **8시간**. 이후에는 고객사 서버가 다시 발급해야 함 |
| 만료·회수 후 갱신 | `401 TOKEN_EXPIRED`. 뷰어는 재발급 안내 화면으로 전환 |

총 수명 상한을 두는 이유는 self-refresh가 무제한이면 **회수의 실효성이 사라지기** 때문이다. Agent Token도 동일 규칙(1시간 TTL, 총 24시간 상한)을 따른다.

**Guest Token(`iapetusd`)도 갱신한다.** `auto_suspend: false` Desktop은 몇 주간 ACTIVE로 남을 수 있으므로, 24시간 만료 전에 mTLS 인증서를 근거로 자동 재발급받는다. 재발급 실패 시 Desktop은 `DEGRADED` 로 표시된다.

#### mTLS (게스트 채널)

`iapetusd` 는 Guest Token과 별개로 **클라이언트 인증서**를 함께 제시한다. 인증서는 Desktop 프로비저닝 시 발급되며 Desktop 수명과 함께 폐기된다. 게스트가 root라 인증서를 훔칠 수 있지만, 그것으로 할 수 있는 것은 **자기 자신의 Desktop 채널 사용뿐**이다 (§9.1).

### 8.2 API 공통 규약

엔드포인트마다 반복하지 않기 위해 여기서 한 번만 정한다. 아래는 `/v1` 전체에 적용된다. **명시하지 않으면 구현자가 임의로 정하게 되고, 그 값이 곧 장애 조건이 된다.**

#### 식별자

| 리소스 | 접두어 | 리소스 | 접두어 |
|---|---|---|---|
| Desktop | `dsk_` | 시크릿 | `sec_` |
| Session | `ses_` | 웹훅 | `whk_` |
| Owner 엔트리 | `own_` | 이미지 | `img_` |
| 프로젝트 | `prj_` | 이벤트 | `evt_` |
| 비동기 작업 | `job_` | 웹훅 전달 | `dlv_` |
| 스크린샷 | `shot_` | 요청 추적 | `req_` |
| 토큰 식별자 | `jti_` | | |

- 형식: `{접두어}{26자 Crockford Base32 ULID}` — 예 `dsk_01H8XK4M2N7P9Q3R5S6T7V8W9X`.
- **불투명(opaque) 문자열이다.** 접두어 외 어떤 구조도 가정하지 않는다. 정렬 순서·생성 시각을 ID에서 추론하지 않는다.
- **대소문자를 구분한다.** 전체 길이 30자, `[A-Za-z0-9_]` 만 사용. 전부 서버가 생성한다.
- **예외 — actor ID는 이 규칙을 따르지 않는다.** `actor.id`(§8.1)는 고객사가 주장하는 값이므로 자유 형식 UTF-8 ≤128자이며, **Iapetus는 이를 파싱하지 않는다.** 감사 로그에 그대로 기록할 뿐이다.
- 창 ID(`win_1`)는 **게스트 지역 식별자**로 Desktop 재부팅 시 재사용된다. 영속 참조로 쓰지 않는다.

#### 시각

- 모든 타임스탬프는 **RFC 3339 UTC, 소수점 3자리 고정**: `2026-08-15T09:42:13.220Z`. `Z` 는 필수이며 오프셋 표기를 허용하지 않는다.
- **게스트 시각이 아니라 Control Plane 기준 시각이다.** 게스트 시계는 resume 직후 어긋날 수 있다(§7.4).
- **Unix 정수 초를 쓰는 곳은 JWT 클레임(`iat`·`exp`·`orig_iat`)과 `X-RateLimit-Reset` 헤더뿐이다.** 각각 JWT(RFC 7519)와 레이트리밋 관례를 따르기 위한 것이며, **API 본문 필드에는 쓰지 않는다.** 이 목록이 곧 예외의 전부이며, 여기 없는 모든 시각 값은 RFC 3339 문자열이다.
- 기간은 초 단위 정수이며 이름에 `_sec` 를 붙인다(`idle_timeout_sec`).

#### 좌표·수치

- 화면 좌표는 **정수 픽셀**이다. 소수점을 보내면 `400 INVALID_COORDINATE` — 반올림하지 않는다.
- 화면 밖 좌표는 **거부한다. 클램핑하지 않는다.** 조용히 보정하면 Agent가 자기 오류를 인지하지 못한다.
- `bounds` 는 `{x, y, width, height}` 객체다. 위치 배열을 쓰지 않는다 — `[100,100,420,720]` 이 x1y1x2y2인지 xywh인지 읽는 사람이 알 수 없다.
- `scale` 은 `0 < scale ≤ 1` 의 실수다. 확대는 지원하지 않는다.

#### 오류 응답

모든 4xx·5xx는 같은 봉투를 쓴다.

```json
{
  "error": {
    "code": "CONTROL_HELD",
    "message": "Another session holds the write lease.",
    "request_id": "req_01H8XK4M2N7P9Q3R5S6T7V8W9X",
    "details": { "holder": { "type": "agent", "id": "agent_123" } },
    "retry_after_sec": 30
  }
}
```

- `request_id` 는 **2xx 응답에도 헤더 `X-Request-Id` 로 반환한다.** 이것이 없으면 §12.5의 OpenTelemetry 트레이스를 고객이 지목할 방법이 없다.
- `code` 는 §8.9의 안정 식별자다. 새 코드가 추가될 수 있으므로 **클라이언트는 모르는 코드를 HTTP 상태 기준으로 처리해야 한다.**
- `message` 는 사람이 읽기 위한 영문이며 파싱 대상이 아니다.

#### 목록 조회

Control Plane 목록은 **커서 기반**이다. 오프셋을 쓰지 않는 이유는 Desktop이 수천 개인 상태에서 페이지를 넘기는 동안 목록이 바뀌면 항목이 중복·누락되기 때문이다.

```http
GET /v1/desktops?limit=25&starting_after=dsk_...&status=ACTIVE&label=team:sales

{
  "data": [ ... ],
  "has_more": true,
  "next_cursor": "dsk_..."
}
```

| 파라미터 | 기본 | 최대 |
|---|---|---|
| `limit` | 25 | 100 |
| `starting_after` | — | 서버가 발급한 ID만 유효 |

- 정렬은 `created_at` 내림차순 고정이다. v1에서 정렬 키를 선택할 수 없다.
- 필터: `status`, `label`, `os`, `desktop_type` (AND 결합). 감사 로그는 `from`·`to` 로 기간을 좁히며, 미지정 시 **최근 24시간만** 반환한다.

**게스트 측 목록은 페이지네이션하지 않는다.** `fs.list`, `process.list`, `window.list`, `app.list` 는 게스트에 안정적인 스냅샷이 없어 커서를 유지할 수 없다. 대신 **1,000건에서 자르고 `truncated: true` 를 반환**한다. Agent는 경로를 좁혀 다시 부른다.

#### 상한

무제한인 것은 없다.

| 대상 | 상한 | 초과 시 |
|---|---|---|
| `act` 액션 배열 | **64개**, 전체 120초 | `400 BATCH_TOO_LARGE` |
| `type` 텍스트 | 8,192자 | `400 PAYLOAD_TOO_LARGE` |
| 파일 업로드 인라인 | 32MB. 초과는 presigned URL **필수** | `413` |
| 파일 업로드 총량 | 5GB | `413` |
| `shell.exec` 출력 | stdout·stderr 각 1MB. 초과분은 잘리고 `truncated: true` | — |
| 스크린샷 | 4096×4096. `quality` 1~100, `format` ∈ `jpeg`\|`png`\|`webp` | `400` |
| 스크린샷 인라인 base64 | 256KB 미만일 때만. 이상이면 URL 반환 | — |
| Desktop당 동시 Session | **WRITE 1 + READ 10** | `409 TOO_MANY_SESSIONS` |
| Desktop당 Owner | 50 | `400` |
| 프로젝트당 웹훅 | 20 | `400` |
| 경로 길이 | 4,096 (Linux) / 260 (Windows 기본) | `400 INVALID_PATH` |

READ 세션 상한 10은 호스트당 동시 스트리밍 6개(§12.4)보다 **의도적으로 높다.** 두 상한이 같으면 어느 쪽에 걸렸는지 구분되지 않는다 — 세션은 붙었으나 스트림 용량이 없으면 `NO_STREAM_CAPACITY` 로 명확히 알린다.

#### 타임아웃

| 대상 | 기본 | 최대 |
|---|---|---|
| `act` 의 `timeout_ms` (**배치 전체 기준**) | 30,000 | 120,000 |
| `shell.exec` | 30,000 | 300,000 |
| `wait_for` | 10,000 | 120,000 |

**타임아웃은 취소가 아니다.** `ACTION_TIMEOUT` 은 "응답을 기다리지 않겠다"는 뜻이며, **액션이 실행됐는지 여부는 알 수 없다.** 클릭·타이핑은 이미 반영됐을 수 있다. 그래서 상태 변경 액션에 `Idempotency-Key` 는 **선택이 아니라 필수**다(§8.4). 재시도 전에는 `screenshot` 으로 실제 상태를 확인한다.

#### 인코딩

- 요청·응답은 UTF-8 JSON, `Content-Type: application/json; charset=utf-8`.
- `type` 액션의 텍스트는 **UTF-8 NFC로 정규화**해 게스트에 전달한다. 한글 조합형/완성형이 섞여 들어오면 게스트 IME가 자모를 분리하기 때문이다(§11 국제화, §15.2).
- 그 외 문자열은 정규화하지 않는다.
- **바이너리는 원칙적으로 presigned URL로 주고받는다.** 다만 왕복을 줄이는 것이 이득인 두 경우만 인라인을 허용한다 — 32MB 미만 업로드와 256KB 미만 스크린샷 base64(위 상한 표). 그 이상은 URL이 강제된다.

#### 버전 관리

| 축 | 표기 | 대상 |
|---|---|---|
| 전송 형태 | 경로 `/v1` | 파괴적 변경 시에만 `/v2` 신설, 12개월 병행 |
| 동작 변경 | 헤더 `Iapetus-Version: 2026-08-15` | 부가·동작 변경. 미지정 시 계정 고정 버전 |

- `/v1` 안에서는 **필드 추가만** 한다. 삭제·의미 변경·필수화는 파괴적 변경이다.
- 클라이언트는 **모르는 필드를 무시**해야 한다.
- 폐기 시 `Deprecation` 및 `Sunset` 헤더를 붙인다.
- **§19.4의 데몬 프로토콜 정수 버전은 내부 값이며 API 클라이언트에게 노출되지 않는다.** 둘을 연결하지 않는 이유는, N-2 데몬이 `/v1` 호출의 동작을 조용히 바꾸는 것을 막기 위해서다. 데몬 버전 차이로 기능이 제한되면 Desktop이 `DEGRADED` 로 표시되고, 그 사실이 API 응답에 드러난다.

### 8.3 리소스 스키마

`S` = 서버 설정(클라이언트가 보내면 무시), `C` = 클라이언트 설정, `C!` = 생성 시에만 설정 가능.

#### Desktop

| 필드 | 타입 | | 기본 | 비고 |
|---|---|---|---|---|
| `id` | string | S | — | `dsk_` (§8.2) |
| `name` | string | C | — | **프로젝트 내 유일.** `^[a-z0-9][a-z0-9-]{0,62}$` |
| `project_id` | string | S | — | |
| `os` | enum | C! | `linux` | `linux` \| `windows` |
| `image` | string | C! | 기본 이미지 | `img_` 또는 카탈로그 태그 |
| `spec_tier` | enum | C | `standard` | 아래 표 참조 |
| `display` | object | C | 1920×1080@96 | `{width, height, dpi}` |
| `desktop_type` | enum | C! | `personal` | `personal` \| `shared` (§5.2). 전환은 전용 엔드포인트 |
| `privilege_mode` | enum | C | `owner` | `owner` \| `restricted` (§7.3) |
| `os_user` | object | S | — | `{name, sudo}`. 이미지가 정하며 변경 불가 |
| `owners` | array | C! | — | 생성 시에만. 이후 전용 엔드포인트 (§8.1) |
| `status` | enum | S | — | §5.4 |
| `persistent` | bool | S | `true` | v1은 항상 true |
| `idle_timeout_sec` | int | C | 900 | 60 ~ 86400 |
| `auto_suspend` | bool | C | `true` | |
| `labels` | map | C | `{}` | 키·값 각 ≤63자, 최대 20쌍 |
| `sessions` | array | S | — | 현재 붙어 있는 Session 요약. idle 판정 근거 (§5.4) |
| `created_at` / `last_active_at` | string | S | — | RFC 3339 |

**`spec_tier` 는 자유 수치가 아니라 고정 등급이다.** 자유 조합을 허용하면 §12.4 용량 모델(메모리 오버커밋 1:1, 등급별 호스트 풀 분리)이 성립하지 않는다.

| `spec_tier` | vCPU | 메모리 | 디스크 | 용도 |
|---|---|---|---|---|
| `light` | 2 | 2GB | 20GB | 단순 웹 자동화. **Chrome 탭 5개 권장 상한** |
| `standard` | 2 | 4GB | 40GB | 기본 |
| `large` | 4 | 8GB | 80GB | Windows·엑셀·ERP |
| `gpu` | 4 | 8GB + GPU | 80GB | 관찰 비율 높은 워크로드 (§6.3) |

`name` 은 `confirm_name`(삭제)과 `get_or_create` 의 비교 대상이므로 **바이트 단위로 정확히 비교**한다.

#### Image

| 필드 | 타입 | | 비고 |
|---|---|---|---|
| `id` | string | S | `img_` |
| `name` / `tag` | string | C | `acme/erp-desktop:2026.08` |
| `os` | enum | C | |
| `visibility` | enum | C | `public`(카탈로그) \| `project` |
| `source` | object | C! | **무엇으로부터 빌드하는가.** 아래 참조 |
| `apps` | array | C | 사전 설치 앱 카탈로그 (§7.3) |
| `status` | enum | S | `BUILDING` \| `READY` \| `FAILED` |
| `size_bytes` | int | S | |

`source` 는 셋 중 하나다. **이 필드가 없으면 D-09는 구현할 수 없다** — 빌드 팜을 운영해야 하는지 아닌지가 결정되지 않기 때문이다.

```jsonc
{ "source": { "type": "registry", "ref": "ghcr.io/acme/erp-desktop:2026.08" } }  // 고객이 빌드해 올림
{ "source": { "type": "base_image", "base_image_id": "img_...",                  // 기본 이미지 + 설치 스크립트
              "setup_script": "https://..." } }
{ "source": { "type": "dockerfile", "context_url": "https://..." } }             // Phase 3 이후
```

**v1은 `registry` 만 지원한다.** 고객이 자기 CI에서 빌드해 레지스트리에 올리고 우리는 참조만 한다. 빌드 팜은 운영 부담이 크고 D-09의 목적(조직 전용 앱 포함)에는 참조만으로 충분하다. `base_image` 는 Phase 3, `dockerfile` 은 그 이후다.

`POST /v1/images` 로 등록하며 이미지 검증(크기·레이어·`iapetusd` 주입 호환성)은 비동기 작업이다(§8.4).

#### Policy

프로젝트 정책과 Desktop 오버라이드는 **같은 문서 형태**를 쓰고, 조회 시 병합 결과를 반환한다.

```json
{
  "network": { "mode": "standard", "deny_domains": [], "allow_domains": null },
  "recording": { "forced": false, "retention_days": 90, "deletion_lock": false },
  "audit_params": "digest",
  "privilege_mode": "owner",
  "approval_required": [],
  "masking": [{ "window_title_regex": "^Bank", "region": null }]
}
```

- **병합은 최상위 키 단위 교체다.** 깊은 병합을 하지 않는다 — `deny_domains` 를 부분 상속하면 어느 목록이 적용 중인지 아무도 확신할 수 없게 된다.
- `GET /v1/desktops/{id}/policy` 는 병합 결과와 함께 각 키의 출처(`project` \| `desktop`)를 반환한다.

#### Secret

| 필드 | | 비고 |
|---|---|---|
| `id` | S | `sec_` + ULID. **의미 있는 이름을 ID에 넣지 않는다** |
| `name` | C | 사람이 읽는 이름. 변경 가능 |
| `allowed_desktop_ids` | C | 미지정 시 프로젝트 전체 허용 + 경고 (§9.3) |
| `created_at` / `updated_at` | S | |

**값은 어떤 API로도 조회되지 않는다.** 쓰기 전용이며 `secret.type` 으로만 사용된다.

#### Webhook

| 필드 | | 비고 |
|---|---|---|
| `id` | S | `whk_` |
| `url` | C | HTTPS 필수 |
| `events` | C | §8.7의 타입 문자열 배열. 알 수 없는 값은 `400` |
| `secret` | C! | 생성 시 1회만 반환. 이후 조회 불가 |
| `status` | S | `active` \| `failing` \| `disabled` |

#### v1에서 제외

| 리소스 | 사유 |
|---|---|
| **Snapshot** | D-08이 P2다(§7.1). v1은 자동 백업(§11)만 제공하고 사용자 스냅샷 API를 열지 않는다 |
| **Organization** | 개념 계층(§5.1)에만 존재한다. v1은 프로젝트 단위로만 과금·격리하며 조직 API를 두지 않는다 |

두 리소스를 엔드포인트 목록에서 뺀다. **참조만 하고 스키마가 없는 리소스를 남겨두는 것이 더 나쁘다.**

### 8.4 REST API (요약)

```text
POST   /v1/desktops                      # 생성
   owners[]              초기 Owner 지정 (project:manage, 생성 시에만)
   clone_volume_from     기존 Desktop 볼륨을 복제해 시작 (§12.3 ERROR 복구)
   desktop_type          personal(기본) | shared (§5.2)
GET    /v1/desktops                      # 목록. 커서 페이지네이션 + status/label/os/desktop_type 필터 (§8.2)
GET    /v1/desktops/{id}                 # 상세
POST   /v1/desktops/{id}/suspend
POST   /v1/desktops/{id}/resume
POST   /v1/desktops/{id}/restart
DELETE /v1/desktops/{id}                 # confirm_name 필요 (이름 바이트 일치) → DELETING
POST   /v1/desktops/{id}/restore         # DELETING → SUSPENDED 로 복구 (24h 내, §10.3)

GET    /v1/desktops/{id}/owners          # Owner 목록 (사람 뷰어에서 직접 호출 가능)
POST   /v1/desktops/{id}/owners          # Owner 추가 (사람 actor만 호출 가능)
DELETE /v1/desktops/{id}/owners/{oid}    # Owner 제거 (사람 actor만)
POST   /v1/desktops/{id}/convert-to-shared  # personal → shared
   confirm_exposure: true   기존 로그인 세션이 새 Owner에게 노출됨에 동의. 비가역, 사람 actor만
```

**Session 스코프 vs Desktop 스코프**

파일 조작은 두 경로가 있다. 잘못 고르면 SUSPENDED Desktop을 깨우느라 요금이 나간다.

| 경로 | 필요 상태 | 특징 |
|---|---|---|
| `POST /v1/sessions/{sid}/files/upload` | `ACTIVE` + 제어권 | 실행 중인 앱이 즉시 인식. GUI 흐름과 동기화 |
| `GET /v1/desktops/{id}/files` (읽기) | 모든 상태 | 볼륨을 직접 읽는다. Desktop을 깨우지 않음. 결과 회수·ERROR 복구용 |
| `POST /v1/desktops/{id}/files` (쓰기) | 모든 상태 (**제약 있음**) | 아래 규칙 참조 |

**SUSPENDED 상태 볼륨 쓰기는 그냥 허용하면 파일시스템을 깨뜨린다.**

`SUSPENDED` 는 단순 정지가 아니라 **메모리 스냅샷**이다. 스냅샷 안에는 게스트 커널의 페이지 캐시·dentry·inode 상태가 그 시점 디스크 내용을 전제로 얼어 있다. 밖에서 블록 디바이스를 바꾼 뒤 스냅샷을 복원하면 커널이 들고 있는 메타데이터와 실제 디스크가 어긋나 **파일 손상·저널 불일치**가 발생한다.

**결정: 쓰기는 메모리 스냅샷을 무효화한다.**

| 상태 | 읽기 | 쓰기 |
|---|---|---|
| `ACTIVE` | ✅ | ⚠️ 허용하되 응답에 `warning: "desktop_is_active"`. 앱이 연 파일과 경합 가능 |
| `SUSPENDED` | ✅ (크래시 일관성 수준) | ✅ **단, 메모리 스냅샷을 폐기한다.** 다음 resume은 콜드 부팅이 되며 실행 중이던 프로세스는 유실 |
| `ERROR` | ✅ | ✅ (스냅샷 이미 무의미) |

SUSPENDED 쓰기 요청에는 `acknowledge_snapshot_loss: true` 를 명시해야 한다. 없으면 `409 SNAPSHOT_WOULD_BE_DISCARDED` 로 거부하고, 호출자가 의도를 확인하게 한다. **로그인 세션·파일은 볼륨에 있으므로 유지된다** — 잃는 것은 프로세스 상태뿐이다.

#### 웹훅

이벤트를 폴링하지 않고 고객사 서버로 밀어준다. 스케줄 루틴(S3)에서 Agent 런타임이 상시 연결을 유지하지 않아도 되게 하는 장치다.

```http
POST https://customer.example.com/hooks/iapetus
X-Iapetus-Delivery: dlv_01H8XK4M2N7P9Q3R5S6T7V8W9X
X-Iapetus-Timestamp: 1755250933
X-Iapetus-Signature: sha256=...

{ "id": "evt_01H8...", "type": "control.revoked", "created_at": "2026-08-15T09:42:13.220Z",
  "project_id": "prj_01H8...", "desktop_id": "dsk_01H8...", "data": { } }
```

- **본문은 §8.7의 이벤트 봉투 그대로다.** 타입과 이벤트 ID를 헤더에만 두지 않는다 — 본문만 저장하는 수신 측이 둘 다 잃기 때문이다. 헤더의 `X-Iapetus-Delivery` 는 재전송 시도를 구분하는 값으로, 같은 `id` 를 여러 번 받을 수 있다.
- 서명: `HMAC-SHA256(secret, X-Iapetus-Timestamp + "." + raw_body)`. 수신 측은 **원문 바이트로** 검증한다.
- 리플레이 방지: `X-Iapetus-Timestamp`(Unix 초)가 5분 이상 어긋나면 거부한다.
- 재시도: 2xx 아니면 지수 백오프로 최대 6회 (총 ~1시간). 이후 `webhook.failed` 를 SSE·대시보드로 알린다 (§8.7).
- **순서 보장 없음.** 수신 측은 `created_at` 으로 정렬하고 `id` 로 중복을 제거한다.

#### 레이트 리밋 및 쿼터

두 층으로 나눈다. **레이트 리밋은 API 호출 빈도**, **쿼터는 리소스 총량**이다.

| 대상 | 기본 한도 | 초과 시 |
|---|---|---|
| 제어 액션 (`act`, `click`, `type`) | Desktop당 20 req/s | `429 RATE_LIMITED` + `Retry-After` |
| 연속 입력 (`mouse.move`, `scroll`) | **요청 수 제한 대상 아님.** 별도로 초당 60 이벤트 | 초과분은 합쳐서 전달 (§7.5) |
| `screenshot` | Desktop당 5 req/s | 429 |
| Desktop 생성 | 프로젝트당 10 req/min | 429 |
| 토큰 발급 | 프로젝트당 100 req/min | 429 |
| 기타 관리 API | 프로젝트당 50 req/s | 429 |

| 쿼터 | Free | Pro | Enterprise |
|---|---|---|---|
| 동시 ACTIVE Desktop | 1 | 25 | 협의 |
| 총 Desktop (SUSPENDED 포함) | 2 | 200 | 협의 |
| 월 컴퓨트 시간 | 10h | 1,000h | 협의 |
| 볼륨 총량 | 20GB | 2TB | 협의 |
| 감사 로그 보존 | 30일 | 90일 | 365일 |

쿼터 초과는 `429 QUOTA_EXCEEDED` 이며, **실행 중인 Desktop을 강제 종료하지 않는다.** 신규 생성만 막고 대시보드·웹훅으로 알린다. 진행 중인 Agent 작업이 쿼터 때문에 중단되는 것이 더 큰 피해이기 때문이다.

레이트 리밋 응답에는 항상 다음 헤더를 포함한다.
```text
X-RateLimit-Limit: 20
X-RateLimit-Remaining: 3
X-RateLimit-Reset: 1755250000
Retry-After: 1
```

#### 동기 / 비동기

수 초 이상 걸리는 작업은 **비동기 작업 리소스**로 처리한다. 어느 쪽인지 명시하지 않으면 SDK 작성자가 첫 호출부터 추측하게 된다.

| 비동기 (`202` + `job_`) | 동기 |
|---|---|
| Desktop 생성 / resume / restart / 삭제 | 나머지 전부 |
| 이미지 등록·빌드 | |
| `app.install` | |
| 볼륨 내보내기(`export`) | |

```jsonc
// POST /v1/desktops → 202
{ "job_id": "job_01H8...", "resource_id": "dsk_01H8...", "status": "running" }

// GET /v1/jobs/job_01H8...
{
  "id": "job_01H8...", "type": "desktop.create", "status": "succeeded",
  "resource_id": "dsk_01H8...", "started_at": "...", "finished_at": "...",
  "error": null
}
```

`status` ∈ `running` \| `succeeded` \| `failed`. 작업 레코드는 **7일** 보존한다 — 삭제 작업은 24시간 `DELETING` 유예를 추적하므로 24시간 보존으로는 작업이 끝나기 전에 레코드가 사라진다.
SDK의 `create()` 는 기본적으로 완료까지 폴링하며, `wait=False` 로 즉시 반환할 수 있다.

제품의 핵심 기능이므로 본문을 명시한다.

```jsonc
{
```

```jsonc
// POST /v1/sessions/{sid}/heartbeat  →  200
{ "lease_expires_at": "2026-08-15T09:47:30.000Z" }
// 409 CONTROL_LOST — 이미 회수됨. 재획득하려면 acquire 를 다시 부른다
```

**리스 수명은 `heartbeat_interval_sec × 3` 이다.** 기본 30초 주기이므로 90초. §5.6의 "3× 무응답 시 회수" 규칙과 같은 값이며, 두 곳에 다른 숫자가 생기지 않도록 여기서 유도한다.

#### 멱등성 (`Idempotency-Key`)

GUI 액션은 본질적으로 멱등하지 않다. `click` 을 두 번 보내면 두 번 눌린다. 네트워크 타임아웃 후 재시도는 **가장 흔한 실패 모드**이므로 다음과 같이 정의한다.

- 서버는 `Idempotency-Key` 별로 **응답을 캐시**한다. TTL 24시간.
- 같은 키로 재요청이 오면 **액션을 재실행하지 않고** 캐시된 응답을 반환한다.
- 첫 요청이 아직 실행 중이면 `409 REQUEST_IN_FLIGHT` 를 반환한다. 클라이언트는 백오프 후 같은 키로 재조회한다.
**키 형식과 유효 범위**

| 항목 | 값 |
|---|---|
| 생성 주체 | 클라이언트 (SDK가 자동 생성) |
| 형식 | `[A-Za-z0-9_-]{1,255}` |
| **유효 범위** | **`(project_id, session_id, endpoint)`** |
| TTL | 24시간 |

**범위를 전역이 아니라 세션 단위로 두는 것이 핵심이다.** 전역이면 서로 다른 테넌트가 같은 키 문자열을 쓸 때 한쪽이 다른 쪽의 캐시된 응답을 받는다. 키가 필수가 된 이상 이는 스타일 문제가 아니라 **격리 문제**다.

**키를 요구하지 않는 두 경로**

| 경로 | 이유 |
|---|---|
| WebSocket 제어 채널 (§8.5) | 프레임이 연결 단위로 순서 보장되고 재전송이 없다(§19.5). 재시도 개념 자체가 없으므로 키가 무의미하다 |
| 뷰어 입력 (§7.5) | 사람의 클릭은 재시도 가능한 RPC가 아니다. 게이트웨이는 입력을 재전송하지 않으며, 유실되면 사람이 다시 클릭한다 |

즉 **멱등성 키는 REST 액션 경로에만 적용된다.** 이 경계를 명시하지 않으면 구현자가 WS와 뷰어에도 키를 강제해 양쪽 다 동작하지 않게 된다.

- **상태 변경 액션에 키는 필수다.** 없으면 `400 IDEMPOTENCY_KEY_REQUIRED`. `ACTION_TIMEOUT` 이 "실행 여부 불명"을 뜻하는 이상(§8.2), 키 없는 재시도는 중복 실행을 구조적으로 허용하는 셈이기 때문이다. 관측 액션(`screenshot`, `app.list` 등)에는 요구하지 않는다.
- SDK가 자동 부여하므로 사용자가 직접 다룰 일은 없다.

이 계약이 없으면 "타임아웃 → 재시도 → 메시지 2번 발송"이 구조적으로 발생한다.

### 8.5 WebSocket 제어 채널

지연 최소화가 필요한 인터랙티브 루프용. REST와 동일한 액션 스키마를 프레임 단위로 주고받는다.

**한 연결 안에서 프레임은 도착 순서대로 실행된다(FIFO).** 파이프라이닝은 허용하되 재정렬은 하지 않으며, 인플라이트 깊이는 8이다. 이 보장은 §19.5의 게스트 스트림이 순서를 유지하는 데서 나온다. 서로 다른 연결 사이에는 순서 보장이 없다 — 순서가 중요하면 같은 연결을 쓰거나 `act` 로 묶는다.

**WebSocket 프레임에는 멱등성 키가 없다**(§8.4). 재전송이 없기 때문이다.

```text
wss://api.iapetus.dev/v1/sessions/{sid}/control
  → { "id": 1, "type": "mouse.click", "x": 640, "y": 120 }   // id 는 uint64
  ← { "id": 1, "ok": true, "elapsed_ms": 22 }
  ← { "event": "window.opened", "window": {...} }      # 서버 푸시
```

```python
    owners=[                                  # 생성 시에만 지정 가능 (§8.1)
        {"type": "agent", "id": "agent_123"},
        {"type": "human", "id": "usr_kim"},
    ],
    labels={"team": "sales"},
)
# 이미 존재하는 Desktop을 가져온 경우 owners 는 무시된다 —
# 생성 후 Owner 변경은 사람 전용이므로 SDK가 대신 적용하지 않는다.
# 불일치가 있으면 desktop.owners 로 확인할 수 있다.

with desktop.session() as c:          # 제어권 획득 + 자동 heartbeat
    # 카탈로그 앱
    c.launch_app("acme_messenger", wait_for_window=True)
    shot = c.screenshot()
    c.click(320, 210)
    c.type("안녕하세요")
    c.key("Enter")

    # 카탈로그에 없는 프로그램도 그대로 실행 (OWNER 모드)
    c.launch_app(command=r"C:\Program Files\SomeERP\erp.exe", args=["--kiosk"])

    # 관리자 셸 / 설치
    r = c.shell("winget install --id Notepad++.Notepad++ -e", elevated=True)
    assert r.exit_code == 0
# 세션 종료. Desktop은 계속 ACTIVE → 접속자 0 상태로 idle_timeout 경과 시 auto-suspend
```

### 8.7 이벤트 스트림

`GET /v1/desktops/{id}/events` (SSE) 및 WS 제어 채널로 푸시된다. **Agent는 제어권 상실을 다음 액션 호출까지 기다려 알게 되어서는 안 된다.**

모든 이벤트는 아래 봉투를 공유하며 `data` 만 타입별로 다르다. **SSE와 웹훅이 같은 봉투를 쓴다** — 수신 측이 전송 경로에 따라 파서를 나누지 않게 하기 위해서다.

```json
{
  "id": "evt_01H8XK4M2N7P9Q3R5S6T7V8W9X",
  "type": "control.revoked",
  "created_at": "2026-08-15T09:42:13.220Z",
  "project_id": "prj_01H8XK4M2N7P9Q3R5S6T7V8W9X",
  "desktop_id": "dsk_01H8XK4M2N7P9Q3R5S6T7V8W9X",
  "data": {}
}
```

웹훅 전달 시에도 **이 본문을 그대로** 보낸다. 전달 ID와 타입을 헤더에만 두면 본문만 저장하는 수신 측이 둘 다 잃는다.

| 이벤트 | `data` | 언제 |
|---|---|---|
| `control.granted` | `session_id`, `actor{type,id}` | 제어권 획득 |
| `control.revoked` | `session_id`, `by_actor{type,id}`, `reason` ∈ `preempted`\|`lease_expired`\|`session_closed`, `note?` | **사람이 선점** / 리스 만료 |
| `control.requested` | `by_actor{type,id}` | 사람 보유 중 Agent가 요청 |
| `desktop.status` | `from`, `to`, `reason?` | 상태 전이 (§5.4) |
| `desktop.error` | `reason`, `recoverable`, `data_recoverable` — 볼륨 회수 가능 여부 (§12.3) | 복구 불가 진입 |
| `job.finished` | `job_id`, `type`, `status`, `error?` | 비동기 작업 완료 (§8.4) |
| `quota.exceeded` | `quota`, `limit`, `current` | 쿼터 도달 (신규 생성만 차단) |
| `window.opened` / `window.closed` | `window{id,title,bounds}` | 창 변화 |
| `app.exited` | `key?`, `pid`, `exit_code`, `crashed` | 앱 종료 |
| `viewer.joined` / `viewer.left` | `actor{type,id}`, `control` | 뷰어 접속/이탈 |

`webhook.failed` 는 **SSE·대시보드 전용**이며 웹훅으로 보내지 않는다. 웹훅 실패를 웹훅으로 알리는 것은 순환이다.

**전달 보장은 at-least-once, 순서는 무보장이다.** 수신 측은 `id` 로 중복을 제거하고 `created_at` 으로 정렬해야 한다. 같은 이벤트가 SSE와 웹훅 양쪽으로 도착하는 것은 정상이다.

**SSE 재연결:** 각 이벤트에 SSE `id:` 필드를 실어 보내며, 클라이언트는 `Last-Event-ID` 헤더로 재접속해 **24시간 이내 누락분을 재수신**한다. 15초마다 `:keepalive` 주석 프레임을 보내 유휴 연결이 프록시에서 끊기지 않게 한다.

`control.revoked` 를 받은 Agent의 권장 동작: 진행 중 작업을 중단하고 사람의 조작이 끝날 때까지 대기한다. 화면이 이미 바뀌었을 수 있으므로 **재개 시 반드시 screenshot부터 다시 찍는다.**

## 9. 보안 및 정책

### 9.1 격리 — 신뢰 경계는 Desktop 바깥

Agent가 게스트 내부에서 root를 갖는다는 것은 **게스트 OS를 보안 경계로 쓸 수 없다**는 뜻이다. 따라서 격리는 전부 게스트 밖에서 강제한다.

| 경계 | 수단 |
|---|---|
| 커널 격리 | Desktop 1개 = microVM 1개 (**Firecracker**, 대안 Cloud Hypervisor). 멀티테넌트에서 공유 커널 컨테이너 **금지** |
| 네트워크 | Desktop별 전용 네트워크 네임스페이스. 기본 egress-only, 인바운드 전면 차단 |
| 이웃 접근 | Desktop 간 L2/L3 통신 차단. 메타데이터 엔드포인트(169.254.169.254) 차단 |
| 호스트 자격증명 | 게스트에 호스트/클라우드 자격증명 일절 미주입 |
| 제어 채널 | 게스트 → Control Plane 아웃바운드 mTLS 단방향. 게스트가 Control Plane API를 호출할 권한 없음 |
| 리소스 | CPU/메모리/디스크/네트워크 하드 쿼터. fork bomb·디스크 고갈 방어 |
| 볼륨 | Desktop 전용 암호화 볼륨. 타 Desktop 볼륨 접근 불가 |

#### 네트워크 통제는 게스트 밖에서만 유효하다

게스트 안의 프록시 설정(`http_proxy`, 브라우저 설정, `/etc/hosts`)은 **통제 수단이 아니다.** 사람도 Agent도 root이므로 전부 되돌릴 수 있다. 실제 강제는 아래 계층에서만 이뤄진다.

```text
Desktop (게스트)  ── 여기서 무엇을 설정하든 강제력 없음
      │
      ▼
호스트 네트워크 네임스페이스 / vNIC
      │
      ├─ ① 기본 정책: 티어별 (표준=허용+차단목록 / 강화=DROP+허용목록)
      ├─ ② DNS 강제: 53/853 를 플랫폼 리졸버로 DNAT. 외부 DNS 직행 차단
      ├─ ③ 도메인 필터: TLS SNI 검사 (복호화 없음). 정책 위반 시 연결 리셋
      ├─ ④ IP 직행 차단: DNS 응답에 없던 IP로의 신규 연결 거부 (DNS-IP 상관)
      ├─ ⑤ 사설/메타데이터 대역 차단: 10/8, 172.16/12, 192.168/16, 169.254.169.254
      │     (사내망 연결을 켠 프로젝트는 지정된 대역만 예외 허용. 메타데이터는 예외 없음)
      └─ ⑥ 이상 탐지: 대역폭 급증, 포트 스캔, 알려진 채굴 풀 시그니처
```

**기본값은 "열림"이다.** 표준 티어에서 egress는 **허용이 기본**이고 알려진 악성·채굴 목적지만 차단한다. §14.1 온보딩(크롬 열어 검색)이 첫 시도에서 성공해야 하기 때문이다. DROP 기본은 **강화 모드(enterprise/regulated)에서만** 켜지며, 이때는 고객이 허용 도메인을 등록해야 한다. §9.2 정책 표의 "제한 없음"은 이 표준 티어 기본값을 가리킨다.

**SNI 검사를 택하고 MITM 복호화를 택하지 않은 이유:** 복호화하려면 게스트에 CA를 심어야 하는데, 사용자의 은행·사내 시스템 트래픽까지 평문으로 보게 된다. 이는 §10.2의 데이터 최소수집 원칙과 정면 충돌한다. SNI만으로 도메인 단위 allow/deny는 충분하며, ESNI/ECH가 확산되면 ④의 DNS-IP 상관 방식으로 대체한다.

**DoH/DoT 문제:** Chrome은 기본적으로 DNS-over-HTTPS를 443 포트로 보내므로 ②의 DNAT를 우회한다. 그러면 플랫폼 리졸버가 질의를 보지 못해 ④(DNS-IP 상관)가 모든 연결을 "IP 직행"으로 오판한다. 게스트가 root이므로 게스트 안에서 DoH를 끄는 것은 통제가 아니다.

**대응:** 강화 모드에서는 **알려진 공개 DoH 리졸버의 IP 대역을 ①에서 차단**하고(브라우저는 자동으로 시스템 DNS로 폴백), ④는 그 위에서만 활성화한다. 표준 티어에서는 ④를 켜지 않고 ③(SNI)까지만 적용한다. ECH가 확산되면 SNI도 가려지므로, 그 시점에는 **도메인 단위 통제를 포기하고 목적지 IP 평판 + 트래픽 이상 탐지로 전환**한다. 이 전환을 미리 인정해 둔다 — 도메인 필터링은 영구적인 통제 수단이 아니다.

**한계 명시:** 정교한 공격자는 허용된 도메인을 경유해 터널링할 수 있다(예: 허용된 CDN 위의 covert channel). 네트워크 통제는 **오남용 억제와 사고 방지**를 위한 것이지, 결심한 내부자를 막는 장치가 아니다. 그 수준이 필요하면 egress 전면 차단 + 사내망 PrivateLink 전용 구성을 쓴다.

**`iapetusd` 자체도 신뢰하지 않는다.** 사람과 Agent 모두 게스트 root이므로 데몬을 변조하거나 우회할 수 있다고 가정한다. 쿼터·네트워크·감사는 전부 하이퍼바이저/호스트 레벨에서 강제한다.

### 9.2 정책 엔진 (Project 단위)

**게스트 내부 제약은 기본 없음.** 정책은 주로 Desktop 경계에 적용된다.

| 정책 | 적용 지점 | 기본값 |
|---|---|---|
| 네트워크 도메인 allow/deny | 호스트 egress 프록시 | 제한 없음 |
| 사내망 연결 | VPN/PrivateLink | off |
| 파일 반출 (`fs.download`) | Control Plane | 허용 |
| 고위험 액션 사람 승인 | Control Plane | off |
| 세션 녹화 강제 | Control Plane | off |
| `privilege_mode` | 게스트 (옵트인) | `owner` (제약 없음) |

### 9.3 자격증명 처리

**권장 1순위: 사람이 직접 로그인한다.** 공동 소유 모델의 가장 큰 실무 이득이다 (S5). 사람이 뷰어로 접속해 메신저·사내 시스템에 직접 로그인하면, **자격증명이 Agent에게도 Iapetus에게도 전달되지 않는다.** Agent는 이미 로그인된 세션만 쓴다. 2FA·캡차도 자연히 해결된다.

자동 로그인이 필요할 때만 `secret.type` 을 쓴다.
```json
{ "type": "secret.type", "secret_ref": "sec_erp_password" }
```
- 감사 로그에는 `secret_ref`만 기록하고 값은 절대 기록하지 않는다.
- **시크릿은 Desktop에 바인딩한다.** 프로젝트 스코프로만 두면 같은 프로젝트의 아무 Desktop이나 아무 시크릿을 타이핑할 수 있어, 아래의 "Desktop = 신뢰 단위" 원칙이 API로 강제되지 않는다. 생성 시 `allowed_desktop_ids` 를 지정하며, 미지정 시 프로젝트 전체 허용임을 경고한다.
- 스크린샷 마스킹 규칙(지정 영역 블러) 옵션 제공.

**`secret.type` 의 보호 범위를 오해하지 말 것.**

| 막는 것 | 못 막는 것 |
|---|---|
| 평문이 Agent의 LLM 컨텍스트에 들어가는 것 | Agent가 `shell.exec` 로 게스트 메모리·디스크에서 회수하는 것 |
| 평문이 감사 로그·스크린샷에 남는 것 | Agent가 키로거를 설치하는 것 |

OWNER 모드에서 Agent는 root다. `secret.type` 은 **"실수로 노출되는 것"을 막는 위생 장치이지, "악의적 Agent로부터 보호하는 장치가 아니다."** Agent 코드를 신뢰하지 못하면 그 Desktop에 자격증명을 두면 안 된다.

#### 최종 사용자 보호 (3자 관계)

Desktop에는 최종 사용자의 로그인 세션이 있고, Agent 코드는 고객사가 작성하며, 둘의 권한은 동등하다. 즉 **고객사 코드가 최종 사용자의 계정을 완전히 다룰 수 있다.** 기술로는 막을 수 없으므로 — 막으면 제품이 성립하지 않는다 — **투명성과 통제권**으로 대응한다.

| 장치 | 내용 | 성격 |
|---|---|---|
| **고지·동의 의무** | 최종 사용자에게 "이 Desktop에 어떤 Agent가 어떤 권한으로 붙어 있는지" 고지하고 동의를 받을 의무를 고객사에 부과 | 계약(DPA) |
| **Owner 가시성** | 뷰어에서 현재 Owner 목록과 Agent 식별자를 항상 확인 가능. `GET /v1/desktops/{id}/owners` | 기술 |
| **Agent 축출권** | 사람 Owner는 언제든 Agent Owner를 제거할 수 있다. Agent는 사람을 제거할 수 없다 (§5.2). Viewer Token에 자동 부여되는 `desktop:owners:manage` 로 **고객사 서버를 거치지 않고** 직접 호출 | 기술 |
| **감사 로그 열람권** | 자기 Desktop의 감사 로그를 뷰어에서 직접 조회. `desktop:audit:read` 가 자동 부여되므로 고객사가 스코프를 빼서 가릴 수 없다 | 기술 |
| **상시 관찰권** | 언제든 뷰어로 접속해 Agent가 무엇을 하는지 볼 수 있다 (§7.5) | 기술 |

**이 장치가 막는 것은 스코프 박탈이지 신원 위조가 아니다.** §8.1대로 actor 식별자는 고객사가 주장하는 값이므로, 고객사는 `actor: {type: "human", id: "…"}` 로 토큰을 발급해 두 스코프를 받고 진짜 사람 Owner를 제거할 수 있다. 즉 위 권리들은 **정당한 사용자에게 보장되지만 그에게만 배타적이지는 않다.** 신원 경계는 여전히 §8.1의 계약적 신뢰에 있으며, 이 한계는 R-07로 추적한다.

**§5.2의 두 비대칭 중 하나 — "Owner 변경은 사람만" — 이 여기서 값을 한다.** 그 규칙이 없으면 고객사 Agent가 사람 Owner를 제거하고 Desktop을 탈취할 수 있다. 처음부터 이 상황을 위해 설계된 제약이다.

**Desktop = 자격증명 신뢰 단위.** 서로 다른 신뢰 수준의 자격증명은 **다른 Desktop에 분리**한다. 개인용 메신저와 회사 ERP를 한 Desktop에 두지 않는 것이 권장 패턴이다.

### 9.4 감사 및 추적

사람과 Agent가 같은 OS 계정을 공유하므로(§5.2), **누가 했는지는 OS가 아니라 제어 세션이 증명한다.** 모든 **API 액션**은 actor를 포함한 불변 감사 로그로 기록한다.

**감사 경계를 정확히 밝힌다.** Control Plane을 지나는 것만 기록된다. `shell.spawn` 으로 띄운 백그라운드 프로세스의 이후 행위, 게스트 안에서 앱이 스스로 하는 일, 사람이 터미널을 열어 실행한 명령의 내부 동작은 **API 로그에 남지 않는다.** OWNER 모드에서 이는 원리적 한계다. 전 행위 추적이 필요한 규제 고객에게는 세션 녹화(§10.6) + 게스트 내 감사 에이전트를 별도로 안내하며, API 감사 로그만으로 충족된다고 주장하지 않는다.

```json
{
  "id": "evt_01H8XK4M2N7P9Q3R5S6T7V8W9X",
  "created_at": "2026-08-15T09:42:13.220Z",
  "desktop_id": "dsk_01H8XK4M2N7P9Q3R5S6T7V8W9X",
  "session_id": "ses_01H8XK4M2N7P9Q3R5S6T7V8W9X",
  "actor": { "type": "agent", "id": "agent_123" },
  "action": "type",
  "params": { "text": "안녕하세요" },
  "params_digest": "sha256:...",
  "result": "ok",
  "screenshot_ref": "shot_88a1"
}
```

**원문 기록 정책 (`audit_params`)**

| 값 | 동작 | 용도 |
|---|---|---|
| `full` | `params` 원문 저장 | 규제·감사 대응. 무엇을 입력했는지 재구성 가능 |
| `digest` (기본) | `params_digest`만 저장 | 프라이버시 우선. 변조 검증만 가능 |
| `off` | 액션 타입만 | 최소 기록 |

`secret.type` 의 값은 어떤 모드에서도 기록하지 않는다.

제어권 이양(`control.acquired` / `control.revoked`)도 감사 이벤트로 남긴다. 사람이 Agent를 선점한 시점이 사후 분석의 핵심 단서다.

보존 기간은 플랜별(30/90/365일)로 설정한다.

### 9.5 오남용 방지

- Desktop 수, 동시 실행, 월 컴퓨트 시간 쿼터.
- 네트워크 이상 트래픽(스크래핑·스팸 패턴) 탐지 및 차단.
- 이용약관: 대량 계정 생성, 캡차 우회 서비스, 타인 계정 무단 조작 금지.

## 10. 규제·컴플라이언스·데이터 수명주기

### 10.1 Desktop에 쌓이는 데이터의 성격

Iapetus는 구조상 **개인정보를 저장하게 된다.** 이를 부정하지 않고 설계에 반영한다.

| 데이터 | 어디에 | 개인정보 해당 | 통제 |
|---|---|---|---|
| 앱 로그인 세션·쿠키 | Desktop 볼륨 | ✅ (인증정보) | 볼륨 암호화, Desktop 격리 |
| 메신저 대화 내용 | Desktop 볼륨 | ✅ (제3자 정보 포함 가능) | 고객이 통제. 우리는 열람하지 않음 |
| 스크린샷·세션 녹화 | 오브젝트 스토리지 | ✅ (화면에 무엇이든 찍힘) | 보존기간·마스킹·기본 off |
| 감사 로그 `params` | 로그 저장소 | ✅ (`audit_params: full` 인 경우) | 기본은 `digest` |
| 계정·결제 정보 | Control Plane DB | ✅ | 표준 처리 |

**역할 구분:** Iapetus는 원칙적으로 **수탁자(처리자)** 다. 어떤 데이터를 Desktop에 넣을지 결정하는 주체는 고객사이며, 우리는 그 지시에 따라 저장·처리한다. 이 구분을 계약서(DPA)에 명시하고, 최종 사용자에 대한 고지·동의 의무는 고객사에 있음을 못 박는다.

**우리가 하지 않는 것 (명시적 약속)**
- Desktop 볼륨 내용을 열람하지 않는다. 지원 목적이라도 **고객의 명시적 승인 + 시간 제한 접근**을 거친다.
- 화면·입력 데이터를 모델 학습에 사용하지 않는다.
- 스크린샷을 기본으로 장기 보관하지 않는다 (기본 24시간 후 삭제, 감사 참조가 걸린 것만 보존기간 적용).

### 10.2 데이터 최소수집 및 보존

| 데이터 | 기본 보존 | 최대 | 설정 |
|---|---|---|---|
| 스크린샷 (액션 응답용) | 24시간 | 90일 | 프로젝트 정책 |
| 세션 녹화 | 저장 안 함 (기본 off) | 365일 | 명시적 opt-in |
| 감사 로그 | 30일 | 365일 | 플랜별 |
| Desktop 볼륨 | 무기한 (고객 소유) | — | 고객이 삭제 |
| 볼륨 백업 스냅샷 | 7일 | 30일 | 플랜별 |

**민감 화면 마스킹:** 정책으로 좌표 영역 또는 창 제목 정규식을 지정하면 해당 영역을 가린다. 마스킹은 **게스트 Frame Source에서 인코딩 이전에** 적용되므로 스크린샷·녹화·라이브 스트림에 동일하게 반영된다(§10.6). `secret.type` 중에도 캡처를 멈추지 않고 입력 영역만 가린다 — 캡처를 멈추면 관찰 중인 사람의 화면이 얼어 장애로 오인된다.

### 10.3 삭제 (Right to Erasure)

```text
DELETE /v1/desktops/{id}  (confirm_name 필요)
   │
   ├─ 즉시: `DELETING` 전이 (§5.4). Desktop 종료, 제어 API 차단, 목록에서 기본 숨김
   ├─ 즉시: 키를 격리 보관소로 이동 + 모든 접근 경로 차단 (논리적 불능화)
   ├─ 24시간: 복구 유예. `POST /v1/desktops/{id}/restore` 로 SUSPENDED 로 되돌린다
   ├─ T+24h: 암호화 키 파기 (crypto-shredding) ← 이 시점부터 복호화 불가
   ├─ 7일 이내: 볼륨 물리 삭제 + 볼륨과 같은 키로 암호화된 백업 스냅샷 삭제
   └─ 30일 이내: 오브젝트 스토리지(스크린샷·녹화·썸네일) 완전 삭제
```

- **"즉시 삭제"의 정확한 의미:** T+0에 키를 파기하면 T+12h 복구 요청을 들어줄 수 없다. 둘 다 약속할 수는 없으므로 **복구 유예를 우선**하고, T+0에는 접근 차단(논리적 불능화), **T+24h에 키를 파기**한다. 마케팅 문구로 "즉시 파기"를 쓰지 않는다.
- **백업은 같은 키로 암호화한다.** 그래야 키 파기 하나로 백업까지 함께 불능화된다. 별도 키로 암호화된 백업이 남으면 crypto-shredding 주장이 성립하지 않는다.
- 24시간 유예를 원하지 않는 고객을 위해 `immediate_key_destruction: true` 옵션을 제공한다. 이 경우 복구가 불가능함을 API가 명시적으로 경고한다.
- 계정 해지 시: 전체 Desktop에 동일 절차 적용. 30일 내 완료 후 **삭제 증명서**를 발급한다.
- 감사 로그는 법적 보존 의무와 충돌할 수 있으므로, 삭제 대신 **익명화**로 처리한다. 단 `audit_params: full` 인 경우 `params` 안에 메시지 본문·이름 등 **제3자 개인정보**가 들어 있으므로, actor ID만 지우는 것으로는 부족하다. 이 모드에서는 `params` 필드 전체를 파기하고 `params_digest` 만 남긴다.

### 10.4 반출 (Portability)

| 대상 | 방법 |
|---|---|
| Desktop 볼륨 전체 | `POST /v1/desktops/{id}/export` → 암호화된 tar/qcow2 이미지, presigned URL (7일 유효) |
| 개별 파일 | `GET /v1/desktops/{id}/files/download` (SUSPENDED 에서도 가능) |
| 감사 로그 | JSONL 내보내기 |
| 설정·정책 | JSON 내보내기 |

**락인 방지:** 볼륨을 표준 이미지 포맷(qcow2/tar)으로 내보내므로 고객은 자체 인프라에서 그대로 부팅할 수 있다. 셀프호스트 경로(§19.2)가 존재하는 것 자체가 협상력 균형 장치다.

### 10.5 목표 인증

| 인증 | 시점 | 비고 |
|---|---|---|
| 개인정보보호법 준수 체계 (내부) | Phase 2 | DPA 템플릿, 처리방침, 위탁 고지 |
| **ISMS-P** | Phase 3~4 | 국내 엔터프라이즈 영업의 사실상 전제조건 |
| **SOC 2 Type II** | Phase 4 | 해외 고객 대상. 최소 6개월 관측 기간 필요 |
| 클라우드보안인증(CSAP) | 공공 진입 시 | 공공 시장 진입을 결정한 경우에만 |

**주의:** 인증 취득에는 최소 6~12개월이 걸리며 감사 로그·접근통제·변경관리 증적이 **Phase 1부터 쌓여 있어야** 한다. 나중에 소급 생성할 수 없으므로, 로깅과 변경관리는 초기부터 인증 요건에 맞춰 설계한다.

### 10.6 규제 산업 대응

| 요구 | 대응 |
|---|---|
| 금융권 망분리 | 셀프호스트 배포(§19.2) + PrivateLink 전용 egress |
| 데이터 국외 이전 금지 | 리전 고정 옵션 (ap-northeast-2 pin), 백업도 동일 리전. Windows는 Azure Korea Central 고정 |
| 전 세션 녹화 의무 | 정책으로 강제 녹화 on (**비용·제약은 아래 참조**) |
| 접근 승인 절차 | 고위험 액션 사람 승인(§9.2) |

**강제 녹화의 실제 비용 — 숨기지 않고 명시한다**

강제 녹화는 §6.3의 세 가지 최적화와 정면 충돌하며, 그 대가는 고객이 지불해야 한다.

| 충돌 | 결과 |
|---|---|
| "뷰어 0명이면 인코더 정지" | **성립하지 않는다.** 관찰자가 없어도 계속 인코딩해야 하므로 Desktop당 상시 ~1.8 vCPU 소요 |
| "스트리밍은 별도 과금하지 않는다" (§13) | **예외.** 강제 녹화 티어는 컴퓨트 단가가 상승하며 별도 고지한다 |
| "재인코딩 없는 mux" | **성립한다.** 마스킹이 인코딩 이전(게스트 Frame Source)에 적용되므로 인코딩된 스트림을 다시 건드리지 않는다 |
| §12.4 등급별 배치 밀도 | 강제 녹화 테넌트만 모으면 인코딩 예약 CPU가 먼저 소진되어 대수가 밀도표보다 줄어든다. **전용 호스트 풀로 분리** |

**"삭제 불가 모드"는 §10.3 삭제 보장과 충돌하므로 제공하지 않는다.** 대신 **보존기간 내 삭제 잠금**(예: 365일간 삭제 요청 거부, 이후 자동 파기)으로 제공한다. 법적 보존 의무와 삭제권을 동시에 만족시키는 유일한 형태다.

**라이브 관찰 중 `secret.type`:** 캡처를 멈추면 뷰어 화면이 얼어 사용자가 장애로 오인한다. 대신 **게스트의 Frame Source에서 인코딩 이전에 입력 영역을 검은 사각형으로 덮고**, 뷰어에 "민감 입력 중" 배지를 띄운다.

**마스킹은 반드시 게스트에서, 인코딩 전에 한다.** 게이트웨이는 RTP를 복제만 하는 SFU이므로(§6.3) 거기서 픽셀을 바꾸려면 디코딩·재인코딩이 필요하고, 이는 §6.3이 "뷰어 수 × 비용"으로 기각한 게이트웨이 트랜스코딩을 되살린다. 게스트에서 하면 ① RGBA 버퍼에 사각형을 그리는 비용이라 사실상 0이고 ② 인코딩은 여전히 1회이며 ③ **`secret.type` 실행 시점을 아는 유일한 컴포넌트가 게스트**다. 스크린샷·녹화·라이브가 같은 Frame Source를 읽으므로 **한 곳만 가리면 세 경로가 동시에 가려진다.**

### 12.1 SLA 정의

| 항목 | 목표 | 측정 방법 |

**계산 제외 사유:** 예고된 정기 점검(월 4시간 이내, 7일 전 공지), 고객 측 네트워크 장애, 고객이 게스트 내부에서 유발한 장애(§9.1에 따라 게스트 내부는 고객 책임 영역).

**크레딧 정책**

크레딧 구간은 **절대 수치가 아니라 각 서비스의 목표 대비 미달폭**으로 정의한다. Linux 99.5% / Windows 99.0% 로 목표가 다르므로(위 표), 절대 구간을 쓰면 Windows가 목표를 지켜도 크레딧이 발생한다.

| 목표 대비 미달폭 | 크레딧 | Linux(목표 99.5%) | Windows(목표 99.0%) |
|---|---|---|---|
| 0 ~ 0.5%p | 10% | 99.0% ~ 99.5% | 98.5% ~ 99.0% |
| 0.5 ~ 4.5%p | 25% | 95.0% ~ 99.0% | 94.5% ~ 98.5% |
| 4.5%p 초과 | 50% | < 95.0% | < 94.5% |

크레딧은 고객 신청 기반이며 다음 달 요금에서 차감한다. **컴퓨트 요금에만 적용**하고 Windows 라이선스 등 원가 전가 항목은 제외한다. Linux Desktop과 Windows Desktop은 **별도 산정**하며, 한쪽의 장애가 다른 쪽 크레딧을 발생시키지 않는다.

### 12.2 장애 런북

런북 ID는 `RB-n` 을 쓴다. 리스크 레지스터(§17.1)의 `R-nn` 과 구분하기 위한 것으로, 둘은 서로 다른 체계다.

#### RB-1. 게스트 행(hang) — 화면이 멈추고 입력이 안 먹음

```text
증상: 액션이 ACTION_TIMEOUT 반복, 스트리밍 프레임 정지
1. iapetusd 헬스체크 확인 (호스트 → 게스트 하트비트)
   ├─ 데몬 응답 O → X 서버/컴포지터 문제.  system.service 로 디스플레이 세션 재시작
   └─ 데몬 응답 X → 게스트 OS 레벨 행
2. 게스트 OS 행 → 하이퍼바이저 레벨에서 강제 재시작 (restart)
   - 볼륨은 보존됨. 실행 중이던 앱은 유실
3. 재시작 후에도 실패 → ERROR 전이 + 고객 알림 (웹훅 desktop.error)
목표 복구 시간: 5분
```

#### RB-2. 스냅샷 복원 실패 — resume 이 안 됨

```text
증상: SUSPENDED → ACTIVE 전이 실패
1. 메모리 스냅샷 손상으로 판단되면 즉시 폴백:
   메모리 스냅샷 폐기 → 볼륨만으로 콜드 부팅
   → 프로세스는 유실되지만 로그인 세션·파일은 보존됨
2. 고객에게 degraded resume 사실을 응답에 명시
   { "status": "ACTIVE", "warning": "process_state_lost" }
3. 볼륨까지 손상 → 최근 백업 스냅샷(최대 24시간 전)으로 복원 제안
목표 복구 시간: 2분 (폴백 부팅)
```

**설계 원칙:** 프로세스 보존 실패가 **데이터 손실로 번지지 않게** 한다. 메모리 스냅샷과 볼륨은 독립적으로 저장하며, 메모리 스냅샷은 언제든 버릴 수 있는 캐시로 취급한다.

#### RB-3. 스트리밍 끊김

```text
1. WebRTC ICE 재협상 자동 시도 (3회)
2. 실패 → TURN/TCP 강제 전환
3. 실패 → WebSocket JPEG 폴백 진입 + 뷰어에 배지 표시
4. 그래도 실패 → Desktop 자체는 정상임을 UI에 명시
   ("화면 전송만 실패했으며 Agent 작업은 계속 진행 중입니다")
```

스트리밍 장애가 **Desktop 장애로 오인되지 않게** 하는 것이 핵심이다. 둘은 독립 컴포넌트다.

#### RB-4. 호스트 노드 장애

```text
ACTIVE Desktop 이 있는 호스트가 죽음
1. 볼륨은 네트워크 스토리지에 있으므로 생존
2. 다른 호스트에서 볼륨 재부착 후 콜드 부팅
3. 프로세스 상태는 유실 → 고객에게 process_state_lost 통지
목표: 10분 내 재기동
```

**따라서 볼륨은 반드시 노드 로컬이 아닌 네트워크 스토리지에 둔다.** 이는 §2.2 웜스타트 KPI(로컬 NVMe < 5s)와 상충하므로, **메모리 스냅샷은 로컬 NVMe, 볼륨은 네트워크 스토리지**로 분리한다. 스냅샷을 잃어도 볼륨이 살아 있으면 복구된다.

### 12.3 ERROR 상태에서의 데이터 회수

Desktop이 복구 불가 상태여도 **볼륨은 살아 있다.** 사용자가 데이터를 잃지 않도록 다음을 보장한다.

| 가능 | 방법 |
|---|---|
| 파일 조회·다운로드 | `GET /v1/desktops/{id}/files` (Desktop 스코프, ERROR 상태에서도 동작) |
| 볼륨 전체 내보내기 | `POST /v1/desktops/{id}/export` |
| 새 Desktop으로 볼륨 이전 | `POST /v1/desktops` + `clone_volume_from: dsk_...` |

ERROR Desktop은 **자동 삭제하지 않는다.** 스토리지 요금은 계속 부과되며, 30일 후 삭제 예정 알림을 보낸다.

### 12.4 용량 산정 및 배치

§8.3이 `spec_tier` 를 네 등급으로 나눴으므로, 단일 스펙을 전제한 계산은 더 이상 성립하지 않는다. **배치 정책을 먼저 정하고 등급별 밀도를 유도한다.**

#### 배치 정책 — 등급별 호스트 풀 분리

**하나의 호스트에는 하나의 `spec_tier` 만 배치한다.** 혼합 배치를 허용하면 남은 메모리와 남은 인코딩 예약분이 서로 다른 단위로 파편화되어 스케줄러가 매번 다른 산식을 써야 한다.

이미 스냅샷 어피니티 때문에 **CPU 템플릿별로 호스트 풀을 나누고 있으므로**(§7.4), 등급 축을 하나 더 얹는 것은 새 메커니즘이 아니다.

```text
호스트 풀 = (CPU 템플릿) × (spec_tier)
   예) tmpl-a/standard, tmpl-a/large, tmpl-b/standard, …
```

- resume은 **스냅샷이 있는 풀**로만 배치된다. 등급은 생성 시 고정이므로 풀이 바뀔 일이 없다.
- 등급 변경은 지원하지 않는다. 필요하면 새 Desktop을 만들고 볼륨을 복제한다(`clone_volume_from`).

#### 등급별 밀도 (32 vCPU / 128GB 호스트, 호스트 오버헤드 16GB 차감)

| `spec_tier` | vCPU/메모리 | 호스트당 ACTIVE | 테넌트 vCPU 합 | 테넌트 오버커밋 | 인코딩 예약 | 동시 관찰 |
|---|---|---|---|---|---|---|
| `light` | 2 / 2GB | **56** | 112 | 3.50 : 1 ⚠ | 11 vCPU | 6 |
| `standard` | 2 / 4GB | **28** | 56 | 1.75 : 1 | 11 vCPU | 6 |
| `large` | 4 / 8GB | **14** | 56 | 1.75 : 1 | 11 vCPU | 6 |
| `gpu` | 4 / 8GB + GPU | **14** | 56 | 1.75 : 1 | GPU 세션 한도에 종속 | 실측 |

**2.5:1 상한은 테넌트 할당이 아니라 호스트 물리 vCPU 전체를 기준으로 한다.** 인코딩 예약분도 실제 물리 CPU를 쓰므로 이를 빼고 세면 상한이 아무것도 규율하지 못한다.

```text
(테넌트 vCPU 합 + 인코딩 예약 11) ÷ 32 물리 ≤ 2.5
```

**`light` 는 이 상한에 걸린다.** 메모리로는 56대가 들어가지만 CPU가 먼저 막는다.

```text
사용 가능 테넌트 vCPU = 2.5 × 32 − 11 = 69
light 상한 = ⌊69 ÷ 2⌋ = 34대
검산: (34×2 + 11) ÷ 32 = 2.47 ≤ 2.5 ✓   메모리 34×2GB = 68GB ≤ 112GB (비제약)
```

| 최종 배치 상한 | 값 | 제약 요인 | 총 오버커밋 |
|---|---|---|---|
| `light` | **34** | **CPU** (2.5:1 상한) | 2.47 : 1 |
| `standard` | **28** | 메모리 | 2.09 : 1 |
| `large` / `gpu` | **14** | 메모리 | 2.09 : 1 |

경량 티어를 쓰는 워크로드가 오히려 CPU를 더 자주 쓴다는 점(브라우저 렌더링)을 감안하면 34는 보수적이지도 않다. **Phase 1 실측 대상**이다.

#### 불변 규칙

| 규칙 | 값 | 근거 |
|---|---|---|
| 메모리 오버커밋 | **1 : 1 (금지)** | 스왑이 발생하면 GUI 반응성이 붕괴한다. 등급과 무관하게 적용 |
| CPU 오버커밋 상한 | 2.5 : 1 | **(테넌트 vCPU + 인코딩 예약) ÷ 물리 vCPU** 기준. 초과하는 등급은 대수를 줄여 맞춘다 |
| 인코딩 예약 | 호스트당 11 vCPU (테넌트 할당과 별개) | 6 × 1.8 vCPU = 10.8 (OpenH264, §6.3) |
| 동시 관찰 | 호스트당 6개 | 인코딩 예약분에서 유도. 초과는 `NO_STREAM_CAPACITY` |
| SUSPENDED | 컴퓨트 미점유 | 단 스냅샷 저장·호스트 어피니티는 존재한다(§7.4) |

**인코딩 예약 11 vCPU는 등급과 무관하게 고정이다.** 관찰 비용은 화면 해상도가 결정하며 Desktop 등급과 무관하기 때문이다. 그 결과 **Desktop 1대가 부담하는 예약분이 등급마다 달라진다.**

| 등급 | 호스트당 대수 | Desktop당 예약 vCPU |
|---|---|---|
| `light` | 34 | 0.32 |
| `standard` | 28 | 0.39 |
| `large` / `gpu` | 14 | **0.79** |

대수가 적을수록 고정 예약분을 나눠 질 Desktop이 없어 단가가 오른다. **관찰이 잦은 워크로드를 `large` 로 운영하면 원가 효율이 가장 나쁘며**, 이 경우 `gpu` 등급이 정답이다 — 인코딩이 GPU로 넘어가 이 예약분 자체가 사라진다.

**동시 관찰 6개는 낮다.** 관찰 비율이 20%를 넘는 워크로드(교육·감사·데모)는 소프트웨어 인코딩으로 감당되지 않으므로 **GPU 티어가 선택이 아니라 요구사항**이 된다. 지연에 민감한 용도도 마찬가지다(§6.3).

**Windows는 별도 산정:** 기본 메모리 요구가 4~8GB이고 유휴 CPU 사용량도 높아 `large` 기준 호스트당 12대 수준으로 본다. 조달이 Azure이므로(§19.3) 호스트 규격 자체가 다르며, Phase 3에서 재산출한다.

**이 표의 수치는 실측 대상이다.** 밀도·오버커밋·인코딩 비용은 Phase 1 종료 시 실측해 확정하며(§18), 배치 정책(등급별 풀 분리)만 지금 확정한다. 스케줄러는 정책이 있어야 쓸 수 있고 상수는 나중에 바꿔 끼울 수 있다.

### 12.5 경량화 레버

§12.4의 밀도는 현재 이미지 구성 기준이다. 무게의 근원은 **Desktop 하나가 전체 OS + 디스플레이 세션**이라는 사실이며, 헤드리스 대안 대비 구조적으로 10~20배 무겁다(§4.3). 아래는 그 구조를 유지하면서 줄일 수 있는 여지이며, **전부 실측 후 적용 판단**한다.

| # | 레버 | 추정 절감 | 위험 |
|---|---|---|---|
| 1 | **공유 읽기전용 rootfs** | 호스트당 4~5GB | 낮음 |
| 2 | **데스크톱 환경 지연 기동** | 250~350MB/대 | 낮음 |
| 3 | Chrome 프로세스 모델 튜닝 | Chrome RSS의 20~30% | 낮음 |
| 4 | free page reporting (balloon) | 할당량의 15~30% | 중간 |
| 5 | `auto_suspend` 공격적 튜닝 | 활성 대수 자체 감소 | 낮음 |
| 6 | zram | 미상 | 높음 |

**1. 공유 읽기전용 rootfs — 가장 크다.** 지금은 Desktop마다 자기 볼륨을 가지므로 Chrome 바이너리·폰트·라이브러리가 **Desktop 수만큼 페이지 캐시에 중복**된다. 28대면 같은 Chrome이 28벌 올라간다. rootfs를 호스트당 1벌의 읽기전용 블록 디바이스로 두고 Desktop별 오버레이에만 쓰기를 받으면 중복이 사라진다.

**오버레이는 영속 볼륨의 일부여야 한다.** `app.install` 은 `/usr`·`/opt` 에 쓰는데, §19.2가 영속으로 마운트하는 것은 `/home/iapetus` 와 앱 데이터뿐이다. 오버레이를 휘발성으로 두면 **설치한 앱이 재시작에서 사라지고**, 이는 §1.3·§4.2가 내건 "설치 앱을 다음 실행까지 들고 간다"는 약속을 깬다. 이 모호함은 레버 1 이전부터 있었으나 레버 1이 그것을 드러내므로 여기서 정한다.

**부작용 — 호스트 풀 키에 축이 하나 늘어난다.** 공유 rootfs는 이미지 버전을 호스트에 고정시키므로 §12.4의 풀 키가 `(CPU 템플릿) × (spec_tier) × (이미지 버전)` 이 된다. §19.2가 이미 "메모리 스냅샷이 rootfs를 고정한다"고 적어둔 것과 같은 제약이 호스트 단위로 올라온 것이다. **§19.4가 `iapetusd` 를 읽기전용 squashfs로 주입하는 것과 같은 패턴의 확장**이며, Firecracker는 블록 디바이스를 여러 개 붙일 수 있다.

**2. 데스크톱 환경 지연 기동.** *(X11 WM만 후보다 — 캡처(XGetImage)·입력(XTEST)·클립보드(X11 selection)가 전부 X11이므로(§6.2), Wayland 컴포지터로 바꾸면 셋이 동시에 깨진다.)* XFCE 세션(xfwm4 + xfsettingsd + thunar + panel + dbus)이 300~400MB를 상시 점유하는데, **Agent는 이를 거의 쓰지 않는다** — 앱을 직접 실행하고 좌표로 조작하므로 창 관리자만 있으면 된다. Agent 전용 상태에서는 Xvfb + 최소 X11 WM(openbox/i3, 10~30MB)만 띄우고, **사람이 뷰어에 접속할 때 패널·파일관리자를 기동**한다. §6.3의 "뷰어 0명이면 인코더 정지"와 정확히 같은 사고다 — 사람이 없을 때 사람용 부품을 끈다.

**3. Chrome 튜닝.** 실제 최대 소비자는 데스크톱 환경이 아니라 Chrome이다(탭 5개에 800MB~1.5GB). `--process-per-site`(site-per-process 대신), `--disable-dev-shm-usage`, GPU 합성 비활성. `light` 등급의 탭 상한(§8.3)과 함께 적용한다.

**4. balloon 회수는 밀도 계산에 넣지 않는다.** 게스트가 실제로 비어 있는 페이지를 호스트에 반납하는 것은 오버커밋이 아니므로 §12.4의 1:1 원칙을 깨지 않는다. 다만 **회수분을 다시 배치에 쓰면 그 순간 오버커밋이 된다.** 버퍼로만 두고 밀도 상수는 할당량 기준을 유지한다. **스냅샷과도 상호작용한다** — balloon으로 반납된 게스트를 스냅샷·복원하면 복원 후 balloon을 다시 구동해야 한다(§7.4가 복원 조건에 엄격하므로 이 단계를 빠뜨리면 메모리가 이중으로 잡힌다).

**5. `auto_suspend` 튜닝이 밀도보다 효과적일 수 있다.** §12.4의 손익분기 분석이 보여주듯 비용을 지배하는 것은 호스트당 대수가 아니라 **활성 비율**이다. `light` 의 `idle_timeout_sec` 를 900 → 120으로 낮추면 활성 대수가 직접 줄어든다. 이는 **기본값을 등급별로 나누는 스키마 변경**이며(§8.3은 현재 전 등급 900 단일 기본), 적용 시 `spec_tier` 별 기본값 표를 §8.3에 추가해야 한다. 웜 스타트가 5초 이내(§2.2)라면 체감 손실이 작다.

**6. zram은 조건부다.** §12.4가 스왑을 금지한 것은 **디스크 스왑** 기준이다. zram은 압축 RAM이라 지연이 µs 단위로 성격이 다르다. RAM의 25% 이하, `light` 등급 한정으로 검토할 수 있으나 **압박 상황에서 CPU를 먹으므로** 실측 전에는 적용하지 않는다.

**적용 시 예상치**

| | 현재 | 레버 1~3 적용 후(추정) |
|---|---|---|
| `standard` 실효 메모리 | 4GB | 2.5~3GB |
| 호스트당 `standard` | 28대 | **37~44대** |
| `light` | 34대 (CPU 제약) | **34대 — 변화 없음** |

**`light` 은 이미 CPU가 제약이므로 메모리를 줄여도 대수가 늘지 않는다.** 이 등급에서는 레버 3(Chrome 튜닝)만 효과가 있다. 어떤 레버가 어느 등급에 듣는지 구분하지 않으면 헛수고를 한다.

**하지 않을 것 — 웹 전용 헤드리스 경로 분기.** 가장 가벼워지지만 런타임이 둘이 되고, 그 시장은 §4.3에서 이미 구조적으로 진다고 인정한 영역이다. **런타임을 하나로 유지하되 레버 2처럼 무거운 부분만 끄는 쪽**을 택한다.

이 절의 수치는 전부 추정이며 §18의 실측 목록에 포함된다.

### 12.6 관측성

| 계층 | 지표 |
|---|---|
| Control Plane | 요청률·오류율·지연(RED), 토큰 발급 실패율 |
| Desktop | CPU/메모리/디스크 IO, 액션 지연 히스토그램, 캡처 FPS |
| 스트리밍 | 연결 성공률, 비트레이트, 패킷 손실, 폴백 진입률 |
| 비즈니스 | Desktop 생성/삭제, ACTIVE 시간, 관찰 비율, 쿼터 도달률 |

**액션 트레이스:** 하나의 `act` 호출이 API → Control Plane → `iapetusd` → X11 까지 가는 경로를 OpenTelemetry 스팬으로 잇는다. "왜 이 클릭이 느렸는가"를 답하지 못하면 지연 KPI를 개선할 수 없다.

**폴백 진입률은 제품 지표다.** 이 값이 높으면 특정 고객사 방화벽 환경에서 제품 경험이 무너지고 있다는 뜻이므로, 인프라 지표가 아니라 고객 성공 지표로 다룬다.

## 13. 과금 모델

| 항목 | 단위 |
|---|---|
| 컴퓨트 | Desktop 실행 시간(초) × 스펙 |
| 스토리지 | 볼륨 GB-월 |
| 스냅샷 | GB-월 |
| 네트워크 | 아웃바운드 GB |
| Windows 라이선스 | Desktop-시간 추가 요금 (원가 전가, 마진 0) |
| 녹화 보관 | GB-월 |

`SUSPENDED` 상태는 컴퓨트 과금 없음 → Agent가 자주 절전하도록 유도.

**과금 설계 원칙**

1. **절전을 보상한다.** `auto_suspend` 기본 on. 유휴 Desktop이 돈을 먹지 않으므로 고객이 Desktop을 지우지 않고 유지하게 된다 — 영속성이 제품 가치이므로 삭제를 유도하는 가격은 자해다.
2. **일반 관찰은 별도 과금하지 않는다.** 사람이 화면을 보는 행위에 요금을 매기면 §14의 온보딩("먼저 보게 하라")과 충돌한다. 인코딩용 예약 CPU 비용(§12.4)은 컴퓨트 단가에 평균으로 흡수한다. **예외는 두 가지다** — ① 관찰 비율이 지속적으로 높은 계정은 GPU 티어로 유도한다 ② 강제 녹화 티어는 상시 인코딩이 필요하므로 별도 단가를 적용한다(§10.6).
3. **쿼터 초과가 작업을 죽이지 않는다.** 신규 생성만 막는다 (§8.4).

**원가 검증 전 가격 미확정:** Phase 1에서 Desktop당 실측 원가(컴퓨트·스토리지·인코딩·네트워크)를 확보한 뒤 가격을 정한다. 리스크 R-02(단위 경제성)의 완화책이며, 그 전까지 이 표는 **과금 항목의 목록일 뿐 단가가 아니다.**

## 14. 온보딩 및 사용자 여정

### 14.1 Agent 개발자: 가입 → 첫 조작

**목표: 15분 내 첫 성공.** 이 시간을 넘기면 이탈한다.

```text
1. 가입 → 프로젝트 자동 생성 → Project Key 발급          (1분)
2. 대시보드 "Desktop 만들기" 클릭 또는 API 1회 호출         (15초 + 부팅 15초)
3. 대시보드에서 Desktop 화면이 즉시 보임  ← 결정적 순간
4. SDK 설치 후 예제 5줄 실행                              (3분)
5. 브라우저에서 그 조작이 실시간으로 움직이는 것을 확인     ← "아, 이게 되는구나"
```

3번과 5번이 온보딩의 전부다. **화면을 못 보면 이 제품은 이해되지 않는다.** 코드를 실행했는데 무슨 일이 일어났는지 알 수 없으면 개발자는 떠난다. 그래서 대시보드에서 Desktop을 만들면 **뷰어가 기본으로 열려 있어야** 한다.

**첫 실행 예제는 반드시 눈에 보이는 것으로 한다.**

```python
from iapetus import Iapetus

client = Iapetus(api_key="sk_iap_...")
desktop = client.desktops.create(
    name="my-first-desktop",
    owners=[{"type": "agent", "id": "agent_me"}],   # 사람은 부트스트랩 예외로 나중에 추가 (§8.1)
)

print(f"👀 지금 여기서 보세요: {desktop.viewer_url}")   # ← 먼저 출력

with desktop.session() as c:
    c.launch_app("chrome", wait_for_window=True)
    c.type("iapetus")
    c.key("Enter")
```

`viewer_url` 을 **작업 시작 전에** 출력하는 것이 의도적 설계다. 사용자가 브라우저를 열 시간을 준 뒤 조작이 시작되게 한다.

### 14.2 사람 Owner: 최초 세팅 여정 (S5)

Agent에게 자격증명을 넘기지 않는 권장 경로다.

```text
[고객사 제품 화면]
   "메신저 연동하기" 버튼
         │
         ▼
고객사 서버가 Viewer Token 발급 (control: write = 요청 가능 최대 권한)
         │
         ▼
[Iapetus 뷰어 열림 — 임베드 또는 새 창]
   ┌──────────────────────────────────────┐
   │  🖥  내 Desktop                       │
   │  ┌────────────────────────────────┐  │
   │  │                                │  │
   │  │   (실제 데스크톱 화면)           │  │
   │  │                                │  │
   │  └────────────────────────────────┘  │
   │  [메신저 열기]    ← 가이드 버튼        │
   │  상태: 관찰 중  [조작하기] ← 클릭 필요  │
   └──────────────────────────────────────┘
         │
         ▼
사용자가 [조작하기] 클릭 → control/acquire → WRITE 획득 (§8.1)
         │
         ▼
사용자가 직접 로그인 (2FA 포함) — 자격증명은 우리도 Agent도 못 봄
         │
         ▼
   "연동 완료" → 뷰어 닫기 → Agent가 이어받음
```

**가이드 오버레이:** 뷰어에 고객사가 지정한 단계별 안내(예: "메신저 아이콘을 클릭하세요")를 띄울 수 있게 한다. 원격 데스크톱을 처음 쓰는 사용자는 무엇을 해야 할지 모른다.

### 14.3 상시 사용 여정

| 상황 | 사용자가 하는 일 |
|---|---|
| 평소 | 아무것도 안 함. Agent가 알아서 함 |
| 확인하고 싶을 때 | 대시보드에서 썸네일 확인 (§6.3) → 궁금하면 클릭해 라이브 관찰 |
| Agent가 막혔을 때 | 알림 수신 → 뷰어 진입 → 제어권 선점 → 해결 → 반환 |
| 결과 확인 | 파일 다운로드 또는 Desktop에서 직접 열어봄 |
| 문제 조사 | 세션 녹화·감사 로그 재생 |

### 14.4 로컬 개발 경험

SDK를 붙이기 전에 **결제 없이 로컬에서 돌려볼 수 있어야** 한다.

```bash
# 한 줄로 로컬 Iapetus 실행 (Control Plane + Desktop 1개 + 뷰어)
docker compose up

# → API:    http://localhost:8080
# → 뷰어:   http://localhost:3000
# → Desktop: 자동 생성됨 (dsk_local)
```

| 로컬에서 되는 것 | 안 되는 것 |
|---|---|
| Computer API 전체 | 멀티테넌트 격리 (runc 사용, §19.2) |
| 뷰어·스트리밍 | suspend/resume 프로세스 보존 |
| Linux Desktop | Windows Desktop |
| 영속 볼륨 | 멀티 리전, 웜 풀 |

**SDK는 엔드포인트만 바꾸면 로컬↔클라우드가 동일하게 동작한다.** 로컬 전용 코드 경로를 만들지 않는다.

### 14.5 온보딩 KPI

| 지표 | 목표 |
|---|---|
| 가입 → 첫 Desktop 생성 | 중앙값 3분 이내 |
| **가입 → 첫 성공 액션 (time-to-first-action)** | **중앙값 15분 이내** |
| 첫 세션에서 뷰어를 연 비율 | > 80% (열지 않은 사용자는 이탈률이 급증할 것으로 가정, 검증 필요) |
| 문서 없이 첫 액션 성공 비율 | > 50% |
| 7일 리텐션 (가입 후 재방문) | > 40% |

**측정 시작 시점:** 이 지표들은 셀프서비스 가입이 열리는 **Phase 2부터** 유효하다. Phase 1은 멀티테넌트 격리가 없어(§19.2) 초대 기반 파일럿으로만 운영하며, 그 기간에는 정성 인터뷰로 대체한다.

## 15. 테스트·검증 전략

GUI 자동화 플랫폼은 일반 백엔드와 실패 양상이 다르다. **화면은 비결정적이고, 게스트 OS는 블랙박스이며, 지연이 곧 기능이다.** 테스트 전략을 여기에 맞춘다.

### 15.1 테스트 계층

| 계층 | 대상 | 도구 | 실행 시점 |
|---|---|---|---|
| **L1 단위** | `iapetus-proto` 직렬화, 좌표 변환, 정책 평가, 토큰 검증 | `cargo test` | 매 커밋 |
| **L2 게스트 통합** | 실제 Xvfb 안에서 입력·캡처가 동작하는가 | 컨테이너 내 통합 테스트 | 매 커밋 |
| **L3 API 계약** | REST/WS 스키마, 에러 코드, 멱등성, 인증 | OpenAPI 기반 계약 테스트 | 매 커밋 |
| **L4 E2E 시나리오** | S1~S6 전체 흐름 | 실제 Desktop + 실제 앱 | 매 머지 + 야간 |
| **L5 부하·내구** | 동시 Desktop 수, 스트리밍 밀도, 7일 연속 운전 | k6 + 자체 하네스 | 주간 |
| **L6 카오스** | 호스트 강제 종료, 스냅샷 손상, 네트워크 단절 | 장애 주입 | 릴리스 전 |

### 15.2 L2 게스트 통합 — 핵심 테스트

이 계층이 가장 중요하다. 여기서 잡지 못한 버그는 프로덕션에서만 드러난다.

```rust
#[test]
fn 클릭_좌표가_실제_창_좌표와_일치한다() {
    let d = TestDesktop::launch();           // Xvfb + 테스트 앱
    d.open_target_window(400, 300, 100, 50); // 알려진 위치에 버튼
    d.input().click(425, 315, Button::Left, 1).unwrap();
    assert_eq!(d.target_app().last_click(), Some((25, 15))); // 창 기준 상대좌표
}

#[test]
fn 한글_입력이_조합없이_그대로_전달된다() {
    let d = TestDesktop::launch();
    d.focus_text_field();
    d.input().type_text("안녕하세요", Duration::from_millis(10)).unwrap();
    assert_eq!(d.text_field_value(), "안녕하세요");  // 자모 분리 없음
}

#[test]
fn 스케일된_스크린샷도_좌표계는_물리픽셀이다() {
    let d = TestDesktop::launch();
    let shot = d.display().screenshot_scaled(0.5).unwrap();
    assert_eq!(shot.image_size(), (960, 540));
    assert_eq!(shot.display.width, 1920);   // 좌표 기준은 불변 (§7.2)
}
```

**한글 입력 테스트를 CI 필수로 둔다.** IME 문제는 한국 시장에서 치명적인데 영어권 오픈소스 스택에서는 검증되지 않는 영역이다.

### 15.3 화면 비결정성 대응

스크린샷 픽셀 비교는 **하지 않는다.** 폰트 힌팅, 안티에일리어싱, 커서 깜빡임, 애니메이션 때문에 매번 다르다.

| 문제 | 대응 |
|---|---|
| 픽셀 미세 차이 | 픽셀 비교 금지. **의미 기반 단언**(창 제목, 앱 상태, 파일 내용)으로 검증 |
| 애니메이션 진행 중 캡처 | `wait_for(mode: screen_stable)` — 연속 2프레임의 변화율이 임계 이하일 때까지 대기 |
| 폰트 렌더링 환경차 | 테스트 이미지에 폰트 버전 고정. 이미지 태그로 재현성 확보 |
| 앱 시작 시간 편차 | 고정 sleep 금지. `wait_for_window` + 타임아웃 |
| 네트워크 의존 화면 | E2E에서 외부 사이트 대신 **로컬 테스트 페이지** 사용 |

**스크린샷 회귀가 꼭 필요한 경우**(뷰어 UI 등)에만 perceptual diff(SSIM 임계 0.98)를 쓰고, 실패 시 사람이 확인하는 승인 절차를 둔다.

### 15.4 시나리오 → 수용 테스트 매핑

§3.2의 시나리오를 그대로 자동화 테스트로 만든다. **PRD의 시나리오와 테스트가 1:1로 대응**하므로 요구사항 누락이 드러난다.

| 시나리오 | 수용 테스트 | 검증 포인트 | Phase |
|---|---|---|---|
| S1 웹 검색 | `e2e/s1_chrome_search` | 앱 실행 → 입력 → 결과 화면 도달 | 1 |
| S2 메신저 발송 | `e2e/s2_messenger_send` | 로그인 상태 재사용, 메시지 실제 전송 | 3 |
| S3 정기 루틴 | `e2e/s3_scheduled_routine` | **7일 연속 실행 후에도 로그인 유지** | 2 |
| S4 사람 개입 | `e2e/s4_preempt` | 선점 500ms 이내, Agent가 `control.revoked` 수신 | 2 |
| S5 사람 최초 세팅 | `e2e/s5_human_setup` | 사람 로그인 후 Agent가 세션 재사용 성공 | 2 |
| S6 결과 확인·수정 | `e2e/s6_shared_file` | 양측이 같은 파일을 보고 수정 | 2 |

**S3가 가장 중요한 테스트다.** 이 제품의 핵심 주장("영속성")을 유일하게 증명하며, 7일이라는 시간 축 때문에 다른 방법으로 대체할 수 없다. CI와 별도로 **상시 운영되는 장기 카나리아**로 돌린다.

### 15.5 부하 목표

| 시나리오 | 목표 |
|---|---|
| 동시 ACTIVE Desktop | 리전당 10,000 (§11) |
| 동시 스트리밍 뷰어 | 1,000 세션에서 프레임 지연 < 200ms 유지 |
| 액션 처리량 | Desktop당 20 req/s에서 p95 < 300ms |
| Desktop 생성 폭주 | 분당 500개 생성 시 콜드스타트 KPI 유지 |
| 7일 내구 | 메모리 누수 없음, 액션 지연 증가 < 10% |

### 15.6 Phase 완료 기준 (테스트 연결)

각 Phase는 **해당 테스트가 CI에서 녹색**일 때만 완료로 인정한다. "동작하는 것 같다"는 완료가 아니다.

| Phase | 필수 통과 |
|---|---|
| 1 | L1, L2, L3 전체 + `e2e/s1_chrome_search` |
| 2 | + `s3`(7일 카나리아), `s4`, `s5`, `s6` + L6 카오스(RB-1, RB-2) |
| 3 | + `s2` + Windows L2 전체 |
| 4 | + L5 부하 목표 전부 |

## 16. 로드맵

### Phase 1 — MVP (Linux, Docker)
- Linux XFCE OCI 이미지 + Docker 런타임 (셀프호스트/개발용)
- `iapetusd` Rust 데몬 + `iapetus-proto` 공유 크레이트
- Desktop 생성/조회/삭제, 영속 볼륨
- Computer API: screenshot, click, type, key, scroll, launch_app, shell.exec
- OWNER 권한 모델 (root + sudo), 임의 실행/설치
- 사전 설치 카탈로그: chrome, terminal, files, text_editor
- REST API + Python/TS SDK
- 사람용 뷰어: 스트리밍 + 완전 입력 제어 + **배타적 제어권 리스**(선점·이벤트는 Phase 2). 리스 없이 사람과 Agent가 동시에 입력하면 화면이 깨지므로(§5.6) Phase 1에도 최소한의 상호배제는 필요하다
- **완료 기준:** S1 시나리오(크롬 검색)가 API만으로 성공

### Phase 2 — 영속성 + 개입 + 멀티테넌트 격리
- **Firecracker microVM 전환** (이미지 정의 동일, OCI→rootfs 변환. Kata는 스냅샷 부재로 미채택 §6.4)
- Suspend/Resume (메모리 스냅샷), auto-suspend
- window.* API, wait_for, act 배치 실행
- 제어권 중재 (사람 선점 / 반환) + 이벤트 스트림
- 감사 로그, 세션 녹화
- **정책 엔진 + `secret.type` + egress 프록시** (SaaS 오픈 전 필수 — 이것 없이 멀티테넌트를 열 수 없다)
- MCP 서버
- **완료 기준:** S3 시나리오(정기 루틴, 세션 재사용)가 7일 연속 성공

### Phase 3 — Windows
- Windows VM 런타임, DXGI 캡처, SendInput
- 사내 메신저 / Excel 등 데스크톱 앱 카탈로그
- 조직 커스텀 이미지 빌드
- Windows 뷰어 특수키(Ctrl+Alt+Del) 처리
- **완료 기준:** S2 시나리오(메신저 발송)가 로그인 유지 상태로 성공

### Phase 4 — 스케일
- 멀티 리전, 스냅샷/복원, GPU Desktop (관찰 비율 높은 워크로드용)
- 시맨틱 접근성 트리 기반 조작 (좌표 의존 감소, R-05 완화)
- 임베드 뷰어 SDK, 모바일 뷰어
- 사내망 연결(VPN/PrivateLink), 오디오(v2 단방향)
- SOC 2 Type II 관측 기간 시작 (§10.5)
- **완료 기준:** §15.5 부하 목표 전부 달성

### Phase별 검증 게이트

각 Phase는 기능 목록이 아니라 **가설 검증**으로 종료를 판단한다 (§17.2).

| Phase | 검증 대상 | 실패 시 |

| 1 | 기술 실현 가능성 — GUI 조작이 API로 신뢰성 있게 되는가 | 좌표 기반 한계면 접근성 트리를 Phase 2로 당김 |
| 2 | **H-2 영속성** + H-3 사람 개입 활용도 | H-2 실패 시 제품 근거 소멸 → §17.3 중단 기준 발동 |
| 3 | H-5 데스크톱 앱 수요 | 수요 미달 시 웹·사내 프로그램으로 범위 축소 |

### 17.2 MVP 검증 가설

Phase 1~2는 기능 구현이 아니라 **가설 검증**으로 본다.

| # | 가설 | 검증 방법 | 실패 판정 |
|---|---|---|---|
| H-1 | 사람들은 "영속 데스크톱"에 돈을 낸다 | Phase 2 종료 시 유료 전환율 측정 | 무료 사용자의 유료 전환 < 5% |
| H-2 | 로그인 세션 영속성이 실제로 유지된다 | S3 카나리아를 **병렬 50대 × 30일 ≈ 1,500 resume 사이클**로 운영 | 유실 **2회 이상**(≈99.87%). 카나리아 1대로는 30 사이클뿐이라 99.9% KPI를 통계적으로 검증할 수 없다 |
| H-3 | 사람 개입 모델을 사용자가 실제로 쓴다 | 뷰어 접속률·선점 발생 빈도 | 첫 주 뷰어 접속률 < 30% |
| H-4 | 단위 경제성이 성립한다 | Desktop당 실원가 vs 가격 | 마진 < 30% |
| H-5 | 데스크톱 앱 자동화 수요가 웹보다 크다 | Phase 3 이후 앱별 사용 분포 | 데스크톱 앱 사용이 전체의 < 20% |

### 17.3 중단 기준 (Kill Criteria)

사전에 정해 두지 않으면 매몰비용 때문에 계속 가게 된다.

| 조건 | 판단 시점 | 조치 |
|---|---|---|
| H-2 실패 (영속성이 신뢰 불가) | Phase 2 종료 | **제품 근거가 사라짐.** 중단 또는 일회성 샌드박스로 피벗 |
| H-4 실패 + 개선 경로 없음 | Phase 2 종료 | 가격 재설계 또는 엔터프라이즈 전용(셀프호스트)으로 축소 |
| R-03 실현 (테넌트 침해 발생) | 즉시 | 멀티테넌트 SaaS 중단, 단일 테넌트 전용으로 전환 |
| R-01 광범위 실현 (주요 앱 다수 차단) | 상시 | 데스크톱 앱 축을 접고 웹+사내 프로그램으로 좁힘 |
| Phase 3 종료 시 유료 고객 < 10곳 | Phase 3 종료 | 시장 부재로 판단, 축소 또는 중단 |

**피벗 옵션:** 중단이 유일한 선택지는 아니다. ① 사내 자동화 온프레미스 제품 ② Agent 개발자용 테스트 인프라 ③ VDI + AI 결합 제품. 셀프호스트 경로(§19.2)를 처음부터 유지하는 이유가 여기에 있다.

## 18. 미해결 이슈 / 결정 필요

**논쟁이 있던 설계 결정은 전부 끝났다.** 모든 항목이 본문의 확정 설계로 옮겨졌으며, 취소선은 이력 보존용이다.

**단, "결정 완료"를 "구현 준비 완료"로 읽으면 안 된다.** 이 표는 *이견이 있던 것*만 다뤘다. 아무도 이견을 내지 않는 작업 — 필드·타입·상한·봉투·규약의 평범한 열거 — 은 논쟁이 없었기에 오래 비어 있었고, v0.7에서 §8.2·§8.3·§19.5·§19.6으로 채웠다. 남은 인터페이스 작업은 아래에 명시한다.

**남은 것은 문서 밖의 작업이다.** 아래는 설계가 아니라 문안 작성·외부 검토·실측·레퍼런스 집필이며, 이 문서의 완료 조건이 아니다.

| OpenH264 인코딩 비용 실측 (§6.3 1.2~1.8 vCPU 검증) | 실측 | Phase 1 종료 시 |
| 경량화 레버 효과 실측 (§12.5 6종) | 실측 | Phase 1 종료 시 |
| **API 레퍼런스 집필** — 엔드포인트별 요청·응답 전체 | 문서 | Phase 1 API 스프린트 전 |
| `iapetus-proto` 크레이트 — Protobuf 타입 정의 및 OpenAPI 생성 | 구현 | Phase 1 착수 시 |

**API 레퍼런스와 이 문서의 경계 판별 기준:** 어떤 필드가 PRD에 있어야 하는지는 다음 하나로 가른다 — **그 필드의 존재 자체가 능력(capability)을 규정하는가, 아니면 이미 정해진 능력을 직렬화할 뿐인가.**

- 존재가 능력을 규정하면 **PRD가 소유한다.** 예: Image의 `source`(빌드 팜을 운영할지가 결정된다), `PUT .../policy`(Desktop별 정책이 v1에 존재하는지가 결정된다), `viewer_url`(온보딩의 결정적 순간이 작동하는 방식이다).
- 능력이 이미 정해졌고 모양만 남았으면 **레퍼런스와 `iapetus-proto` 가 소유한다.** 예: `window.list` 가 id/title/bounds/focused를 반환하는 것, `GET /v1/health` 의 본문.

이 기준이 필요한 이유는, 레퍼런스 집필자가 "이건 PRD로 되돌려야 하나"를 판단할 규칙이 있어야 하기 때문이다.

PRD는 **구현자가 스스로 정하면 안 되는 결정**만 담는다 — 식별자 체계, 페이지네이션 방식, 오류 봉투, 상한값, 멱등성 규약, 전송 프로토콜(§8.2·§8.3·§19.5). 엔드포인트별 필드 나열은 레퍼런스와 `iapetus-proto` 가 담당한다. 이 경계를 두는 이유는, 같은 내용을 두 문서에 적으면 반드시 갈라지기 때문이다.

## 19. 기술 스택

### 19.1 언어: Rust

| 컴포넌트 | 언어 | 근거 |
|---|---|---|
| **iapetusd** (게스트 내 데몬) | **Rust** | 단일 정적 바이너리 → 런타임 의존성 없이 어떤 이미지에도 투입. X11/Win32 FFI 안전. 상시 실행이라 GC 스톨 없는 저지연·저메모리가 직접 이득 |
| **Control Plane** (API/오케스트레이터) | **Rust** (axum + tokio) | 세션당 WS 연결 수천 개 유지. async 런타임 성숙. iapetusd와 프로토콜 타입 크레이트 공유 |
| **스트리밍 게이트웨이** | **Rust** (webrtc-rs) | 프레임 경로에서 GC/복사 최소화 |
| SDK | Python / TypeScript | 소비자는 Agent 개발자. 이쪽은 Rust 아님 |
| CLI | Rust (clap) | Control Plane 크레이트 재사용 |
| 대시보드 | TypeScript / React | |

**Rust 선택의 실제 근거 (성능만이 아님)**
- `iapetusd`는 고객 이미지 안에 들어간다. Python 런타임이나 JVM을 같이 넣을 수 없다. 정적 링크된 단일 바이너리가 사실상 요구사항이다.
- X11(XTEST), DXGI, SendInput은 전부 unsafe FFI다. Rust는 이 unsafe를 좁은 모듈에 가두고 나머지를 안전하게 유지할 수 있다.
- 액션 프로토콜 타입을 `iapetus-proto` 크레이트 하나로 정의하고 Control Plane과 iapetusd가 공유 → 스키마 드리프트 제거. SDK용 JSON Schema/OpenAPI는 이 크레이트에서 생성.

**Rust 선택의 비용 (인정하고 감수)**
- 초기 개발 속도가 Go/TypeScript보다 느리다. Windows 캡처·입력 계층은 특히 느릴 것이다.
- Windows 지원 시 `windows-rs` 크레이트 학습 비용이 있다.
- 완화책: v0 프로토타이핑은 Python으로 하되, **iapetusd는 처음부터 Rust로 쓴다** (나중에 바꾸기 가장 어려운 컴포넌트이므로).

**워크스페이스 구조 (안)**
```text
iapetus/
├── crates/
│   ├── iapetus-proto/      # 액션/이벤트 스키마 (공유)
│   ├── iapetusd/           # 게스트 데몬
│   │   ├── input/          # linux(xtest) | windows(sendinput)
│   │   ├── capture/        # linux(x11/pipewire) | windows(dxgi)
│   │   ├── apps/           # launch / install / process
│   │   └── fs/
```

### 19.2 패키징: Docker — 단, 격리 경계로는 쓰지 않는다

Docker는 **이미지 빌드·배포 포맷**으로 쓴다. 이 결정은 좋다.

| 용도 | Docker 적합성 |
|---|---|
| Desktop 이미지 정의(Dockerfile), 레이어 캐시, 레지스트리 배포 | ✅ 최적 |
| 로컬 개발 / 셀프호스트 / 단일 테넌트 배포 | ✅ 충분 |
| **멀티테넌트 SaaS에서 서로 모르는 고객 격리** | ❌ **부적합** |

**이유:** §7.3에서 Agent에게 게스트 root를 주기로 했다. Docker 컨테이너 안의 root는 호스트 커널을 공유한다. 커널 취약점 하나로 컨테이너 탈출 → 다른 고객 Desktop 침해가 가능하다. "root를 주는 컨테이너"는 보안 경계가 아니다.

**결론: 이미지는 Docker, 실행은 microVM.**

| 배포 형태 | 실행 런타임 |
|---|---|
| 로컬 개발 / 셀프호스트 / 단일 조직 전용 | Docker (`docker run`) |
| 멀티테넌트 SaaS | **Firecracker + OCI→rootfs 변환** (Kata는 스냅샷 부재로 미채택, §6.4) |
| Windows Desktop | 전용 VM (컨테이너 아님) |

**이미지 정의는 한 벌만 관리한다.** 셀프호스트는 OCI 이미지를 그대로 실행하고, SaaS는 같은 이미지를 rootfs로 변환해 Firecracker에 태운다. 고객이 커스텀 이미지를 만들 때도 Dockerfile 하나만 쓴다.

```yaml
# 셀프호스트: runc (공유 커널, 단일 테넌트 전용)
# SaaS:      Firecracker microVM (OCI → rootfs 변환, 스냅샷 지원)
#            이미지 정의(Dockerfile)는 양쪽 동일
```

**Linux Desktop 이미지 (Dockerfile 개요)**
```dockerfile
# 개발·셀프호스트용 단일 이미지. 프로덕션은 §19.4의 squashfs 블록 디바이스 주입을 쓴다.
FROM rust:1-bookworm AS builder
WORKDIR /src
COPY Cargo.toml Cargo.lock ./
COPY crates/ ./crates/
RUN cargo build --release -p iapetusd && \
    mkdir -p /out && cp target/release/iapetusd /out/

FROM debian:bookworm-slim

# fonts-noto-cjk / ibus-hangul: 한글 표시·입력 필수
RUN apt-get update && apt-get install -y --no-install-recommends \
      xvfb xfce4 xfce4-terminal dbus-x11 \
      fonts-noto-cjk ibus ibus-hangul \
      sudo ca-certificates curl \
 && rm -rf /var/lib/apt/lists/*

# Chrome 등 기본 카탈로그 앱
COPY scripts/install-apps.sh /tmp/
RUN /tmp/install-apps.sh

# 공용 OS 계정 — 사람과 Agent가 이 하나를 공유 (§5.2)
# NOPASSWD sudo. 별도 비밀번호를 두지 않으므로 password_ref 개념도 없다.
RUN useradd -m -s /bin/bash iapetus \
 && echo 'iapetus ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/iapetus

# Rust 데몬: 정적 바이너리 하나만 투입
COPY --from=builder /out/iapetusd /usr/local/bin/iapetusd

ENV DISPLAY=:1
USER iapetus
ENTRYPOINT ["/usr/local/bin/iapetusd", "--supervise-x11"]
```

`iapetusd`가 Xvfb·XFCE 세션을 직접 supervise한다. 별도 supervisord를 넣지 않는다 (프로세스 트리를 데몬이 알아야 `app.list`·`process.kill`이 정확해진다).

**베이스 이미지 업그레이드는 SUSPENDED Desktop에 즉시 적용되지 않는다.** 메모리 스냅샷에는 그 시점의 커널과 rootfs가 묶여 있으므로, 이미지를 새 버전으로 올려도 스냅샷에서 재개하면 옛 이미지로 깨어난다. 적용은 **다음 콜드 부팅(restart 또는 스냅샷 폐기 후 resume)** 시점이며, 보안 패치가 필요하면 고객에게 재시작을 예고한다(§19.3과 동일 절차).

**영속성과 이미지의 관계:** 이미지는 무상태(stateless)로 유지하고, `/home/iapetus`(공용 OS 계정의 홈)와 앱 데이터는 **영속 볼륨을 마운트**한다. 이미지를 새 버전으로 교체해도 Chrome 쿠키·메신저 로그인은 유지된다. Suspend/Resume의 프로세스 보존은 컨테이너로는 불완전하므로(CRIU 의존, 취약함) **microVM 스냅샷이 있는 SaaS 환경에서만 완전 보장**한다. Docker 셀프호스트에서는 `restart` 수준(볼륨만 보존)으로 명시한다.

### 19.3 Windows 조달 방식

**문제:** Windows를 멀티테넌트 SaaS로 재판매하려면 일반 볼륨 라이선스(VL)로는 불가능하고 Microsoft SPLA 계약이 필요하다. SPLA는 최소 약정·월별 보고·감사 의무가 따라오며, 검증되지 않은 제품이 초기에 지기에는 무거운 부담이다.

**결정: Phase 3은 Azure에서 Windows 인스턴스를 조달한다.**

| 방식 | 채택 | 근거 |
|---|---|---|
| **Azure Windows 인스턴스** | ✅ Phase 3 | 라이선스가 인스턴스 요금에 포함되어 재판매 적격성 문제를 클라우드 제공자가 해결한다. 계약 리드타임 0 |
| 자체 SPLA 계약 | △ Phase 4 이후 | Windows Desktop이 월 500개를 넘으면 원가가 Azure보다 유리해진다. 그 시점에 전환을 재검토 |
| 일반 VL 전용 | ❌ | 멀티테넌트 재판매에 사용할 수 없다. 법적 리스크 |

**대가를 명시한다:** Linux는 자체 인프라, Windows는 Azure가 되어 **리전·네트워크·운영이 이원화**된다. Windows Desktop의 지연·가용성 KPI는 Azure 리전 기준으로 별도 측정하며, §12.1 SLA도 분리 산정한다. 이 복잡도를 감수하는 이유는 SPLA 협상이 Phase 3 일정을 통째로 잡아먹는 것보다 낫기 때문이다.

### 19.4 `iapetusd` 배포 및 업데이트

**문제:** 데몬을 이미지에 굽으면(§19.2 Dockerfile) 고객이 만든 커스텀 이미지(D-09)에도 특정 버전이 박힌다. 프로토콜을 고치거나 보안 패치가 나올 때마다 **고객에게 이미지 재빌드를 요구**하게 되고, 그 순간 플랫폼은 업데이트를 못 하는 상태가 된다.

**결정: 볼륨 주입 (side-loading).** 이미지에는 데몬을 굽지 않는다.

Firecracker에는 virtio-fs가 없으므로(§6.4) 파일 단위 주입이 불가능하다. **데몬은 읽기 전용 squashfs 블록 디바이스로 붙인다.**

```text
Desktop 부팅
   │
   ├─ 호스트가 읽기 전용 squashfs **블록 디바이스**를 붙임 → 게스트가 /opt/iapetus 에 마운트
   │
   └─ 이미지의 ENTRYPOINT 는 얇은 셸 스텁이 /opt/iapetus/bin/iapetusd 를 exec
```

| 방식 | 채택 | 이유 |
|---|---|---|
| 이미지에 굽기 | ❌ | 고객 이미지가 버전을 고정시킴 |
| **읽기 전용 볼륨 주입** | ✅ | 호스트가 버전 결정. 재부팅만으로 업데이트. 고객 이미지 불변 |
| 부팅 시 네트워크 다운로드 | ❌ | 콜드 스타트 지연 + 네트워크 장애 시 부팅 실패 |
| 사이드카 컨테이너 | ❌ | 게스트 디스플레이·입력에 접근하려면 같은 네임스페이스여야 함 |

**앞의 Dockerfile(§19.2)은 개발 편의용 단일 이미지 형태다.** 프로덕션 이미지에서는 `COPY --from=builder /out/iapetusd` 줄이 빠지고 ENTRYPOINT가 스텁으로 바뀐다.

**버전 협상:** Control Plane과 `iapetusd` 는 접속 시 프로토콜 버전을 교환한다.

```json
{ "daemon_version": "1.7.2", "protocol": { "min": 3, "max": 5 } }
```

- Control Plane이 지원하는 범위와 겹치면 **가장 높은 공통 버전**을 사용한다.
- 겹치지 않으면 Desktop을 `ERROR` 로 두지 않고 **`DEGRADED` 상태**로 두고, 다음 resume 때 자동으로 새 데몬 볼륨을 붙여 복구한다.
- **`auto_suspend: false` Desktop은 스스로 resume하지 않으므로 DEGRADED에 무기한 머물 수 있다.** 이런 Desktop은 7일 이상 DEGRADED가 지속되면 고객에게 알리고, 30일 경과 시 유지보수 창에서 재시작한다.
- 프로토콜 변경은 **N-2 버전까지 하위 호환**을 유지한다. 즉 데몬을 강제로 동시에 갈아엎지 않아도 된다.

**무중단 업데이트 불가 명시:** 데몬 교체는 재부팅 또는 suspend/resume이 필요하다. 실행 중인 Desktop을 건드리지 않으며, **긴급 보안 패치 시에만** 플랫폼이 강제 재시작을 예고(24시간 전 웹훅·대시보드 공지) 후 수행한다.

### 19.5 `iapetusd` ↔ Control Plane 전송 계약

**이 절이 없으면 두 팀이 서로 다른 프로토콜을 만든다.** "타입은 `iapetus-proto` 크레이트에 있다"는 답은 아직 존재하지 않는 코드를 가리키는 순환 참조이므로, 여기서 계약을 못 박는다.

#### 연결 모델

```text
게스트 (iapetusd)                          Control Plane
  │                                             │
  │──① 게스트가 아웃바운드로 건다 (mTLS + Guest Token)──►│
  │   세션 어피니티: 한 Desktop = 한 CP 노드        │
  │                                             │
  │◄─② HELLO / 프로토콜 버전 협상 ────────────────►│
  │                                             │
  │◄─③ 하나의 장수명 양방향 다중화 스트림 ──────────►│
  │   CP→게스트: 액션 요청  |  게스트→CP: 응답·이벤트  │
  │                                             │
  │──④ 하트비트 5초 ────────────────────────────►│
```

**"아웃바운드 전용"과 "액션 전달"이 모순되지 않는 이유:** 게스트가 연결을 걸지만 스트림은 양방향이다. Control Plane은 **그 연결 위에서** 액션을 요청할 뿐, 게스트에 새로 접속하지 않는다. 게스트는 여전히 인바운드 포트를 열지 않으며 Control Plane API를 호출할 권한도 없다(§9.1).

**RB-1의 호스트→게스트 헬스체크는 별도 경로다.** 데몬이 죽어 스트림이 끊긴 상황에서도 게스트 OS가 살아 있는지 구분하려면 네트워크와 무관한 경로가 필요하다. 런타임마다 수단이 다르다.

| 런타임 | 헬스체크 경로 | 시점 |
|---|---|---|
| Docker (Phase 1, 셀프호스트) | 컨테이너 PID 1 상태 + `docker exec` 프로브 | Phase 1 |
| Firecracker (SaaS) | **vsock** — 하이퍼바이저 내부 채널 | Phase 2 |
| Windows / Hyper-V | hvsocket | Phase 3 |

셋 다 게스트의 네트워크 네임스페이스를 거치지 않으므로 §9.1의 인바운드 차단 원칙을 깨지 않는다. **Phase 1이 Docker인데 vsock을 전제하면 RB-1의 첫 단계가 실행 불가능해지므로**, 런타임별 경로를 여기서 못 박는다.

#### 전송·프레임

| 항목 | 선택 | 근거 |
|---|---|---|
| 전송 | **gRPC over mTLS** (HTTP/2 양방향 스트리밍) | 다중화·흐름 제어·재연결이 기본 제공. Rust 생태계 성숙 |
| 직렬화 | **Protobuf** (`iapetus-proto`) | Control Plane과 게스트가 타입을 공유해 스키마 드리프트 제거(§19.1) |
| 스트림 | Desktop당 1개 장수명 양방향 스트림 | 액션·이벤트·하트비트를 한 채널에 다중화 |

```protobuf
message Frame {
  uint64 id = 1;              // 요청·응답 상관관계. 연결 내에서만 유일
  oneof body {
    ActionRequest  request   = 2;   // CP → 게스트
    ActionResponse response  = 3;   // 게스트 → CP
    Event          event     = 4;   // 게스트 → CP
    Heartbeat      heartbeat = 5;   // 양방향
    StreamChunk    chunk     = 6;   // shell.stream, 파일 전송
  }
}
```

- **같은 연결의 요청은 도착 순서대로 실행한다.** 게스트는 액션을 재정렬하지 않으며, 이것이 §7.2 `act` 의 순차 실행과 §8.5 WebSocket의 FIFO 보장을 뒷받침한다.
- 인플라이트 깊이는 **8**로 제한한다. 초과분은 HTTP/2 흐름 제어로 자연히 밀린다.
- `ActionRequest` 는 `deadline_ms` 를 포함한다. **초과하면 게스트는 응답을 보내지 않고 버린다.** 이미 실행된 입력은 되돌리지 않는다(§8.2).

#### 재연결과 인플라이트 처리

```text
연결 끊김
  → 게스트가 지수 백오프로 재연결 (1s → 최대 30s, 지터 포함)
  → 인플라이트 액션은 재전송하지 않는다
  → Control Plane은 해당 요청을 ACTION_TIMEOUT 으로 응답
  → 제어권 리스는 유지된다 (하트비트 3회 누락 전까지)
```

**재전송하지 않는 것이 핵심이다.** 끊긴 사이 실행됐는지 알 수 없는 액션을 재전송하면 클릭이 두 번 들어간다. 재시도 판단은 멱등성 키를 쥔 Agent의 몫이다(§8.4).

하트비트 3회 연속 누락(15초) 시 Desktop을 `DEGRADED` 로 표시하고, 60초 지속되면 RB-1을 발동한다(§12.2).

#### 버전 협상

```json
{ "daemon_version": "1.7.2", "protocol": { "min": 3, "max": 5 } }
```

- 겹치는 범위의 최댓값을 쓴다. 겹치지 않으면 `DEGRADED` 로 두고 다음 resume 때 새 데몬 볼륨으로 복구한다(§19.4).
- **N-2 하위 호환**을 유지해 데몬을 일괄 교체하지 않아도 되게 한다.
- 이 정수 버전은 **내부 값이며 API 클라이언트에게 노출되지 않는다**(§8.2).

#### 게스트가 책임지는 것 / 신뢰하지 않는 것

| 게스트 책임 | 참조 |
|---|---|
| 디스플레이 세션 supervise (별도 supervisor 없음) | §19.2 |
| Frame Source 유지 + **인코딩 이전 마스킹** | §10.6 |
| 뷰어 0명이면 비디오 인코더 정지 | §6.3 |
| resume 직후 강제 시각 동기화, 완료까지 액션 대기 | §7.4 |
| 제어권 이양 시 눌린 키·버튼 강제 해제 | §5.6 |

사람과 Agent 모두 게스트 root이므로 데몬은 변조될 수 있다고 가정한다(§9.1). 따라서 아래는 **게스트 보고값을 근거로 쓰지 않는다.**

| 항목 | 실제 근거 |
|---|---|
| 리소스 사용량 과금 | 하이퍼바이저 계측 |
| 네트워크 통제 | 호스트 vNIC |
| 감사 로그의 actor | Control Plane의 제어권 원장 |
| 쿼터 강제 | Control Plane |

하트비트의 `load` 는 관측용 힌트이지 과금·스케줄링 근거가 아니다.

### 19.6 게스트 ↔ 스트림 게이트웨이 미디어 계약

§6.3이 미디어 파라미터를 정했지만 전송 계약은 비어 있었다. 여기서 채운다.

| 항목 | 선택 | 근거 |
|---|---|---|
| 전송 | **SRTP over UDP**, 게스트 → 게이트웨이 단방향 | 게이트웨이가 그대로 뷰어에게 중계하므로 재패킷화가 필요 없다 |
| 경로 | 호스트 내부 네트워크. 인터넷을 타지 않음 | ICE 불필요 (§6.3) |
| 인증 | Desktop 프로비저닝 시 발급한 SRTP 키 + 게스트 mTLS 인증서로 최초 등록 | 게이트웨이는 등록된 Desktop의 SSRC만 수용 |
| 계층 ID | **RTP 확장 헤더** (`urn:3gpp:video-orientation` 방식의 1바이트 확장) | 게이트웨이가 페이로드를 열지 않고 헤더만 보고 계층을 버린다 |
| 정지 오버레이 | **미디어가 아니라 제어 스트림으로** 보낸다 (§19.5 `StreamChunk`) → 게이트웨이가 뷰어 DataChannel로 중계 | WebP는 비디오 트랙에 실을 수 없고, 게이트웨이는 디코딩하지 않으므로 통과만 시킨다 |

게이트웨이는 **끝까지 디코딩하지 않는다.** 계층 폐기는 헤더 기반, 오버레이는 통과, 마스킹은 게스트에서 이미 적용됨 — 세 가지 모두 §6.3이 기각한 트랜스코딩을 요구하지 않는다.

## 20. 용어 정의

| 용어 | 정의 |
|---|---|
| **Desktop** | 사람과 Agent가 **공동 소유**하는 영속 가상 컴퓨터 |
| **Session** | 사람 또는 Agent가 Desktop에 붙어 있는 제어 연결. 동시 다수 존재 가능하며 `WRITE` 는 1개 |
| **Computer API** | OS 무관 통합 조작 인터페이스 |
| **`iapetusd`** | 게스트 OS 내부에서 동작하는 Iapetus 데몬. 문서 전체에서 "Agent"와 구분해 이 이름만 쓴다 |
| **OWNER 모드** | 사람·Agent 양쪽이 Desktop에 대해 root/Administrator 권한을 갖는 기본 모드 |
| **restricted 모드** | 앱 화이트리스트·셸 차단이 강제되는 옵트인 모드 |
| **App 카탈로그** | 실행 가능 앱 목록. 차단 장치가 아닌 발견 도구 |
| **Owner** | Desktop에 대해 완전 권한을 갖는 주체. `human` 또는 `agent` |
| **제어권 (control lease)** | 입력을 보낼 수 있는 배타적 권리. Desktop당 1개 |
| **선점 (Preempt)** | 사람이 Agent로부터 제어권을 즉시 회수하는 동작 |
| **Suspend** | 메모리 스냅샷 후 절전. 프로세스 보존 여부는 런타임에 따라 다름 (§7.4) |
| **Project Key** | 고객사 서버가 보유하는 장기 시크릿 키. 토큰 발급·리소스 관리용 (§8.1) |
| **Agent Token / Viewer Token** | Desktop 단위로 스코프가 제한된 단기 토큰 |
| **Frame Source** | 게스트의 단일 캡처 링 버퍼. 스틸·비디오 인코더가 공유 (§6.3) |
| **Stream Gateway** | 인코딩된 스트림을 다수 뷰어에게 복제 전송하는 SFU 컴포넌트 |
| **폴백 (Fallback)** | WebRTC 불가 환경에서 WebSocket JPEG diff로 전환하는 저품질 경로 |
| **crypto-shredding** | 암호화 키를 파기해 데이터를 복호화 불능으로 만드는 삭제 방식. Iapetus는 24시간 복구 유예 후 **T+24h에 키를 파기**한다 (§10.3) |
| **DEGRADED** | 데몬 프로토콜 불일치·Guest Token 갱신 실패 등으로 기능이 제한된 상태. 다음 resume 시 자동 복구되며, resume하지 않는 Desktop은 7일 후 통지·30일 후 유지보수 재시작 (§19.4) |
| **Kill Criteria** | 제품을 중단·피벗할 사전 합의 조건 (§17.3) |
| **관찰 비율** | 전체 ACTIVE Desktop 중 사람이 스트리밍으로 보고 있는 비율. 용량 산정의 핵심 변수 (§12.4) |
