## 사용자 지시 반영
- "에이전트가 모든 권한" → OWNER 모드 기본, 화이트리스트는 restricted 옵트인
- "사용자도 모든 권한"   → 공동 소유 모델(§5.2), 단일 OS 세션 공유, 제어권 중재(§5.6)
- "사용자가 볼 수 있어야" → §6.3 파이프라인 + §7.5 가시성 3단계 + §14 온보딩에서 "먼저 보게 하라"
- "가장 최적의 방법 선택" → 후보 비교표 후 단일 채택 + 근거 + 한계 명시 방식으로 통일

## 설계 판단 기록 (되돌리려면 근거부터 볼 것)
1. 사람/Agent 별도 OS 계정 안 만듦 — 나누면 Agent가 사람 로그인을 못 씀 = 제품 존재 이유 소멸
2. 사람만 선점 가능(역방향 금지) — 권한 서열이 아니라 사람 입력 유실 방지
3. 동시 요청 큐잉 안 함 — Agent 작업이 길어 큐 대기가 타임아웃 초과. 동시성은 Desktop 분리로
4. MITM 복호화 안 함 — 사용자 은행/사내 트래픽 평문 노출이 §10 최소수집과 충돌. SNI만 검사
5. 데몬을 이미지에 안 굽음 — 고객 커스텀 이미지가 버전 고정시켜 업데이트 불가
6. 스트리밍 별도 과금 안 함 — 온보딩("먼저 보게 하라")과 충돌

## 리뷰 사이클 1 — 아키텍트 REJECTED → 수정 완료 (v0.3)

리뷰어가 찾은 것: 내부 모순 13, 기술적 오류 6, 갭 10. 전부 실제 결함이었음.
체크리스트는 통과했으나 "완결성 ≠ 정합성"이 드러남.

### 가장 값비쌌던 지적 3개
1. Kata에는 실행 중 VM 스냅샷 API가 없다 — 제품 핵심 주장(프로세스 보존 resume)을
   지원하지 않는 런타임을 골라놨었음. → Firecracker 직접 오케스트레이션으로 변경.
   부수 효과: Firecracker는 virtio-fs가 없어 데몬 주입·홈 볼륨 모두 블록 디바이스여야 함.
2. SUSPENDED 상태 볼륨 직접 쓰기 = 파일시스템 손상. 메모리 스냅샷에 얼어붙은
   페이지 캐시·inode가 디스크와 어긋남. 경고를 ACTIVE에만 달아뒀고 정작 위험한
   SUSPENDED에는 안 달아뒀었음. → 쓰기가 스냅샷을 폐기하도록 규칙화.
3. 스냅샷 복원 시 게스트 시계가 며칠 전에 멈춰 있음 → TLS/JWT/쿠키 만료 검증이 깨져
   "로그인 세션 보존 99.9%" KPI를 직접 공격. 문서에 아예 없던 요구사항.
   → 복원 직후 강제 시각 동기화를 iapetusd 책임으로 명시.

### 스스로 못 잡았을 유형
- 같은 수치를 두 섹션에 다르게 씀 (호스트당 40 vs 28)
- 한 섹션 안에서 7줄 간격으로 정반대 결정 (대기 큐 vs 큐 없음)
- 최적화(뷰어 0명 인코더 정지)와 규제 기능(강제 녹화)이 서로를 무효화
- 인코더를 게스트 안에 두면 관찰 시작 순간 Chrome이 느려짐 (비용 귀속 미결정)
- H-2 킬 기준이 통계적으로 KPI를 검증할 수 없음 (30 사이클로 99.9% 판정 불가)

### 설계 판단 추가 (v0.3)
7. 다중 관찰 적응은 시간 계층만 — 해상도를 낮추면 글자를 못 읽어 목적 자체가 사라짐
8. 게스트는 WebRTC 피어가 아님 — P2P면 게스트 IP 노출 + 관찰자당 인코딩
9. crypto-shredding은 T+24h — 24시간 복구 유예와 즉시 키파기는 양립 불가, 유예를 우선
10. egress 기본은 열림 — DROP 기본이면 온보딩 첫 시도가 실패함. DROP은 강화 모드만
11. 뷰어 접속만으로 선점 금지 — 관찰이 위험한 행동이 되면 가시성 3단계가 무의미
12. 정지 500ms 후 무손실 오버레이 — 글자를 읽는 순간은 항상 화면이 멈춰 있을 때

## 리뷰 사이클 2 — REJECTED (6건, 그중 4건은 내 1차 수정이 유발) → v0.4

### 내가 만든 결함 4개 (패턴이 뚜렷함)
공통점: **결정을 바꾸면서 그 결정이 의존하던 다른 문장을 안 고침.**
1. 시간 계층(hierarchical-P)을 채택하면서 인코더는 x264 그대로 뒀음.
   x264엔 SVC/참조리스트 API가 없어 물리적으로 불가. → OpenH264 교체,
   비용 0.8~1.2 → 1.2~1.8 vCPU, 동시 관찰 8→6, 예약 10→11 vCPU 전부 재산출.
2. "게이트웨이 트랜스코딩 기각"을 쓴 같은 개정에서 마스킹을 게이트웨이에 배치.
   → 게스트 Frame Source(인코딩 전)로 이동. 부수 효과로 무재인코딩 mux가 다시 성립.
3. 정지 시 무손실 PNG 오버레이 "대역폭 부담 없다" → 1080p PNG는 1~3MB,
   1.5Mbps에서 5~16초. 거짓. → 변경영역 WebP q95 / 200KB 상한 / DataChannel.
4. L0(7.5fps) 강등 뷰어는 프레임 간격만 133ms인데 지연 예산은 30fps만 가정.
   → L0 행 추가(153~289ms), KPI 적용 범위를 전 계층 수신 뷰어로 한정 + 강등률 지표 신설.

### 교훈
수치·기술선택을 바꿀 때 **그 값을 인용하는 모든 곳**을 기계적으로 찾아야 함.
1차 수정 때 "1 vCPU vs 1.2 vCPU"를 자체 적발했던 것과 같은 유형인데,
인코더 교체는 파급이 3개 섹션에 걸쳐 있어 육안으로는 못 잡았음.

## 설계 판단 추가 (v0.4)
13. 마스킹은 게스트에서 인코딩 전 — SFU는 픽셀을 못 바꾸고, secret.type 시점을
    아는 건 게스트뿐. 한 곳만 가리면 스크린샷·녹화·라이브 세 경로가 동시에 가려짐.

## 리뷰 사이클 3 — REJECTED (2건) → v0.5

### N-1: 가장 값진 지적 (전 사이클 통틀어)
§9.3에서 최종 사용자 보호를 표로 만들면서 "Agent 축출권", "감사 로그 열람권"에
**성격: 기술** 이라고 라벨했음. 그런데:
  - 최종 사용자의 유일한 자격증명은 Viewer Token
  - Owner 관리는 `project:manage` = Project Key 전용, Key는 브라우저에 못 내려감
  - 감사 로그 조회를 커버하는 스코프가 아예 없었음
→ 두 권리 모두 **고객사 서버를 거쳐야만** 행사 가능.
   그런데 고객사는 그 절의 위협 주체 본인. 보호가 성립하지 않음.
   "기술적 보장"이라 써놓고 실제로는 계약적 약속이었음.

수정: `desktop:owners:manage` / `desktop:audit:read` 신설 →
      actor.type=human 토큰에 **무조건 부여, 고객사가 제외 시도 시 400**.
      이걸로 비로소 라벨이 사실이 됨.

교훈: **표에 "기술/계약" 같은 성격 라벨을 붙일 때는 그 주장을 스스로 검증해야 함.**
     라벨이 설계보다 앞서가면 문서가 거짓말을 하게 됨.

### N-2: 또 같은 패턴 (수치 파급 누락)
인코더를 OpenH264로 바꾸며 vCPU 비용은 5곳에 전파했는데,
지연 예산표의 "캡처→인코딩 8~20ms(zerolatency)"만 x264 값으로 남음.
→ 12~30ms 재산출, 합계 57~199ms.
   결과가 200ms KPI를 1ms 남기고 통과 = 사실상 못 지킴을 인정하고,
   NVENC(5~10ms → 상한 179ms)로 지연 민감 용도는 GPU 권장이라는 새 결론 도출.
